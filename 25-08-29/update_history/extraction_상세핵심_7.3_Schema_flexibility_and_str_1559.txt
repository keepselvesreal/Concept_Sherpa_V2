"available": {"type": "boolean"},
"isbn": {"type": "string"}
}
}

TIP In JSON Schema, by default, fields not specified in the schema of a map are
allowed.
Theo Why is that?
Joe The reason is that usually having additional fields in a map doesn't cause
trouble. If your code doesn't care about a field, it simply ignores it. But some-
times we want to be as strict as possible, and we set additionalProperties
to false.
Theo What about the search request and response schema from the previous discus-
sions? Should we set additionalProperties to false?
Joe That's an excellent question. I'd say it's a matter of taste. Personally, I like to

Theo What's the advantage?
Joe Well, the web server is responsible for the responses it sends to its clients. It
makes sense then to be as strict as possible. However, the requests are created
by the clients, and I prefer to do my best to serve my clients even when they are

Theo Naturally. "The client is always right."

## 7.3 Schema 유연성(flexibility)과 엄격성(strictness)

본 내용은 JSON Schema를 사용하여 데이터의 유효성을 검사하는 과정에서, 스키마의 유연성과 엄격성을 조절하는 방법에 대해 설명합니다.

### 1. 기본 개념: 필드의 선택성과 필수성

*   **JSON Schema의 기본 동작**: 맵(map) 내 필드는 기본적으로 선택적(optional)입니다. 즉, 스키마에 정의되지 않은 필드가 있어도 유효성 검사에서 오류가 발생하지 않습니다.
*   **필수 필드 정의**: `required` 배열을 사용하여 필수 필드를 지정합니다. `required` 배열에 포함된 필드는 반드시 데이터에 존재해야 합니다.

### 2. 스키마 재사용 및 구성 가능성

*   **스키마 분리**: JSON Schema는 맵과 같아서 다른 맵처럼 자유롭게 조작하고 구성할 수 있습니다.
    *   예시: 재사용을 위해 개별 스키마 정의(예: `bookInfoSchema`)를 만들고, 이를 상위 스키마(예: `searchBooksResponseSchema`) 내에서 `items`의 값으로 사용할 수 있습니다.
*   **장점**: 코드의 가독성을 높이고, 스키마의 재사용성을 증대합니다.

### 3. 외부 데이터 유효성 검사

*   **데이터 유효성 검사의 중요성**: 외부 데이터 소스(예: 데이터베이스)에서 가져온 데이터는 유효성 검사를 통해 신뢰성을 확보해야 합니다.
*   **예시**: 데이터베이스 검색 응답의 스키마를 정의하여, 응답에 예상된 필드(title, isbn, available)와 데이터 타입이 포함되어 있는지 검증합니다.

### 4. `additionalProperties` 필드

*   **기본 동작**: JSON Schema는 기본적으로 스키마에 정의되지 않은 추가 필드를 허용합니다.
*   **`additionalProperties` 설정**: `additionalProperties` 필드를 사용하여 추가 필드의 허용 여부를 제어합니다.
    *   `additionalProperties: false`: 스키마에 정의되지 않은 필드는 허용하지 않음(엄격한 모드).
*   **사용 시점**:
    *   응답(response) 스키마: 엄격하게 추가 필드를 허용하지 않도록 설정하는 것이 좋습니다. 서버는 응답을 생성하므로, 불필요한 데이터를 포함하지 않도록 관리할 수 있습니다.
    *   요청(request) 스키마: 유연하게 추가 필드를 허용하는 것이 좋을 수 있습니다. 클라이언트가 보낸 요청에 대해 최대한 유연하게 처리하여, 클라이언트의 편의성을 높일 수 있습니다.

### 5. "Jon Postel의 견고성 원칙"

*   **원칙**: "보내는 데이터는 신중하게 하고, 받는 데이터는 관대하게 하라(Be conservative in what you send, be liberal in what you accept)."
*   **의미**: 서버는 자신이 생성하는 데이터(응답)에 대해 엄격하게 관리하고, 클라이언트로부터 받는 데이터(요청)는 가능한 유연하게 처리해야 합니다.
