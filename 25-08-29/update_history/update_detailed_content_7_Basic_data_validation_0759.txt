## 7 Basic data validation 상세 정보 및 새로운 내용 식별

본 텍스트는 "7 Basic data validation"에 대한 상세 정보와 새로운 내용을 식별하여 정리한 것입니다. 기존 내용을 포함하여, 더 깊이 있는 이해를 돕고, 실제 구현에 필요한 구체적인 정보들을 제공합니다.

**1. 시스템 경계 (System Boundaries)에 대한 추가 정보:**

*   **정의:** 시스템 경계는 시스템이 데이터를 주고받는 지점입니다. 이는 클라이언트, 데이터베이스, 웹 서비스 등 여러 지점이 될 수 있습니다.
*   **중요성:** 시스템 경계에서의 데이터 검증은 시스템의 무결성을 보장하는 데 가장 중요합니다. 경계에서 유효하지 않은 데이터가 유입되는 것을 막으면 시스템 내부에서 예상치 못한 데이터 문제 발생 가능성을 줄일 수 있습니다.
*   **예시:** 웹 서버의 경우, 클라이언트 요청(request) 및 응답(response), 데이터베이스 쿼리 결과, 외부 API 응답 등이 시스템 경계에 해당합니다.

**2. JSON Schema 상세 정보:**

*   **개요:** JSON Schema는 JSON 데이터의 구조를 정의하기 위한 스키마 언어입니다. 데이터의 유효성 검증을 위해 사용되며, 데이터 표현(representation)과 분리되어 유연성을 제공합니다.
*   **핵심 개념:**
*   `type`: 데이터 유형 (object, array, string, number, boolean 등)을 지정합니다.
*   `properties`: 객체(object)의 각 필드에 대한 스키마를 정의합니다.
*   `items`: 배열(array)의 각 요소에 대한 스키마를 정의합니다.
*   `enum`: 허용되는 값의 목록 (enumeration)을 정의합니다.
*   `required`: 필수 필드를 지정합니다.
*   `additionalProperties`: 객체에 스키마에 정의되지 않은 추가적인 속성의 허용 여부를 설정합니다 (true: 허용, false: 불허).
*   `allOf`, `anyOf`, `oneOf`: 스키마 조합(composition)을 위한 키워드입니다.

*   **JSON Schema 예시 (검색 요청 스키마):**
```json
{
"type": "object",
"properties": {
"title": {"type": "string"},
"fields": {
"type": "array",
"items": {
"enum": [
"publishers",
"number_of_pages",
"weight",
"physical_format",
"subjects",
"publish_date",
"physical_dimensions"
]
}
}
},
"required": ["title", "fields"]
}
```

*   **JSON Schema 예시 (검색 응답 스키마 - refactored):**
```json
var bookInfoSchema = {
"type": "object",
"required": ["title", "available"],
"properties": {
"title": {"type": "string"},
"available": {"type": "boolean"},
"subtitle": {"type": "string"},
"number_of_pages": {"type": "integer"},
"subjects": {
"type": "array",
"items": {"type": "string"}
},
"isbn": {"type": "string"},
"isbn_13": {"type": "string"}
}
};

var searchBooksResponseSchema = {
"type": "array",
"items": bookInfoSchema
};
```

*   **JSON Schema 예시 (Open Library Books API 응답 스키마):**
```json
{
"type": "object",
"required": ["title"],
"properties": {
"title": {"type": "string"},
"publishers": {
"type": "array",
"items": {"type": "string"}
},
"number_of_pages": {"type": "integer"},
"weight": {"type": "string"},
"physical_format": {"type": "string"},
"subjects": {
"type": "array",
"items": {"type": "string"}
},
"isbn_13": {
"type": "array",
"items": {"type": "string"}
},
"isbn_10": {
"type": "array",
"items": {"type": "string"}
},
"publish_date": {"type": "string"},
"physical_dimensions": {"type": "string"}
}
}
```

*   **JSON Schema 예시 (Open Library Books API 응답 스키마 - schema composition 사용):**
```json
var basicBookInfoSchema = {
"type": "object",
"required": ["title"],
"properties": {
"title": {"type": "string"},
... (other properties) ...
}
};

var mandatoryIsbn13 = {
"type": "object",
"required": ["isbn_13"]
};

var mandatoryIsbn10 = {
"type": "object",
"required": ["isbn_10"]
};

var bookInfoSchema = {
"allOf": [
basicBookInfoSchema,
{
"anyOf": [mandatoryIsbn13, mandatoryIsbn10]
}
]
};
```

*   **JSON Schema의 장점:**
*   **언어 독립성:** 다양한 프로그래밍 언어에서 사용할 수 있는 검증 라이브러리가 존재합니다.
*   **표현력:** 클래스로 표현하기 어려운 복잡한 검증 조건을 표현할 수 있습니다.
*   **조합성:** 여러 스키마를 조합하여 복잡한 데이터 구조에 대한 유효성 검증을 수행할 수 있습니다.
*   **JSON Schema의 단점:**
*   **상세한 구문 (Verbose):** JSON Schema의 구문은 클래스 정의보다 다소 장황할 수 있습니다.

**3. 데이터 유효성 검사 (Data Validation)에 대한 추가 정보:**

*   **정의:** 데이터 유효성 검사는 데이터가 미리 정의된 스키마를 준수하는지 확인하는 프로세스입니다.
*   **목적:**
*   시스템에 유효하지 않은 데이터가 유입되는 것을 방지합니다.
*   잘못된 데이터로 인한 오류를 예방합니다.
*   데이터의 무결성을 유지합니다.
*   개발 과정에서 개발자가 데이터를 이해하고 관리하는 데 도움을 줍니다.
*   **검증 라이브러리:**
*   JavaScript: Ajv, Zod, Joi
*   Java: Snow
*   C#: JSON.net Schema
*   Python: jschon
*   Ruby: JSONSchemer
*   **유효성 검사 실패 시 정보:**
*   검증 실패의 원인에 대한 상세 정보를 얻을 수 있습니다 (예: 누락된 필드, 잘못된 데이터 유형).
*   예시 (Ajv 라이브러리):
*   `ajv.errors`: 유효성 검사 오류를 배열로 저장합니다. 각 오류는 `instancePath`, `schemaPath`, `keyword`, `params`, `message` 등의 정보를 포함합니다.
*   `ajv.errorsText(ajv.errors)`: 오류 배열을 사람이 읽기 쉬운 형식으로 변환합니다.
*   `allErrors: true` 옵션을 사용하여 여러 오류를 한 번에 감지할 수 있습니다.

**4. 데이터 유효성 검사의 종류:**

*   **경계에서의 검증 (Boundaries):** 시스템의 외부 경계에서 데이터의 유효성을 검증합니다 (예: 클라이언트 요청, 데이터베이스 응답, 외부 API 응답).
*   **내부에서의 검증 (Inside):** 시스템 내부에서 데이터의 유효성을 검증합니다. 주로 코드의 가독성과 유지보수성을 높이기 위해 사용됩니다. (예: 함수 인자 검증, 데이터 변환 후 유효성 검증)

**5. 데이터 유효성 검사 관련 권장 사항:**

*   **엄격한 검증:** 시스템에서 보내는 데이터는 엄격하게 검증합니다. (보수적인 자세)
*   **유연한 검증:** 시스템이 받는 데이터는 유연하게 검증합니다. (자유로운 자세)
*   **외부 데이터 출처 검증:** 외부 데이터 소스에서 받은 데이터는 항상 유효성을 검증합니다.

**6. 추가적인 내용:**

*   **Chapter 12 (Advanced data validation):** 본 챕터에서는 다루지 않았지만, 고급 데이터 유효성 검사에 대한 내용이 다뤄질 예정입니다 (예: 숫자 범위 검증, 정규 표현식 검증).

구성노드2(7.2 JSON Schema in a nutshell): ## 7.2 JSON Schema in a nutshell - 추가 상세 정보 및 새로운 내용 정리
이 내용은 "7.2 JSON Schema in a nutshell"의 내용을 기반으로 JSON Schema에 대한 이해를 더욱 깊게 하기 위해, 기존 텍스트에서 다루지 않은 추가적인 세부 사항과 새로운 내용을 식별하여 정리합니다.
**1. JSON Schema의 개념:**
*   **데이터 스키마와 데이터 표현의 분리:** JSON Schema는 데이터의 구조(스키마)를 데이터 자체(표현)와 분리하여 정의합니다. 이로 인해 데이터 검증(validation)을 언제든 독립적으로 수행할 수 있습니다. (TIP: DOP에서 데이터 스키마는 데이터 표현과 분리됩니다.)
*   **JSON Schema의 기본 구조:**
*   `type`: 데이터 타입을 정의합니다. (예: "object", "string", "array")
*   `properties`: 객체(object) 내 필드의 스키마를 정의합니다.
*   `items`: 배열(array)의 각 요소의 스키마를 정의합니다.
*   `enum`: 열거형(enumeration) 값을 정의합니다. 특정 값들 중 하나를 허용합니다.
*   `required`: 객체 내 필수 필드를 정의합니다.
**2. JSON Schema의 활용 예시 - Book Search Request 스키마:**
*   **요청 구조:** 검색 요청은 "title" (string)과 "fields" (array of strings) 두 필드로 구성됩니다.
*   **스키마 구성 단계:**
1.  **기본 구조 (object):** `{"type": "object", "properties": {...}}`
2.  **title 필드 (string):** `"title": {"type": "string"}`
3.  **fields 필드 (array of string):**
*   `"fields": {"type": "array", "items": {"type": "string"}}`
*   **열거형(enum)을 사용한 값 제한:** `"fields": {"type": "array", "items": {"enum": ["publishers", "number_of_pages", "weight", "physical_format", "subjects", "publish_date", "physical_dimensions"]}}`
4.  **필수 필드 (required):** `"required": ["title", "fields"]`
*   **완성된 스키마:**
```json
{
"type": "object",
"properties": {
"title": {"type": "string"},
"fields": {
"type": "array",
"items": {
"enum": [
"publishers",
"number_of_pages",
"weight",
"physical_format",
"subjects",
"publish_date",
"physical_dimensions"
]
}
}
},
"required": ["title", "fields"]
}
```
**3. 데이터 검증 (Data Validation):**
*   **검증의 의미:** 스키마에 따라 데이터가 유효한지 확인하는 과정입니다.
*   **검증 라이브러리:** 다양한 프로그래밍 언어에서 JSON Schema 검증 라이브러리를 사용할 수 있습니다.
*   JavaScript: Ajv (https://github.com/ajv-validator/ajv)
*   Java: Snow (https://github.com/ssilverman/snowy-json)
*   C#: JSON.net Schema (https://www.newtonsoft.com/jsonschema)
*   Python: jschon (https://github.com/marksparkza/jschon)
*   Ruby: JSONSchemer (https://github.com/davishmcclurg/json_schemer)
**4. JSON Schema의 장점:**
*   **언어 독립성:** 여러 프로그래밍 언어에서 사용할 수 있는 검증 도구를 제공합니다.
*   **표현력:** 클래스 기반의 데이터 표현보다 더 복잡한 검증 조건을 표현할 수 있습니다. (예: 숫자 범위, 정규 표현식)
**5. 추가적인 궁금증과 해결:**
*   **유효성 검사 실패 시 상세 정보:**  검증 실패의 원인을 자세히 알 수 있는 기능을 제공하는 라이브러리가 있습니다. (예: Ajv는 에러 메시지를 제공합니다.)
*   **복잡한 응답 스키마:** 검색 결과와 같이 여러 필드가 있고, 일부 필드가 선택적인 복잡한 응답의 유효성 검사도 가능합니다.
*   **고급 검증:** 숫자 범위 제한, 정규 표현식과 같은 고급 검증 기능도 JSON Schema에서 제공합니다. (챕터 12에서 다룸)
**6. 추가 정보:**
*   JSON Schema 공식 웹사이트: https://json-schema.org/
*   이 책에서 사용하는 JSON Schema 버전: 2020-12
*   JSON Schema는 데이터 유효성 검사를 위한 강력하고 유연한 도구입니다.
구성노드3(7.3 Schema flexibility and strictness): ## 7.3 Schema flexibility and strictness - 추가 상세 정보 및 새로운 내용 분석
**1. JSON Schema의 유연성 (Composability) 강조:**
*   **세부 내용:** JSON Schema는 단순한 맵(map, 즉, 객체)으로 구성되어 있어, 다른 맵처럼 자유롭게 조합하고 조작할 수 있습니다.
*   **예시:** `bookInfoSchema`와 `searchBooksResponseSchema`를 분리하여 재사용성을 높이는 방법. `bookInfoSchema`를 별도로 정의한 후, `searchBooksResponseSchema`에서 이를 `items` 필드로 사용하여 결합합니다.
*   **구현 방법:** JSON Schema는 문자열, 숫자, 객체, 배열 등과 같은 기본적인 JSON 데이터 타입으로 구성되므로, 변수에 할당하고, 다른 스키마 내에서 참조하며, 필요에 따라 조합하여 사용할 수 있습니다.
**2. 외부 데이터 소스(예: 데이터베이스)에서 데이터 검증의 중요성:**
*   **세부 내용:** 외부 데이터 소스에서 받은 데이터는 반드시 유효성 검사를 수행해야 합니다. 외부 데이터 소스는 예상치 못한 형식이나 구조의 데이터를 제공할 수 있으며, 이는 애플리케이션의 오류나 보안 문제를 야기할 수 있습니다.
*   **예시:** 데이터베이스 쿼리 응답의 예시. 응답은 `title`, `isbn`, `available` 필드를 가지며, `title`과 `isbn`은 문자열, `available`은 부울 값으로 정의됩니다.
*   **구현 방법:** 데이터베이스 응답의 스키마를 정의하고, 받은 데이터가 스키마를 준수하는지 JSON Schema 유효성 검사기를 사용하여 확인합니다.
**3. `additionalProperties` 필드의 역할과 중요성:**
*   **세부 내용:** JSON Schema에서 기본적으로 객체에 정의되지 않은 추가적인 필드를 허용합니다. `additionalProperties` 필드를 `false`로 설정하면, 스키마에 명시된 필드 외의 모든 추가 필드를 허용하지 않도록 합니다.
*   **예시:** `dummy_property`를 가진 데이터가 유효하지 않은 경우를 보여주는 예시. 스키마에 정의되지 않은 `dummy_property` 필드가 추가된 데이터는 `additionalProperties`가 `false`로 설정된 경우 유효성 검사에서 실패합니다.
*   **구현 방법:** 스키마 정의 시 `additionalProperties: false`를 설정합니다.
```json
"additionalProperties": false
```
**4. 요청(Request)과 응답(Response) 스키마 유연성 차이:**
*   **세부 내용:** 일반적으로 요청에 대해서는 보다 유연하게, 응답에 대해서는 더 엄격하게 스키마를 적용하는 것이 좋습니다.
*   **예시:** 서버는 클라이언트가 보낸 요청에 대해 다양한 형태의 데이터를 수용하고, 응답에서는 명확하게 정의된 데이터만을 반환하도록 합니다.
*   **구현 방법:** 요청 스키마는 `additionalProperties`를 `true` (기본값)로 설정하고, 응답 스키마는 `additionalProperties`를 `false`로 설정합니다. 이는 서버가 예상치 못한 요청 필드에 대해 관대하게 대처하고, 클라이언트에게는 정확한 형식의 응답을 제공하여 상호 운용성을 높이는 데 기여합니다.
**5. Jon Postel의 견고성 원칙 (Robustness Principle):**
*   **세부 내용:** "보내는 데이터에 대해 보수적이고, 받는 데이터에 대해 관대하라." (Be conservative in what you send, be liberal in what you accept.)
*   **의미:** 서버는 클라이언트에게 정확하고 엄격한 형식의 데이터를 보내야 하고, 클라이언트의 요청에 대해서는 가능한 한 유연하게 처리해야 합니다.
*   **구현 방법:** 이는 요청과 응답에 대한 스키마 설정에 반영됩니다. 응답 스키마를 엄격하게 정의하고, 요청 스키마는 좀 더 유연하게 허용하여 이 원칙을 따를 수 있습니다.
**6. 추가 팁:**
*   JSON Schema는 필드 정의 시 `required` 배열을 사용하여 필수 필드를 지정합니다.
*   스키마는 코드에서 변수로 정의되고 조작될 수 있습니다.
*   데이터 유효성 검사는 외부 데이터뿐만 아니라 내부 데이터, 사용자 입력 등 다양한 곳에서 적용될 수 있습니다.
요약하자면, 이 챕터는 JSON Schema를 사용하여 데이터의 유효성을 검사하고, 스키마의 유연성을 활용하여 코드의 재사용성과 유지보수성을 높이는 방법을 보여줍니다. 특히, 요청과 응답에 대한 스키마의 유연성 차이를 강조하며, 외부 데이터 소스에서 데이터를 검증하는 중요성을 강조합니다.
구성노드4(7.4 Schema composition): ## 7.4 Schema composition 상세 분석 및 추가 정보
다음은 "7.4 Schema composition"의 내용을 분석하여, 기존 내용에서 다루지 않은 추가적인 상세 정보와 새로운 내용들을 식별하여 정리한 내용입니다.
**1. 외부 API 응답 데이터 검증의 필요성:**
*   **상세 정보:** 외부 웹 서비스(예: Open Library Books API)에서 제공하는 데이터의 유효성을 검증해야 하는 필요성을 제기합니다.  이는 외부 서비스의 데이터 구조가 변경될 경우, 애플리케이션의 동작에 오류가 발생할 수 있기 때문입니다.
*   **추가 정보:** 외부 서비스의 데이터 구조는 통제할 수 없으므로, 스키마를 사용하여 응답 데이터를 검증하는 것은 데이터 무결성을 보장하고 잠재적인 오류를 방지하는 데 필수적입니다.
**2. `isbn_10` 및 `isbn_13` 필드의 문제점과 해결 방법:**
*   **상세 정보:**  `isbn_10`과 `isbn_13` 필드가 모두 필수적인 것은 아니며, 책의 출판 연도에 따라 하나 또는 둘 다 존재할 수 있다는 점을 지적합니다.
*   **추가 정보:**  이러한 유연성을 표현하기 위해 JSON Schema의 "Schema composition" 기능을 사용합니다.  즉, `isbn_10` 또는 `isbn_13` 중 하나 이상이 존재해야 하는 조건을 스키마로 표현합니다.
**3. JSON Schema Composition:**
*   **상세 정보:**  JSON Schema composition은 여러 스키마를 조합하여 더 복잡한 데이터 유효성 검사 규칙을 정의하는 방법입니다.
*   **추가 정보:**
*   `allOf`:  AND 연산과 유사하며, 데이터가 모든 하위 스키마를 만족해야 합니다.
*   `anyOf`:  OR 연산과 유사하며, 데이터가 적어도 하나의 하위 스키마를 만족해야 합니다.
*   `oneOf`:  데이터가 정확히 하나의 하위 스키마를 만족해야 합니다. (본문에서는 언급만 됨)
*   **구체적인 구현:**  Open Library Books API 응답에 대한 예시를 통해 `allOf`와 `anyOf`를 사용한 스키마 조합을 보여줍니다.  이는 기본 정보 스키마(`basicBookInfoSchema`)와 `isbn_10` 또는 `isbn_13`을 포함하는 스키마를 결합하는 방식으로 구현됩니다.
**4. 코드 예시 (Listing 7.18 및 7.19) 상세 분석:**
*   **Listing 7.18:**
*   `basicBookInfoSchema`: `title` 필드가 필수이며, 다른 필드들의 타입(type)을 정의합니다.
*   `mandatoryIsbn13`:  `isbn_13` 필드가 필수임을 정의합니다.
*   `mandatoryIsbn10`: `isbn_10` 필드가 필수임을 정의합니다.
*   `bookInfoSchema`:  `basicBookInfoSchema`와 `anyOf`를 사용하여 `mandatoryIsbn13` 또는 `mandatoryIsbn10`을 결합합니다.  즉, `title`은 필수이고, `isbn_10` 또는 `isbn_13` 중 하나 이상이 존재해야 합니다.
*   **Listing 7.19:**  `bookInfoSchema`를 사용하여 "Watchmen" 책의 데이터를 검증하는 예시를 보여줍니다.  데이터가 유효하므로 검증 결과는 `true`입니다.
**5. JSON Schema Composition의 장점:**
*   **상세 정보:**  JSON Schema composition은 클래스를 사용하여 데이터를 표현하는 것보다 더 강력한 데이터 유효성 검사 규칙을 표현할 수 있게 해줍니다.
*   **추가 정보:**  데이터 모델의 유연성을 높이고, 다양한 데이터 구조에 대한 유효성 검사를 효율적으로 수행할 수 있습니다.  또한, 데이터의 특정 부분에 대한 규칙을 재사용할 수 있습니다.
**6. 검증 실패 시 문제점:**
*   **상세 정보:** 데이터가 유효하지 않을 경우, 어떤 이유로 실패했는지 명확하게 알 수 없다는 점을 지적합니다.
*   **추가 정보:**  이는 디버깅 및 오류 처리에 어려움을 초래할 수 있습니다. (이 문제는 12장에서 다루어질 예정임을 언급합니다.)
**7. 추가 학습 팁:**
*   12장에서 더 발전된 데이터 유효성 검사 기술을 다룬다는 점을 언급하며, 학습 범위를 확장할 것을 권장합니다.
구성노드5(7.5 Details about data validation failures): ## 7.5 Details about data validation failures - 추가 상세 정보 및 새로운 내용 정리
다음은 "7.5 Details about data validation failures" 내용을 분석하여 기존 핵심 내용에서 다루지 않은 추가적인 세부 사항, 예시, 구체적인 구현 방법 등을 정리한 내용입니다.
**1. 데이터 유효성 검사 실패 시 상세 정보 제공:**
*   **개념:** 데이터가 유효성 검사에 실패했을 때, 단순히 "유효하지 않음"만 알려주는 것이 아니라, **실패 이유에 대한 구체적인 정보**를 제공합니다.
*   **구체적인 정보 예시:**
*   누락된 필수 필드의 이름
*   예상된 타입과 다른 데이터 타입
*   **의미:** 개발자가 데이터 유효성 검사 실패의 원인을 쉽게 파악하고 문제를 해결할 수 있도록 돕습니다.
**2. 데이터 유효성 검사 실패 정보 접근 방법 (Ajv 라이브러리 기준):**
*   **실패 정보 저장 위치:** Ajv 라이브러리에서는 마지막 유효성 검사에서 발생한 에러 정보를 `validator.errors` 배열에 저장합니다.
*   **배열 형태의 이유:** 여러 개의 유효성 검사 실패가 동시에 발생할 수 있기 때문입니다.
*   **개별 에러 정보의 구조:**
*   `instancePath`: 에러가 발생한 데이터 내의 위치 (예: ""는 최상위 레벨, "/fields/0"은 "fields" 배열의 첫 번째 요소).
*   `schemaPath`: 에러와 관련된 스키마 내의 위치.
*   `keyword`: 발생한 에러의 종류 (예: "required", "type").
*   `params`: 에러에 대한 추가 정보 (예: 누락된 속성의 이름).
*   `message`: 에러에 대한 설명.
**3. 에러 메시지 가독성 개선:**
*   **문제점:** `validator.errors` 배열에 저장된 에러 정보는 개발자가 이해하기 어려울 수 있습니다.
*   **해결 방법:** Ajv는 `errorsText()` 유틸리티 함수를 제공하여 `validator.errors` 배열을 **사람이 읽기 쉬운 형식**으로 변환합니다.
*   **예시:** `ajv.errorsText(ajv.errors);`
**4. 여러 개의 유효성 검사 실패 감지:**
*   **기본 동작:** Ajv는 기본적으로 첫 번째 유효성 검사 실패만 감지합니다.
*   **이유 (추정):** 성능상의 이유로, 첫 번째 에러 발생 시 검사를 중단합니다.
*   **여러 에러 감지 설정:** `Ajv` 생성자에 `allErrors: true` 옵션을 전달합니다.
*   `var ajv = new Ajv({allErrors: true});`
*   **결과:** 여러 개의 유효성 검사 실패가 발생한 경우, 모든 에러 정보를 `validator.errors` 배열에 저장합니다.
**5. 예제 코드 및 상세 분석:**
*   **Listing 7.20 (Ajv에서 유효성 검사 실패 정보 접근 예시):**
*   `var searchBooksRequestSchema = { ... }`: 검색 요청 스키마 정의 (제목(title)과 필드(fields) 필수).
*   `var invalidSearchBooksRequest = { ... }`: 유효하지 않은 검색 요청 데이터 (제목 필드 이름 오류).
*   `var ajv = new Ajv();`: Ajv 인스턴스 생성.
*   `ajv.validate(searchBooksRequestSchema, invalidSearchBooksRequest);`: 유효성 검사 실행.
*   `ajv.errors`: 유효성 검사 실패 정보 (배열) 출력.
*   **Listing 7.21 (단일 실패 정보):** `validator.errors` 배열에 저장된 에러 정보의 예시 (누락된 필수 필드 "title").
*   **Listing 7.22 (에러 메시지 가독성 개선):** `ajv.errorsText(ajv.errors)`를 사용하여 가독성 있는 에러 메시지 출력.
*   **Listing 7.23 (여러 실패 감지):** `allErrors: true` 옵션을 사용하여 여러 개의 실패를 감지하고, 가독성 있는 에러 메시지 출력. (제목 필드 이름 오류 및 필드 배열 요소 타입 오류).
*   **Listing 7.24 (JSON Schema cheat sheet):** JSON Schema의 기본적인 구조와 문법을 간략하게 요약한 치트 시트 예시. (배열, 객체, 타입, 필수 필드, enum, 추가 속성 금지 등)

**6. 새로운 내용:**
*   **JSON Schema Cheat Sheet:** 스키마 정의의 핵심 내용을 한눈에 볼 수 있도록 정리한 자료 (예: `type`, `properties`, `required`, `enum`, `additionalProperties`).  이 자료는 JSON Schema를 처음 접하는 사용자들이 기본적인 구조를 파악하고 빠르게 학습할 수 있도록 돕습니다.

구성노드2: ## 7.2 JSON Schema in a nutshell - 추가 상세 정보 및 새로운 내용 정리

이 내용은 "7.2 JSON Schema in a nutshell"의 내용을 기반으로 JSON Schema에 대한 이해를 더욱 깊게 하기 위해, 기존 텍스트에서 다루지 않은 추가적인 세부 사항과 새로운 내용을 식별하여 정리합니다. 부모 노드에서 언급된 "7 Basic data validation" 및 7.1의 내용과 연계하여, DOP에서의 데이터 유효성 검증을 위한 JSON Schema의 활용법을 구체적으로 설명합니다.

**1. JSON Schema의 개념: DOP와 연결**
*   **데이터 스키마와 데이터 표현의 분리: DOP 원칙 #4의 구현:** JSON Schema는 데이터의 구조(스키마)를 데이터 자체(표현)와 분리하여 정의합니다. 이로 인해 데이터 검증(validation)을 언제든 독립적으로 수행할 수 있습니다. (TIP: DOP에서 데이터 스키마는 데이터 표현과 분리됩니다.)  이는 DOP 원칙 #4를 실현하는 핵심적인 방법론입니다. 이 분리를 통해 데이터의 형식과 구조를 명확하게 정의하고, 시스템 경계에서의 데이터 유효성 검증을 용이하게 할 수 있습니다.
*   **JSON Schema의 기본 구조:**
    *   `type`: 데이터 타입을 정의합니다. (예: "object", "string", "array"). 부모 노드에서 언급된 내용과 일치하며, 데이터 타입 정의를 통해 데이터의 형식을 엄격하게 관리할 수 있습니다.
    *   `properties`: 객체(object) 내 필드의 스키마를 정의합니다. 부모 노드에서 언급된 내용과 일치하며, 객체 내 각 필드의 데이터 타입과 유효성 규칙을 정의하여 데이터의 무결성을 보장합니다.
    *   `items`: 배열(array)의 각 요소의 스키마를 정의합니다. 부모 노드에서 언급된 내용과 일치하며, 배열 내 요소들의 데이터 타입과 유효성 규칙을 정의합니다.
    *   `enum`: 열거형(enumeration) 값을 정의합니다. 특정 값들 중 하나를 허용합니다. 부모 노드에서 언급된 내용과 일치하며, 허용된 값의 범위를 제한하여 데이터의 정확성을 높입니다.
    *   `required`: 객체 내 필수 필드를 정의합니다. 부모 노드에서 언급된 내용과 일치하며, 필수 필드를 지정하여 데이터의 완전성을 보장합니다.

**2. JSON Schema의 활용 예시 - Book Search Request 스키마: 시스템 경계에서의 검증**
*   **요청 구조:** 검색 요청은 "title" (string)과 "fields" (array of strings) 두 필드로 구성됩니다.  이 예시는 시스템 경계, 즉 클라이언트로부터의 요청을 검증하는 시나리오를 보여줍니다. 부모 노드에서 강조된 시스템 경계에서의 데이터 유효성 검증의 중요성을 실질적으로 보여주는 예시입니다.
*   **스키마 구성 단계:**
    1.  **기본 구조 (object):** `{"type": "object", "properties": {...}}`
    2.  **title 필드 (string):** `"title": {"type": "string"}`
    3.  **fields 필드 (array of string):**
    *   `"fields": {"type": "array", "items": {"type": "string"}}`
    *   **열거형(enum)을 사용한 값 제한:** `"fields": {"type": "array", "items": {"enum": ["publishers", "number_of_pages", "weight", "physical_format", "subjects", "publish_date", "physical_dimensions"]}}`
    4.  **필수 필드 (required):** `"required": ["title", "fields"]`
*   **완성된 스키마:**
```json
{
"type": "object",
"properties": {
"title": {"type": "string"},
"fields": {
"type": "array",
"items": {
"enum": [
"publishers",
"number_of_pages",
"weight",
"physical_format",
"subjects",
"publish_date",
"physical_dimensions"
]
}
}
},
"required": ["title", "fields"]
}
```

**3. 데이터 검증 (Data Validation) 및 라이브러리: 다양한 언어 지원**
*   **검증의 의미:** 스키마에 따라 데이터가 유효한지 확인하는 과정입니다. 부모 노드에서 설명된 데이터 유효성 검사의 정의와 일치하며, JSON Schema를 활용한 검증의 핵심입니다.
*   **검증 라이브러리:** 다양한 프로그래밍 언어에서 JSON Schema 검증 라이브러리를 사용할 수 있습니다.  부모 노드에서 제시된 다양한 언어의 라이브러리 목록을 포함하여, 개발 환경에 맞는 도구를 선택할 수 있도록 돕습니다.
    *   JavaScript: Ajv (https://github.com/ajv-validator/ajv)
    *   Java: Snow (https://github.com/ssilverman/snowy-json)
    *   C#: JSON.net Schema (https://www.newtonsoft.com/jsonschema)
    *   Python: jschon (https://github.com/marksparkza/jschon)
    *   Ruby: JSONSchemer (https://github.com/davishmcclurg/json_schemer)

**4. JSON Schema의 장점: DOP와 연결**
*   **언어 독립성:** 여러 프로그래밍 언어에서 사용할 수 있는 검증 도구를 제공합니다. 이는 DOP의 유연성을 지원하며, 다양한 기술 스택에서 동일한 데이터 유효성 검증 규칙을 적용할 수 있게 합니다.
*   **표현력:** 클래스 기반의 데이터 표현보다 더 복잡한 검증 조건을 표현할 수 있습니다. (예: 숫자 범위, 정규 표현식). 이는 DOP에서 데이터 구조의 복잡성을 효과적으로 처리하고, 시스템 경계에서의 데이터 유효성 검증을 정교하게 수행할 수 있도록 돕습니다.

**5. 추가적인 궁금증과 해결: 유효성 검사 실패와 JSON Schema**
*   **유효성 검사 실패 시 상세 정보:** 검증 실패의 원인을 자세히 알 수 있는 기능을 제공하는 라이브러리가 있습니다. (예: Ajv는 에러 메시지를 제공합니다.). 부모 노드에서 설명된 유효성 검사 실패 시의 상세 정보 제공의 중요성을 강조하며, Ajv와 같은 라이브러리가 제공하는 기능을 통해 실패 원인을 효과적으로 파악할 수 있습니다.
*   **복잡한 응답 스키마:** 검색 결과와 같이 여러 필드가 있고, 일부 필드가 선택적인 복잡한 응답의 유효성 검사도 가능합니다. 이는 JSON Schema의 유연성을 활용하여 다양한 데이터 구조에 대한 검증을 수행할 수 있음을 보여줍니다.
*   **고급 검증:** 숫자 범위 제한, 정규 표현식과 같은 고급 검증 기능도 JSON Schema에서 제공합니다. (챕터 12에서 다룸). 부모 노드에서 언급된 고급 검증 기술에 대한 추가 정보를 제공하며, 12장에서 더 자세한 내용을 다룰 것을 예고합니다.

구성노드3: ## 7.3 Schema flexibility and strictness - 추가 상세 정보 및 새로운 내용 분석

본 챕터는 JSON Schema의 유연성과 엄격성을 다룹니다. 이는 DOP 원칙 #4와 연계하여, 스키마를 유연하게 구성하고, 데이터 유효성 검사를 효율적으로 수행하는 방법을 제시합니다. 부모 노드에서 언급된 데이터 유효성 검사, 시스템 경계, 요청/응답의 차이점을 구체적인 예시와 함께 설명합니다.

**1. JSON Schema의 유연성 (Composability) 강조:** 재사용성과 유지보수성을 위한 설계
*   **세부 내용:** JSON Schema는 단순한 맵(map, 즉, 객체)으로 구성되어 있어, 다른 맵처럼 자유롭게 조합하고 조작할 수 있습니다.  이는 JSON Schema의 핵심 장점 중 하나이며, DOP 원칙 #4에 따라 데이터 스키마와 데이터 표현을 분리하는 것과 밀접하게 연결됩니다.
*   **예시:** `bookInfoSchema`와 `searchBooksResponseSchema`를 분리하여 재사용성을 높이는 방법. `bookInfoSchema`를 별도로 정의한 후, `searchBooksResponseSchema`에서 이를 `items` 필드로 사용하여 결합합니다.  이는 코드의 중복을 줄이고, 스키마의 유지보수성을 향상시키는 효과적인 방법입니다.
*   **구현 방법:** JSON Schema는 문자열, 숫자, 객체, 배열 등과 같은 기본적인 JSON 데이터 타입으로 구성되므로, 변수에 할당하고, 다른 스키마 내에서 참조하며, 필요에 따라 조합하여 사용할 수 있습니다. 이는 JSON Schema가 제공하는 composability의 핵심적인 특징입니다.

**2. 외부 데이터 소스(예: 데이터베이스)에서 데이터 검증의 중요성: 시스템 경계에서의 검증**
*   **세부 내용:** 외부 데이터 소스에서 받은 데이터는 반드시 유효성 검사를 수행해야 합니다. 외부 데이터 소스는 예상치 못한 형식이나 구조의 데이터를 제공할 수 있으며, 이는 애플리케이션의 오류나 보안 문제를 야기할 수 있습니다.  이는 부모 노드와 7.1 챕터에서 강조된 시스템 경계에서의 데이터 유효성 검증의 중요성과 직결됩니다.
*   **예시:** 데이터베이스 쿼리 응답의 예시. 응답은 `title`, `isbn`, `available` 필드를 가지며, `title`과 `isbn`은 문자열, `available`은 부울 값으로 정의됩니다.  이 예시는 데이터베이스 응답이라는 외부 데이터 소스의 데이터를 검증하는 실제 시나리오를 보여줍니다.
*   **구현 방법:** 데이터베이스 응답의 스키마를 정의하고, 받은 데이터가 스키마를 준수하는지 JSON Schema 유효성 검사기를 사용하여 확인합니다. 이는 데이터의 무결성을 보장하고, 예상치 못한 오류를 방지하는 데 필수적입니다.

**3. `additionalProperties` 필드의 역할과 중요성: 엄격성과 유연성 조절**
*   **세부 내용:** JSON Schema에서 기본적으로 객체에 정의되지 않은 추가적인 필드를 허용합니다. `additionalProperties` 필드를 `false`로 설정하면, 스키마에 명시된 필드 외의 모든 추가 필드를 허용하지 않도록 합니다. 부모 노드에서 언급된 "엄격한 검증"과 연결됩니다.
*   **예시:** `dummy_property`를 가진 데이터가 유효하지 않은 경우를 보여주는 예시. 스키마에 정의되지 않은 `dummy_property` 필드가 추가된 데이터는 `additionalProperties`가 `false`로 설정된 경우 유효성 검사에서 실패합니다.  이는 스키마를 엄격하게 적용하여, 정의되지 않은 필드가 데이터에 포함되는 것을 방지합니다.
*   **구현 방법:** 스키마 정의 시 `additionalProperties: false`를 설정합니다.
```json
"additionalProperties": false
```

**4. 요청(Request)과 응답(Response) 스키마 유연성 차이: Jon Postel의 견고성 원칙 적용**
*   **세부 내용:** 일반적으로 요청에 대해서는 보다 유연하게, 응답에 대해서는 더 엄격하게 스키마를 적용하는 것이 좋습니다.  이는 부모 노드에서 언급된 "엄격한 검증"과 "유연한 검증" 원칙을 실제 적용하는 방법입니다.
*   **예시:** 서버는 클라이언트가 보낸 요청에 대해 다양한 형태의 데이터를 수용하고, 응답에서는 명확하게 정의된 데이터만을 반환하도록 합니다. 이는 서버의 상호 운용성을 높이고, 클라이언트의 에러 처리 부담을 줄여줍니다.
*   **구현 방법:** 요청 스키마는 `additionalProperties`를 `true` (기본값)로 설정하고, 응답 스키마는 `additionalProperties`를 `false`로 설정합니다. 이는 서버가 예상치 못한 요청 필드에 대해 관대하게 대처하고, 클라이언트에게는 정확한 형식의 응답을 제공하여 상호 운용성을 높이는 데 기여합니다.

**5. Jon Postel의 견고성 원칙 (Robustness Principle): 송수신 데이터에 대한 균형**
*   **세부 내용:** "보내는 데이터에 대해 보수적이고, 받는 데이터에 대해 관대하라." (Be conservative in what you send, be liberal in what you accept.)  이는 부모 노드에서 설명된 "엄격한 검증"과 "유연한 검증"의 근본적인 철학을 나타냅니다.
*   **의미:** 서버는 클라이언트에게 정확하고 엄격한 형식의 데이터를 보내야 하고, 클라이언트의 요청에 대해서는 가능한 한 유연하게 처리해야 합니다.
*   **구현 방법:** 이는 요청과 응답에 대한 스키마 설정에 반영됩니다. 응답 스키마를 엄격하게 정의하고, 요청 스키마는 좀 더 유연하게 허용하여 이 원칙을 따를 수 있습니다.

**6. 추가 팁:** JSON Schema의 활용
*   JSON Schema는 필드 정의 시 `required` 배열을 사용하여 필수 필드를 지정합니다.  필수 필드 지정은 데이터의 완전성을 보장하는 핵심적인 방법입니다.
*   스키마는 코드에서 변수로 정의되고 조작될 수 있습니다. 이는 스키마의 재사용성과 유지보수성을 높이는 데 기여합니다.
*   데이터 유효성 검사는 외부 데이터뿐만 아니라 내부 데이터, 사용자 입력 등 다양한 곳에서 적용될 수 있습니다. 이는 시스템 전체의 데이터 무결성을 확보하는 데 중요합니다.

구성노드4: ## 7.4 Schema composition 상세 분석 및 추가 정보

본 챕터는 JSON Schema composition (스키마 조합)에 대해 자세히 설명하며, 외부 API 응답과 같은 복잡한 데이터 구조를 검증하는 방법을 제시합니다. 부모 노드에서 설명된 데이터 유효성 검사, JSON Schema의 유연성, 시스템 경계에서의 검증, 그리고 7.3 챕터의 내용과 연계하여, 실제 시나리오에서의 스키마 조합 활용법을 구체적으로 설명합니다.

**1. 외부 API 응답 데이터 검증의 필요성: 시스템 경계에서의 검증 강화**
*   **상세 정보:** 외부 웹 서비스(예: Open Library Books API)에서 제공하는 데이터의 유효성을 검증해야 하는 필요성을 제기합니다. 이는 부모 노드와 이전 챕터에서 강조된 시스템 경계에서의 데이터 유효성 검증의 중요성을 다시 한번 강조하며, 외부 데이터 소스의 신뢰성을 확보하는 방법을 제시합니다.
*   **추가 정보:** 외부 서비스의 데이터 구조는 통제할 수 없으므로, 스키마를 사용하여 응답 데이터를 검증하는 것은 데이터 무결성을 보장하고 잠재적인 오류를 방지하는 데 필수적입니다. 외부 API 응답 검증은 시스템의 안정성을 높이고, 예기치 않은 오류를 방지하는 데 기여합니다.

**2. `isbn_10` 및 `isbn_13` 필드의 문제점과 해결 방법: 유연한 스키마 설계**
*   **상세 정보:** `isbn_10`과 `isbn_13` 필드가 모두 필수적인 것은 아니며, 책의 출판 연도에 따라 하나 또는 둘 다 존재할 수 있다는 점을 지적합니다.  이러한 유연성은 데이터 구조의 변화를 수용하고, 데이터 모델의 확장성을 높이는 데 중요합니다.
*   **추가 정보:** 이러한 유연성을 표현하기 위해 JSON Schema의 "Schema composition" 기능을 사용합니다. 즉, `isbn_10` 또는 `isbn_13` 중 하나 이상이 존재해야 하는 조건을 스키마로 표현합니다.  이는 데이터 모델의 변화에 유연하게 대응하고, 다양한 데이터 구조를 처리할 수 있도록 돕습니다.

**3. JSON Schema Composition: 강력한 유효성 검사 규칙 정의**
*   **상세 정보:** JSON Schema composition은 여러 스키마를 조합하여 더 복잡한 데이터 유효성 검사 규칙을 정의하는 방법입니다.  이는 부모 노드에서 설명된 JSON Schema의 유연성을 극대화하는 방법이며, 데이터의 복잡성을 효과적으로 처리할 수 있도록 돕습니다.
*   **추가 정보:**
    *   `allOf`:  AND 연산과 유사하며, 데이터가 모든 하위 스키마를 만족해야 합니다.
    *   `anyOf`:  OR 연산과 유사하며, 데이터가 적어도 하나의 하위 스키마를 만족해야 합니다.
    *   `oneOf`:  데이터가 정확히 하나의 하위 스키마를 만족해야 합니다. (본문에서는 언급만 됨).  이는 데이터의 특정 필드 간의 상호 의존성을 표현하는 데 유용합니다.
*   **구체적인 구현:**  Open Library Books API 응답에 대한 예시를 통해 `allOf`와 `anyOf`를 사용한 스키마 조합을 보여줍니다.  이는 기본 정보 스키마(`basicBookInfoSchema`)와 `isbn_10` 또는 `isbn_13`을 포함하는 스키마를 결합하는 방식으로 구현됩니다. 이 예시는 실제 API 응답을 검증하는 시나리오를 통해, 스키마 조합의 실용성을 보여줍니다.

구성노드5: ## 7.5 Details about data validation failures - 추가 상세 정보 및 새로운 내용 정리

본 챕터는 데이터 유효성 검사 실패 시 발생하는 문제점과 그 해결책을 제시합니다. 부모 노드에서 설명된 데이터 유효성 검사, JSON Schema의 활용, 그리고 7.2, 7.3, 7.4 챕터의 내용과 연계하여, 구체적인 에러 정보 접근 방법과 가독성 개선 방법을 제시합니다.

**1. 데이터 유효성 검사 실패 시 상세 정보 제공: 문제 해결을 위한 핵심**
*   **개념:** 데이터가 유효성 검사에 실패했을 때, 단순히 "유효하지 않음"만 알려주는 것이 아니라, **실패 이유에 대한 구체적인 정보**를 제공합니다. 이는 부모 노드와 이전 챕터에서 강조된 데이터 유효성 검사의 핵심적인 측면입니다.
*   **구체적인 정보 예시:**
    *   누락된 필수 필드의 이름
    *   예상된 타입과 다른 데이터 타입
*   **의미:** 개발자가 데이터 유효성 검사 실패의 원인을 쉽게 파악하고 문제를 해결할 수 있도록 돕습니다.  이는 개발 생산성을 향상시키고, 오류를 빠르게 수정하는 데 기여합니다.

**2. 데이터 유효성 검사 실패 정보 접근 방법 (Ajv 라이브러리 기준): Ajv의 활용**
*   **실패 정보 저장 위치:** Ajv 라이브러리에서는 마지막 유효성 검사에서 발생한 에러 정보를 `validator.errors` 배열에 저장합니다.
*   **배열 형태의 이유:** 여러 개의 유효성 검사 실패가 동시에 발생할 수 있기 때문입니다.
*   **개별 에러 정보의 구조:**
    *   `instancePath`: 에러가 발생한 데이터 내의 위치 (예: ""는 최상위 레벨, "/fields/0"은 "fields" 배열의 첫 번째 요소).
    *   `schemaPath`: 에러와 관련된 스키마 내의 위치.
    *   `keyword`: 발생한 에러의 종류 (예: "required", "type").
    *   `params`: 에러에 대한 추가 정보 (예: 누락된 속성의 이름).
    *   `message`: 에러에 대한 설명.

**3. 에러 메시지 가독성 개선: Ajv의 유틸리티 함수**
*   **문제점:** `validator.errors` 배열에 저장된 에러 정보는 개발자가 이해하기 어려울 수 있습니다.  부모 노드와 7.4 챕터에서 언급된 검증 실패 시 문제점의 해결책을 제시합니다.
*   **해결 방법:** Ajv는 `errorsText()` 유틸리티 함수를 제공하여 `validator.errors` 배열을 **사람이 읽기 쉬운 형식**으로 변환합니다.
*   **예시:** `ajv.errorsText(ajv.errors);`  이 함수는 개발자가 에러를 쉽게 파악하고, 문제를 해결할 수 있도록 돕습니다.

**4. 여러 개의 유효성 검사 실패 감지: 성능과 정확성의 균형**
*   **기본 동작:** Ajv는 기본적으로 첫 번째 유효성 검사 실패만 감지합니다.
*   **이유 (추정):** 성능상의 이유로, 첫 번째 에러 발생 시 검사를 중단합니다.  성능 최적화와 관련된 중요한 측면을 설명합니다.
*   **여러 에러 감지 설정:** `Ajv` 생성자에 `allErrors: true` 옵션을 전달합니다.
*   `var ajv = new Ajv({allErrors: true});`
*   **결과:** 여러 개의 유효성 검사 실패가 발생한 경우, 모든 에러 정보를 `validator.errors` 배열에 저장합니다.  이는 개발자가 모든 에러를 한 번에 파악하고, 문제를 효율적으로 해결할 수 있도록 돕습니다.
