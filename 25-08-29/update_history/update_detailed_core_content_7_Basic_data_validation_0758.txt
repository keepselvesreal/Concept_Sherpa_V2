### 7 Basic Data Validation: 개요

*   **목표:** 데이터 중심 프로그래밍(DOP) 원칙을 따르면서 데이터 유효성 검사를 수행하는 방법 학습
*   **DOP 원칙 #4:** 데이터 스키마와 데이터 표현을 분리
*   **개념:** 시스템 경계에서 데이터 유효성 검사의 중요성, JSON Schema 언어 사용, 코드 베이스 통합, 실패 정보 획득

### 7.1 DOP에서의 데이터 유효성 검사

*   **문제 제기:** DOP에서 데이터 유효성 검사의 필요성 (객체 지향 프로그래밍(OOP)과의 차이점)
*   **해결책:** DOP에서도 데이터 유효성 검사 가능. 데이터 스키마와 데이터 표현 분리
*   **중요성:** 시스템 경계에서의 데이터 유효성 검사 (클라이언트, 데이터베이스, 웹 서비스)
*   **두 가지 종류의 데이터 유효성 검사:**
*   **경계:** 안전을 위한 검사 (생산 환경)
*   **내부:** 개발 편의성을 위한 검사 (개발 환경)
*   **핵심:** 시스템 경계에서 데이터 유효성 검사가 가장 중요

### 7.2 JSON Schema 개요

*   **JSON Schema 소개:** 데이터 스키마를 표현하는 언어 (JSON 기반)
*   **핵심 원리:** 데이터 스키마는 데이터 표현과 독립적
*   **JSON Schema 기본 구조:** "type" 및 "properties" 필드 포함
*   `type`: 데이터 유형 지정 (예: "object", "string", "array")
*   `properties`: 객체 내 각 필드의 스키마 정의
*   **JSON Schema의 다양한 기능:**
*   `type`: 데이터 타입 지정 (string, array 등)
*   `items`: 배열 요소의 스키마 정의
*   `enum`: 허용된 값 목록 지정 (열거형)
*   `required`: 필수 필드 지정

### 7.3 스키마 유연성 및 엄격성

*   **JSON Schema의 유연성:**
*   맵(Map)의 필드는 기본적으로 선택 사항
*   필수 필드는 `required` 배열에 지정
*   스키마는 다른 맵처럼 자유롭게 구성 및 조작 가능
*   **`additionalProperties` 필드:**
*   스키마에 명시되지 않은 추가 필드 허용 여부 (기본값: 허용)
*   `additionalProperties: false`: 추가 필드 금지
*   **엄격성 vs. 유연성:**
*   보내는 데이터는 엄격하게, 받는 데이터는 유연하게 (클라이언트 요청 vs. 서버 응답)

### 7.4 스키마 구성

*   **개념:** JSON Schema를 마치 AND, OR, NOT 연산처럼 결합하는 방법
*   **핵심 키워드:**
*   `allOf`: 모든 스키마를 만족해야 함 (AND)
*   `anyOf`: 스키마 중 하나 이상을 만족해야 함 (OR)
*   `oneOf`: 스키마 중 정확히 하나를 만족해야 함
*   **활용 예시:** API 응답에서 필수 ISBN 필드 (isbn_10 또는 isbn_13)

### 7.5 데이터 유효성 검사 실패에 대한 세부 정보

*   **개념:** 유효성 검사 실패 시 실패 이유에 대한 상세 정보 획득
*   **JSON Schema 검증 라이브러리:** 각 라이브러리마다 오류 정보를 노출하는 방식이 다름
*   **Ajv (JavaScript):**
*   오류는 배열 형식으로 저장 (여러 오류 가능)
*   `errorsText()` 유틸리티 함수를 사용하여 읽기 쉬운 형식으로 변환
*   `allErrors: true` 옵션을 사용하여 여러 오류 캡처

구성노드1(7.1 Data validation in DOP): ## 7.1 Data Validation in DOP: 상세 분석
### 도입부: DOP에서의 데이터 검증의 중요성
*   **문제 제기:** OOP(객체 지향 프로그래밍)에서 데이터 검증이 보장되는 것과 달리, DOP(데이터 지향 프로그래밍)에서는 필드 이름 및 타입의 작은 실수로 인해 데이터 일관성 문제가 발생할 수 있다는 점이 제기됩니다.
*   **해결책 제시:** DOP에서도 데이터 검증이 가능하며, 시스템 경계에서 데이터를 검증하는 것이 중요합니다.
### DOP에서의 데이터 검증 원리
*   **DOP의 특징:** DOP는 데이터 스키마와 데이터 표현이 분리되어 있습니다. 이는 데이터 검증을 수행하는 데 있어서 중요한 기반이 됩니다.
*   **데이터 검증의 초점:** DOP에서 가장 중요한 데이터 검증은 시스템 경계를 넘나드는 데이터에 집중합니다.
### 시스템 경계의 정의 및 예시
*   **시스템 경계:** 시스템이 데이터를 교환하는 영역을 의미합니다.
*   **예시 (웹 서버):**
*   클라이언트 경계 (웹 브라우저 등)
*   데이터베이스 경계
*   웹 서비스 경계
### 데이터 검증의 종류 및 중요성
*   **두 가지 종류의 데이터 검증:**
*   **경계에서의 검증:** 시스템의 입출력 데이터를 검증합니다. (Guardian, Production 환경)
*   **내부에서의 검증:** 코드 개발의 용이성을 위해 내부 데이터를 검증합니다. (Dev 환경)
*   **경계에서의 검증의 중요성:** 시스템의 경계에서 데이터가 유효한지 확인하면, 시스템 내부에서 예상치 못한 데이터가 발생할 확률을 줄일 수 있습니다.
*   **내부 검증의 목적:** 코드베이스가 커짐에 따라 개발 편의성을 높입니다.
### 데이터 검증의 목적
*   **경계에서의 검증 목적:**
*   유효하지 않은 데이터의 시스템 유입 및 유출 방지.
*   유효하지 않은 데이터를 발견했을 때, 유용한 오류 메시지 제공.
### 데이터 검증 요약 표 (Table 7.1)
| 종류                     | 목적                                     | 환경   |
| :----------------------- | :---------------------------------------- | :----- |
| 경계에서의 데이터 검증 | 시스템 입출력 데이터의 유효성 검증          | Production |
| 내부에서의 데이터 검증  | 개발 편의성                                 | Dev      |
구성노드2(7.2 JSON Schema in a nutshell): ### JSON Schema in a nutshell - 개요
"JSON Schema in a nutshell"은 데이터 유효성 검사를 위한 JSON Schema 언어에 대한 간략한 소개를 제공합니다. 이 챕터에서는 JSON Schema를 사용하여 데이터의 구조와 유효성을 정의하고, 데이터를 검증하는 방법을 설명합니다.
### 데이터 유효성 검사 및 JSON Schema의 중요성
*   **데이터 표현과 스키마의 분리:** 데이터 표현(실제 데이터)과 데이터 스키마(데이터 구조 정의)를 분리하는 것이 중요합니다. 이를 통해 데이터의 유효성을 독립적으로 검증할 수 있습니다.
*   **JSON Schema의 역할:** JSON Schema는 JSON 형식의 데이터에 대한 스키마를 정의하는 언어입니다. 데이터의 타입, 필수 필드, 허용 값 등을 명시하여 데이터의 구조와 유효성을 검사할 수 있습니다.
*   **DOP (Data-Oriented Programming)에서의 중요성:** 데이터 유효성 검사는 DOP에서 중요한 개념입니다. 데이터가 스키마를 준수하는지 검증하여 데이터 무결성을 유지하고 애플리케이션의 안정성을 확보할 수 있습니다.
### JSON Schema 기본 구조
*   **`type` 필드:** 데이터 타입을 지정합니다. 예: `"object"`, `"string"`, `"array"`
*   **`properties` 필드:** 객체(object) 타입의 경우, 각 필드의 스키마를 정의합니다.
*   **`items` 필드:** 배열(array) 타입의 경우, 배열 요소의 스키마를 정의합니다.
*   **`enum` 필드:** 특정 값들만 허용하도록 제한합니다 (열거형).
*   **`required` 필드:** 객체 타입에서 필수 필드를 지정합니다. 값은 필수 필드 이름의 배열입니다.
### JSON Schema 예제: 검색 요청 스키마
책 검색 요청의 스키마를 정의하는 예제를 통해 JSON Schema의 사용법을 설명합니다.
1.  **기본 스키마:** `"type": "object"`, `"properties": {...}`
2.  **필드 타입 지정:** `"title": {"type": "string"}, "fields": {"type": "array"}`
3.  **배열 요소 타입 지정:**  `"fields": {"type": "array", "items": {"type": "string"}}`
4.  **허용 값 제한 (enum):** `{"fields": {"type": "array", "items": {"enum": [...]}}}`
5.  **필수 필드 지정 (required):** `"required": ["title", "fields"]`
### 데이터 유효성 검사 방법
*   **유효성 검사 라이브러리:** JSON Schema를 검증하는 라이브러리를 사용합니다. JavaScript, Java, C#, Python, Ruby 등 다양한 언어에서 사용할 수 있습니다.
*   **validate 함수:** 라이브러리는 일반적으로 스키마와 데이터를 입력으로 받아 유효성 검사 결과를 반환하는 `validate` 함수를 제공합니다.  (true: 유효, false: 무효)
### JSON Schema의 장점
*   **언어 독립성:** 다양한 프로그래밍 언어에서 사용할 수 있습니다.
*   **표현력:** 클래스로 표현하기 어려운 복잡한 유효성 검사 조건을 정의할 수 있습니다 (예: 숫자 범위, 정규 표현식).
### 추가 정보
*   **고급 유효성 검사:** 숫자 범위 검사, 정규 표현식과 같은 고급 유효성 검사 기능이 있습니다.
*   **유효성 검사 실패 정보:** 유효성 검사 실패 시, 구체적인 오류 정보를 얻을 수 있습니다.
*   **스키마 복잡성:** JSON Schema는 클래스 정의보다 더 많은 정보를 제공하며 유연합니다.
구성노드3(7.3 Schema flexibility and strictness): ## 7.3 Schema 유연성(flexibility)과 엄격성(strictness)
본 내용은 JSON Schema를 사용하여 데이터의 유효성을 검사하는 과정에서, 스키마의 유연성과 엄격성을 조절하는 방법에 대해 설명합니다.
### 1. 기본 개념: 필드의 선택성과 필수성
*   **JSON Schema의 기본 동작**: 맵(map) 내 필드는 기본적으로 선택적(optional)입니다. 즉, 스키마에 정의되지 않은 필드가 있어도 유효성 검사에서 오류가 발생하지 않습니다.
*   **필수 필드 정의**: `required` 배열을 사용하여 필수 필드를 지정합니다. `required` 배열에 포함된 필드는 반드시 데이터에 존재해야 합니다.
### 2. 스키마 재사용 및 구성 가능성
*   **스키마 분리**: JSON Schema는 맵과 같아서 다른 맵처럼 자유롭게 조작하고 구성할 수 있습니다.
*   예시: 재사용을 위해 개별 스키마 정의(예: `bookInfoSchema`)를 만들고, 이를 상위 스키마(예: `searchBooksResponseSchema`) 내에서 `items`의 값으로 사용할 수 있습니다.
*   **장점**: 코드의 가독성을 높이고, 스키마의 재사용성을 증대합니다.
### 3. 외부 데이터 유효성 검사
*   **데이터 유효성 검사의 중요성**: 외부 데이터 소스(예: 데이터베이스)에서 가져온 데이터는 유효성 검사를 통해 신뢰성을 확보해야 합니다.
*   **예시**: 데이터베이스 검색 응답의 스키마를 정의하여, 응답에 예상된 필드(title, isbn, available)와 데이터 타입이 포함되어 있는지 검증합니다.
### 4. `additionalProperties` 필드
*   **기본 동작**: JSON Schema는 기본적으로 스키마에 정의되지 않은 추가 필드를 허용합니다.
*   **`additionalProperties` 설정**: `additionalProperties` 필드를 사용하여 추가 필드의 허용 여부를 제어합니다.
*   `additionalProperties: false`: 스키마에 정의되지 않은 필드는 허용하지 않음(엄격한 모드).
*   **사용 시점**:
*   응답(response) 스키마: 엄격하게 추가 필드를 허용하지 않도록 설정하는 것이 좋습니다. 서버는 응답을 생성하므로, 불필요한 데이터를 포함하지 않도록 관리할 수 있습니다.
*   요청(request) 스키마: 유연하게 추가 필드를 허용하는 것이 좋을 수 있습니다. 클라이언트가 보낸 요청에 대해 최대한 유연하게 처리하여, 클라이언트의 편의성을 높일 수 있습니다.
### 5. "Jon Postel의 견고성 원칙"
*   **원칙**: "보내는 데이터는 신중하게 하고, 받는 데이터는 관대하게 하라(Be conservative in what you send, be liberal in what you accept)."
*   **의미**: 서버는 자신이 생성하는 데이터(응답)에 대해 엄격하게 관리하고, 클라이언트로부터 받는 데이터(요청)는 가능한 유연하게 처리해야 합니다.
구성노드4(7.4 Schema composition): ## 7.4 Schema Composition: JSON Schema의 유연성 확장
### 7.4.1 상황 소개: 외부 API 데이터 검증
*   **문제 제기:** 외부 웹 서비스에서 제공하는 데이터의 유효성 검증 필요. 예시: Open Library Books API.
*   **예시 데이터:** "Watchmen" 책의 Open Library Books API 응답 JSON 데이터.
*   **초기 시도:** API 응답 구조에 맞는 JSON Schema를 작성하여 기본적인 유효성 검증 수행.
*   **문제점:** `isbn_10`과 `isbn_13` 필드의 필수 여부 문제 발생. 책의 출판 시기에 따라 두 필드 중 하나 또는 둘 다 존재할 수 있음.
### 7.4.2 JSON Schema Composition의 필요성
*   **목표:** `isbn_10` 또는 `isbn_13` 중 적어도 하나는 반드시 존재해야 하고, 기본 정보(title 등)도 항상 존재해야 함을 표현하는 유효성 검증 규칙 구현.
*   **해결책:** JSON Schema Composition을 활용하여 복잡한 유효성 검증 규칙을 표현.
### 7.4.3 JSON Schema Composition의 개념
*   **개념:** 여러 스키마를 조합하여 더 복잡한 규칙을 정의하는 방법. 논리 연산(AND, OR, NOT)과 유사한 방식으로 스키마를 결합.
*   **연산자:**
*   `allOf`: 모든 스키마를 만족해야 함 (AND).
*   `anyOf`: 스키마 중 적어도 하나를 만족해야 함 (OR).
*   `oneOf`: 정확히 하나의 스키마를 만족해야 함.
### 7.4.4 Open Library Books API 응답 스키마 예시
*   **기본 스키마 (`basicBookInfoSchema`):** `title`을 필수 필드로 하고, 다른 필드(publishers, number_of_pages 등)의 데이터 유형을 정의.
*   **`mandatoryIsbn13` 스키마:** `isbn_13`을 필수 필드로 정의.
*   **`mandatoryIsbn10` 스키마:** `isbn_10`을 필수 필드로 정의.
*   **결합된 스키마 (`bookInfoSchema`):**
*   `allOf`: `basicBookInfoSchema`를 만족해야 함.
*   `anyOf`: `mandatoryIsbn13` 또는 `mandatoryIsbn10` 중 하나를 만족해야 함.
*   **결과:** `title`이 필수이고, `isbn_10` 또는 `isbn_13` 중 하나 이상이 존재해야 함을 나타내는 스키마 완성.
### 7.4.5 Schema Composition의 장점
*   **유연성:** 기존 JSON Schema의 단일 스키마만으로는 표현하기 어려운 복잡한 유효성 검증 규칙을 정의할 수 있음.
*   **표현력 향상:** 데이터의 유효성 검증 조건을 클래스 기반의 데이터 표현 방식보다 더 효과적으로 표현 가능.
### 7.4.6 추가 고려사항
*   **검증 실패 시 문제 파악 어려움:**  검증 실패 시 어떤 스키마에서 문제가 발생했는지 명확하게 알기 어려울 수 있음. (추후 개선 필요)
*   **더 많은 기능:** JSON Schema는 이후 챕터에서 다루는 고급 데이터 유효성 검증 기능을 제공.
구성노드5(7.5 Details about data validation failures): ## 7.5 Details about data validation failures
### 7.5.1 Data Validation의 기본 개념
*   JSON Schema Validation은 데이터가 유효한지(valid) 또는 유효하지 않은지(invalid)를 판단합니다.
*   단순히 유효성 여부만 판단하는 것이 아니라, 실패 시 **구체적인 실패 이유**를 제공합니다.
### 7.5.2 실패 이유 접근 방법
*   각 데이터 검증 라이브러리(예: Ajv in JavaScript)는 실패 정보를 노출하는 방식이 다릅니다.
*   **Ajv**의 경우, 마지막 데이터 검증의 오류를 **`errors` 배열**에 저장합니다.
*   여러 실패가 발생할 수 있으므로 배열 형태로 관리합니다.
*   **`errors` 배열의 내용 예시**:
```json
[
{
"instancePath": "",
"schemaPath": "#/required",
"keyword": "required",
"params": {
"missingProperty":"title"
},
"message": "must have required property 'title'"
}
]
```
*   `instancePath`: 오류가 발생한 데이터 내의 위치
*   `schemaPath`: 오류가 발생한 스키마 내의 위치
*   `keyword`: 오류의 종류 (예: `required`)
*   `params`: 오류에 대한 추가 정보 (예: `missingProperty`)
*   `message`: 오류에 대한 인간 친화적인 설명
### 7.5.3 오류를 사람이 읽기 쉬운 형태로 변환
*   Ajv는 오류 배열을 사람이 이해하기 쉬운 형식으로 변환하는 유틸리티 함수인 `errorsText`를 제공합니다.
*   **예시**: `ajv.errorsText(ajv.errors);` -> "data must have required property 'title'"
### 7.5.4 여러 개의 오류 감지
*   Ajv는 기본적으로 첫 번째 검증 오류만 감지합니다 (성능상의 이유).
*   **여러 개의 오류를 감지**하려면, Ajv 생성자에 `allErrors: true` 옵션을 전달해야 합니다.
*   **예시**: `var ajv = new Ajv({allErrors: true});`
*   이렇게 하면 여러 개의 오류를 감지하고, `errors` 배열에 모든 오류 정보가 저장됩니다. `errorsText`를 사용하여 이 오류들을 사람이 읽을 수 있는 형식으로 변환할 수 있습니다.
*   **여러 개의 오류가 발생했을 때의 errorsText 출력 예시**: "data must have required property 'title', data/fields/0 must be string, data/fields/1 must be string"
구성노드6(Summary): ### DOP 원칙 #4: 데이터 스키마와 데이터 표현의 분리
*   **핵심 내용:** DOP 원칙 #4는 데이터 스키마와 데이터 표현을 분리하는 것이다. 이는 시스템의 경계에서 데이터 교환이 이루어지는 영역을 정의한다.
*   **중요성:** 데이터 유효성 검사를 통해 시스템의 무결성을 유지하고, 외부 데이터 소스로부터의 유효하지 않은 데이터를 걸러낸다.
*   **구체적인 내용:**
*   시스템 경계에서 데이터 유효성 검사가 이루어진다 (클라이언트 요청/응답, 외부 소스 데이터).
*   데이터 유효성 검사는 데이터가 스키마에 부합하는지 확인하는 것을 의미한다.
*   유효하지 않은 데이터는 오류 정보를 사람이 읽을 수 있는 형식으로 클라이언트에 반환한다.
*   경계에서 데이터가 유효한 경우, 내부에서 재검증할 필요가 없다.
### JSON Schema를 이용한 데이터 유효성 검사
*   **핵심 내용:** JSON Schema를 사용하여 데이터 유효성을 데이터 표현과 분리할 수 있다.
*   **장점:**
*   높은 표현력으로 다양한 데이터 구조를 정의하고 유효성 검사를 수행할 수 있다.
*   스키마 정의를 변수에 저장하고 다른 스키마에서 재사용할 수 있다.
*   JSON Schema는 본질적으로 맵(map)이므로, 프로그램 내에서 맵처럼 조작할 수 있다.
*   기본적으로 JSON Schema의 필드는 선택적(optional)이다.
*   **단점:** JSON Schema 문법은 다소 장황할 수 있다.
### 데이터 검증 관련 추가 고려 사항
*   **핵심 내용:**
*   데이터를 보낼 때는 엄격하게, 받는 데이터에 대해서는 유연하게 처리하는 것이 좋은 방법이다.
*   외부 데이터 소스에서 제공되는 데이터는 유효성을 검사하는 것이 좋다.
*   **구체적인 내용:**
*   JavaScript 환경에서 사용 가능한 JSON Schema 라이브러리: Ajv
*   Ajv는 기본적으로 첫 번째 유효성 검사 실패만 감지한다.
*   고급 유효성 검사는 별도 장(chapter 12)에서 다룬다.

*   **DOP에서의 데이터 검증 원리 (부모 노드와의 일관성 강조):** DOP는 데이터 스키마와 데이터 표현을 분리하여 유연성을 확보합니다. 이러한 분리는 데이터 유효성 검사를 통해 더욱 강력해지며, 시스템의 안정성을 높이는 기반이 됩니다.

구성노드2: 7.2 JSON Schema in a nutshell - 개요 (부모 노드와의 연결성 및 상세 내용 강화)

*   **핵심:** "JSON Schema in a nutshell"은 부모 노드에서 설명하는 "데이터 유효성 검사"를 위한 핵심 도구인 JSON Schema에 대한 간략한 소개를 제공합니다. JSON Schema는 DOP 원칙 #4를 구현하는 데 필수적인 기술입니다. 이 챕터에서는 JSON Schema를 사용하여 데이터의 구조와 유효성을 정의하고, 데이터를 검증하는 방법을 설명합니다.
*   **데이터 유효성 검사 및 JSON Schema의 중요성 (부모 노드 내용 명확화):**
    *   **데이터 표현과 스키마의 분리 (DOP 원칙 #4 강조):** 데이터 표현(실제 데이터)과 데이터 스키마(데이터 구조 정의)를 분리하는 것은 DOP 원칙 #4의 핵심입니다. 이를 통해 데이터의 유효성을 독립적으로 검증하고, 시스템의 유연성을 유지할 수 있습니다.
    *   **JSON Schema의 역할:** JSON Schema는 JSON 형식의 데이터에 대한 스키마를 정의하는 언어입니다. 데이터의 타입, 필수 필드, 허용 값 등을 명시하여 데이터의 구조와 유효성을 검사합니다.
    *   **DOP (Data-Oriented Programming)에서의 중요성:** 데이터 유효성 검사는 DOP에서 필수적인 요소입니다. 데이터가 스키마를 준수하는지 검증하여 데이터 무결성을 유지하고 애플리케이션의 안정성을 확보합니다.
*   **JSON Schema 기본 구조 (부모 노드 내용 상세화):**
    *   **`type` 필드:** 데이터 타입을 지정합니다. 예: `"object"`, `"string"`, `"array"` (부모 노드 내용 그대로)
    *   **`properties` 필드:** 객체(object) 타입의 경우, 각 필드의 스키마를 정의합니다. (부모 노드 내용 그대로)
    *   **`items` 필드:** 배열(array) 타입의 경우, 배열 요소의 스키마를 정의합니다. (부모 노드 내용 그대로)
    *   **`enum` 필드:** 특정 값들만 허용하도록 제한합니다 (열거형). (부모 노드 내용 그대로)
    *   **`required` 필드:** 객체 타입에서 필수 필드를 지정합니다. 값은 필수 필드 이름의 배열입니다. (부모 노드 내용 그대로)
*   **JSON Schema 예제: 검색 요청 스키마 (예제 명확성 강화):**  (부모 노드 내용과 일치하도록 수정)
    *   책 검색 요청의 스키마를 정의하는 예제를 통해 JSON Schema의 사용법을 설명합니다.
        1.  **기본 스키마:** `"type": "object"`, `"properties": {...}`
        2.  **필드 타입 지정:** `"title": {"type": "string"}, "fields": {"type": "array"}`
        3.  **배열 요소 타입 지정:**  `"fields": {"type": "array", "items": {"type": "string"}}`
        4.  **허용 값 제한 (enum):** `{"fields": {"type": "array", "items": {"enum": [...]}}}`
        5.  **필수 필드 지정 (required):** `"required": ["title", "fields"]`
*   **데이터 유효성 검사 방법 (부모 노드 내용과 연결):**
    *   **유효성 검사 라이브러리:** JSON Schema를 검증하는 라이브러리를 사용합니다. JavaScript, Java, C#, Python, Ruby 등 다양한 언어에서 사용할 수 있습니다. (부모 노드 내용과 일치)
    *   **validate 함수:** 라이브러리는 일반적으로 스키마와 데이터를 입력으로 받아 유효성 검사 결과를 반환하는 `validate` 함수를 제공합니다. (true: 유효, false: 무효) (부모 노드 내용과 일치)
*   **JSON Schema의 장점 (부모 노드 내용 강조):**
    *   **언어 독립성:** 다양한 프로그래밍 언어에서 사용할 수 있습니다. (부모 노드 내용과 일치)
    *   **표현력:** 클래스로 표현하기 어려운 복잡한 유효성 검사 조건을 정의할 수 있습니다 (예: 숫자 범위, 정규 표현식). (부모 노드 내용과 일치)
*   **추가 정보 (부모 노드 내용과 연결):**
    *   **고급 유효성 검사:** 숫자 범위 검사, 정규 표현식과 같은 고급 유효성 검사 기능이 있습니다. (부모 노드 내용과 일치)
    *   **유효성 검사 실패 정보:** 유효성 검사 실패 시, 구체적인 오류 정보를 얻을 수 있습니다. (이후 7.5 에서 상세히 다룸)
    *   **스키마 복잡성:** JSON Schema는 클래스 정의보다 더 많은 정보를 제공하며 유연합니다. (부모 노드 내용과 일치)

구성노드3: 7.3 Schema flexibility and strictness (부모 노드와의 연결성 및 중요성 강조)

*   **핵심:** JSON Schema를 사용하여 데이터의 유효성을 검사할 때, 스키마의 유연성과 엄격성을 적절하게 조절하는 것은 데이터 무결성과 시스템 유연성 사이의 균형을 맞추는 데 중요합니다. 이는 특히 시스템 경계에서 데이터를 주고받는 경우, 각 상황에 맞는 유효성 검사 규칙을 적용하는 것을 의미합니다.
*   **1. 기본 개념: 필드의 선택성과 필수성 (부모 노드 내용 그대로):**
    *   **JSON Schema의 기본 동작**: 맵(map) 내 필드는 기본적으로 선택적(optional)입니다. 즉, 스키마에 정의되지 않은 필드가 있어도 유효성 검사에서 오류가 발생하지 않습니다.
    *   **필수 필드 정의**: `required` 배열을 사용하여 필수 필드를 지정합니다. `required` 배열에 포함된 필드는 반드시 데이터에 존재해야 합니다.
*   **2. 스키마 재사용 및 구성 가능성 (부모 노드 내용 그대로):**
    *   **스키마 분리**: JSON Schema는 맵과 같아서 다른 맵처럼 자유롭게 조작하고 구성할 수 있습니다.
    *   예시: 재사용을 위해 개별 스키마 정의(예: `bookInfoSchema`)를 만들고, 이를 상위 스키마(예: `searchBooksResponseSchema`) 내에서 `items`의 값으로 사용할 수 있습니다.
    *   **장점**: 코드의 가독성을 높이고, 스키마의 재사용성을 증대합니다.
*   **3. 외부 데이터 유효성 검사 (부모 노드 내용 및 중요성 강조):**
    *   **데이터 유효성 검사의 중요성**: 외부 데이터 소스에서 가져온 데이터는 유효성 검사를 통해 신뢰성을 확보해야 합니다. 특히, 시스템 경계에서 외부 데이터의 유효성을 검사하는 것은 데이터 무결성을 유지하는 데 필수적입니다.
    *   **예시**: 데이터베이스 검색 응답의 스키마를 정의하여, 응답에 예상된 필드(title, isbn, available)와 데이터 타입이 포함되어 있는지 검증합니다.
*   **4. `additionalProperties` 필드 (부모 노드 내용과 역할 강조):**
    *   **기본 동작**: JSON Schema는 기본적으로 스키마에 정의되지 않은 추가 필드를 허용합니다.
    *   **`additionalProperties` 설정**: `additionalProperties` 필드를 사용하여 추가 필드의 허용 여부를 제어합니다.
        *   `additionalProperties: false`: 스키마에 정의되지 않은 필드는 허용하지 않음(엄격한 모드). - **중요:** 시스템 내부 데이터의 검증에 유용합니다.
        *   **사용 시점**:
            *   **응답(response) 스키마**: 엄격하게 추가 필드를 허용하지 않도록 설정하는 것이 좋습니다. 서버는 응답을 생성하므로, 불필요한 데이터를 포함하지 않도록 관리할 수 있습니다. - **핵심:** 서버 응답에 대한 엄격한 검증은 데이터 보안과 시스템 안정성을 강화합니다.
            *   **요청(request) 스키마**: 유연하게 추가 필드를 허용하는 것이 좋을 수 있습니다. 클라이언트가 보낸 요청에 대해 최대한 유연하게 처리하여, 클라이언트의 편의성을 높일 수 있습니다. - **핵심:** 사용자 경험 개선 및 API 호환성 유지를 위해 요청 데이터에 대한 유연성을 확보합니다.
*   **5. "Jon Postel의 견고성 원칙" (부모 노드와의 연관성 강조):**
    *   **원칙**: "보내는 데이터는 신중하게 하고, 받는 데이터는 관대하게 하라(Be conservative in what you send, be liberal in what you accept)."
    *   **의미**: 서버는 자신이 생성하는 데이터(응답)에 대해 엄격하게 관리하고, 클라이언트로부터 받는 데이터(요청)는 가능한 유연하게 처리해야 합니다. 이 원칙은 데이터 스키마와 데이터 표현의 분리를 통해 시스템 유연성을 확보하고, 데이터 유효성 검사를 통해 시스템의 안정성을 유지하는 DOP의 핵심 철학을 잘 보여줍니다.

구성노드4: 7.4 Schema composition (부모 노드와의 연결성 및 깊이 있는 설명)

*   **핵심:** JSON Schema Composition은 부모 노드에서 설명하는 데이터 유효성 검사의 유연성을 극대화하는 중요한 기술입니다. 여러 스키마를 조합하여 복잡한 유효성 검사 규칙을 정의함으로써, 데이터 모델의 복잡성을 효과적으로 관리하고 다양한 요구사항을 충족할 수 있습니다. 이는 DOP 원칙 #4를 더욱 효과적으로 실현하는 데 기여합니다.
*   **7.4.1 상황 소개: 외부 API 데이터 검증 (부모 노드와 연결, 문제점 명확화):**
    *   **문제 제기:** 외부 웹 서비스, 특히 Open Library Books API와 같이 데이터 구조가 유연하고 변경될 수 있는 API에서 제공되는 데이터의 유효성 검증 필요.
    *   **예시 데이터:** "Watchmen" 책의 Open Library Books API 응답 JSON 데이터.
    *   **초기 시도:** API 응답 구조에 맞는 JSON Schema를 작성하여 기본적인 유효성 검증 수행.
    *   **문제점:** `isbn_10`과 `isbn_13` 필드의 필수 여부 문제 발생. 책의 출판 시기에 따라 두 필드 중 하나 또는 둘 다 존재할 수 있으며, 상황에 따라 다른 필드도 존재하거나 부재할 수 있음. 단일 스키마로는 이러한 유연성을 표현하기 어려움.
*   **7.4.2 JSON Schema Composition의 필요성 (부모 노드 내용과 연결, 목표 명확화):**
    *   **목표:** `isbn_10` 또는 `isbn_13` 중 적어도 하나는 반드시 존재해야 하고, 기본 정보(title 등)도 항상 존재해야 함을 표현하는 유효성 검증 규칙 구현. 또한, API의 변화에 유연하게 대응하고, 새로운 필드의 추가를 허용하며, 데이터 무결성을 유지하는 것이 목표입니다.
    *   **해결책:** JSON Schema Composition을 활용하여 복잡한 유효성 검증 규칙을 표현.
*   **7.4.3 JSON Schema Composition의 개념 (부모 노드 내용과 연결):**
    *   **개념:** 여러 스키마를 조합하여 더 복잡한 규칙을 정의하는 방법. 논리 연산(AND, OR, NOT)과 유사한 방식으로 스키마를 결합.
    *   **연산자:**
        *   `allOf`: 모든 스키마를 만족해야 함 (AND).
        *   `anyOf`: 스키마 중 적어도 하나를 만족해야 함 (OR).
        *   `oneOf`: 정확히 하나의 스키마를 만족해야 함.
*   **7.4.4 Open Library Books API 응답 스키마 예시 (구체적인 예제, 부모 노드 내용 참조):**
    *   **기본 스키마 (`basicBookInfoSchema`):**  `title`을 필수 필드로 하고, 다른 필드(publishers, number_of_pages 등)의 데이터 유형을 정의. (부모 노드 내용 참조)
    *   **`mandatoryIsbn13` 스키마:** `isbn_13`을 필수 필드로 정의. (부모 노드 내용 참조)
    *   **`mandatoryIsbn10` 스키마:** `isbn_10`을 필수 필드로 정의. (부모 노드 내용 참조)
    *   **결합된 스키마 (`bookInfoSchema`):**
        *   `allOf`: `basicBookInfoSchema`를 만족해야 함. (부모 노드 내용 참조)
        *   `anyOf`: `mandatoryIsbn13` 또는 `mandatoryIsbn10` 중 하나를 만족해야 함. (부모 노드 내용 참조)
        *   **결과:** `title`이 필수이고, `isbn_10` 또는 `isbn_13` 중 하나 이상이 존재해야 함을 나타내는 스키마 완성. (부모 노드 내용 참조)
*   **7.4.5 Schema Composition의 장점 (부모 노드 내용과 연결, 표현력 강조):**
    *   **유연성:** 기존 JSON Schema의 단일 스키마만으로는 표현하기 어려운 복잡한 유효성 검증 규칙을 정의할 수 있음. API의 변화에 유연하게 대응할 수 있으며, 다양한 데이터 구조를 표현할 수 있습니다.
    *   **표현력 향상:** 데이터의 유효성 검증 조건을 클래스 기반의 데이터 표현 방식보다 더 효과적으로 표현 가능. 데이터의 의미와 구조를 더 정확하게 반영할 수 있습니다.
*   **7.4.6 추가 고려사항 (부모 노드 내용과 연결, 문제점 보완):**
    *   **검증 실패 시 문제 파악 어려움:**  검증 실패 시 어떤 스키마에서 문제가 발생했는지 명확하게 알기 어려울 수 있음. (해결책: 검증 라이브러리의 오류 메시지 활용, 디버깅 도구 사용).
    *   **더 많은 기능:** JSON Schema는 이후 챕터에서 다루는 고급 데이터 유효성 검증 기능을 제공. (예: 사용자 정의 검증, 정규식, 숫자 범위 검증).

구성노드5: 7.5 Details about data validation failures (부모 노드와의 연결성, 심층 분석 및 실용적인 내용 추가)

*   **핵심:** 데이터 유효성 검사가 실패했을 때, 단순히 실패했다는 사실만 아는 것이 아니라, 왜 실패했는지에 대한 구체적인 정보를 얻는 것이 중요합니다.  이는 시스템의 오류를 디버깅하고, 사용자에게 정확한 피드백을 제공하며, 데이터 품질을 향상시키는 데 필수적입니다.  JSON Schema는 이러한 목적으로 상세한 오류 정보를 제공하며, 이 챕터에서는 그 활용법을 자세히 다룹니다.
*   **7.5.1 Data Validation의 기본 개념 (부모 노드 내용과 연결):**
    *   JSON Schema Validation은 데이터가 유효한지(valid) 또는 유효하지 않은지(invalid)를 판단합니다. (부모 노드 내용 그대로)
    *   단순히 유효성 여부만 판단하는 것이 아니라, 실패 시 **구체적인 실패 이유**를 제공합니다. (부모 노드 내용 그대로)
*   **7.5.2 실패 이유 접근 방법 (부모 노드 내용과 연결, 라이브러리별 차이점 강조):**
    *   각 데이터 검증 라이브러리(예: Ajv in JavaScript)는 실패 정보를 노출하는 방식이 다릅니다. (부모 노드 내용 그대로)
    *   **Ajv**의 경우, 마지막 데이터 검증의 오류를 **`errors` 배열**에 저장합니다. (부모 노드 내용 그대로)
    *   여러 실패가 발생할 수 있으므로 배열 형태로 관리합니다. (부모 노드 내용 그대로)
    *   **`errors` 배열의 내용 예시**: (부모 노드 내용 그대로)
        ```json
        [
        {
        "instancePath": "",
        "schemaPath": "#/required",
        "keyword": "required",
        "params": {
        "missingProperty":"title"
        },
        "message": "must have required property 'title'"
        }
        ]
        ```
        *   `instancePath`: 오류가 발생한 데이터 내의 위치 (부모 노드 내용 그대로)
        *   `schemaPath`: 오류가 발생한 스키마 내의 위치 (부모 노드 내용 그대로)
        *   `keyword`: 오류의 종류 (예: `required`) (부모 노드 내용 그대로)
        *   `params`: 오류에 대한 추가 정보 (예: `missingProperty`) (부모 노드 내용 그대로)
        *   `message`: 오류에 대한 인간 친화적인 설명 (부모 노드 내용 그대로)
*   **7.5.3 오류를 사람이 읽기 쉬운 형태로 변환 (부모 노드 내용과 연결, 실용적인 활용법):**
    *   Ajv는 오류 배열을 사람이 이해하기 쉬운 형식으로 변환하는 유틸리티 함수인 `errorsText`를 제공합니다. (부모 노드 내용 그대로)
    *   **예시**: `ajv.errorsText(ajv.errors);` -> "data must have required property 'title'" (부모 노드 내용 그대로)
    *   **실용적인 활용**:  `errorsText`를 사용하여, 유효성 검사 실패 시 클라이언트에게 친절한 오류 메시지를 제공할 수 있습니다. 예를 들어, "제목(title) 필드가 누락되었습니다."와 같은 메시지를 표시할 수 있습니다.
*   **7.5.4 여러 개의 오류 감지 (부모 노드 내용과 연결, 실용적인 활용법 및 예시):**
    *   Ajv는 기본적으로 첫 번째 검증 오류만 감지합니다 (성능상의 이유). (부모 노드 내용 그대로)
    *   **여러 개의 오류를 감지**하려면, Ajv 생성자에 `allErrors: true` 옵션을 전달해야 합니다. (부모 노드 내용 그대로)
    *   **예시**: `var ajv = new Ajv({allErrors: true});` (부모 노드 내용 그대로)
    *   이렇게 하면 여러 개의 오류를 감지하고, `errors` 배열에 모든 오류 정보가 저장됩니다. `errorsText`를 사용하여 이 오류들을 사람이 읽을 수 있는 형식으로 변환할 수 있습니다. (부모 노드 내용 그대로)
    *   **여러 개의 오류가 발생했을 때의 errorsText 출력 예시**: "data must have required property 'title', data/fields/0 must be string, data/fields/1 must be string" (부모 노드 내용 그대로)
    *   **실용적인 활용:**  `allErrors: true` 옵션을 사용하여, 여러 개의 오류를 한 번에 파악하고 수정할 수 있습니다. 예를 들어, 클라이언트가 여러 개의 필드를 잘못 입력한 경우, 모든 오류를 한 번에 알려주어 사용자 경험을 향상시킬 수 있습니다.

구성노드6: Summary (부모 노드와 각 구성 노드의 내용 종합, 학습 목표 강조)

*   **핵심 목표:** 이 챕터에서는 데이터 지향 프로그래밍(DOP)의 핵심 원칙 중 하나인 "데이터 스키마와 데이터 표현의 분리"를 실현하기 위한 JSON Schema를 활용한 데이터 유효성 검사에 대해 학습했습니다.  이를 통해 시스템의 무결성을 유지하고, 외부 데이터 소스로부터의 유효하지 않은 데이터를 효과적으로 관리하며, 오류 발생 시 정확한 정보를 획득하여 시스템의 안정성과 사용자 경험을 향상시키는 방법을 익혔습니다.
*   **DOP 원칙 #4: 데이터 스키마와 데이터 표현의 분리 (요약, 부모 노드 및 각 구성 노드 내용 종합):**
    *   DOP 원칙 #4는 데이터 스키마와 데이터 표현을 분리하는 것입니다. 이는 시스템의 경계에서 데이터 교환이 이루어지는 영역을 정의하며, 데이터 유효성 검사를 통해 시스템의 무결성을 유지하고, 외부 데이터 소스로부터의 유효하지 않은 데이터를 걸러냅니다.
    *   **핵심 요소:**
        *   시스템 경계에서 데이터 유효성 검사가 이루어집니다 (클라이언트 요청/응답, 외부 소스 데이터). (구성노드 1)
        *   데이터 유효성 검사는 데이터가 스키마에 부합하는지 확인하는 것을 의미합니다. (구성노드 2)
        *   유효하지 않은 데이터는 오류 정보를 사람이 읽을 수 있는 형식으로 클라이언트에 반환됩니다. (구성노드 5)
        *   경계에서 데이터가 유효한 경우, 내부에서 재검증할 필요가 없습니다. (구성노드 1)
*   **JSON Schema를 이용한 데이터 유효성 검사 (요약, 부모 노드 및 각 구성 노드 내용 종합):**
    *   JSON Schema를 사용하여 데이터 유효성을 데이터 표현과 분리할 수 있습니다. (구성노드 2)
    *   **핵심 장점:**
        *   높은 표현력으로 다양한 데이터 구조를 정의하고 유효성 검사를 수행할 수 있습니다. (구성노드 2, 4)
        *   스키마 정의를 변수에 저장하고 다른 스키마에서 재사용할 수 있습니다. (구성노드 2, 3)
        *   JSON Schema는 본질적으로 맵(map)이므로, 프로그램 내에서 맵처럼 조작할 수 있습니다. (구성노드 2, 3)
        *   기본적으로 JSON Schema의 필드는 선택적(optional)이며, 유연성과 엄격성을 조절할 수 있습니다. (구성노드 3)
    *   **핵심 단점:**
        *   JSON Schema 문법은 다소 장황할 수 있습니다. (구성노드 2)
        *   검증 실패 시 문제 파악이 어려울 수 있으나, 오류 메시지 활용을 통해 해결할 수 있습니다. (구성노드 5)
*   **데이터 검증 관련 추가 고려 사항 (요약, 부모 노드 및 각 구성 노드 내용 종합):**
    *   데이터를 보낼 때는 엄격하게, 받는 데이터에 대해서는 유연하게 처리하는 것이 좋습니다. (구성노드 3)
    *   외부 데이터 소스에서 제공되는 데이터는 반드시 유효성을 검사해야 합니다. (구성노드 3)
    *   데이터 유효성 검사 실패 시, 구체적인 오류 정보를 활용하여 디버깅하고, 사용자에게 정확한 피드백을 제공해야 합니다. (구성노드 5)
