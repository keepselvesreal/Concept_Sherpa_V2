# 1.2_Sources_of_complexity

<구성 노드 반영 완료>

## 핵심 내용
객체 지향 프로그래밍(OOP)은 코드와 데이터의 결합, 가변 객체, 복잡한 클래스 계층 구조로 인해 시스템 복잡성을 증가시킨다. 데이터 중심 프로그래밍(DOP)은 코드와 데이터를 분리하고 불변성을 활용하여 이러한 복잡성을 줄이는 대안을 제시한다. DOP는 OOP의 문제점을 해결하고 시스템을 더욱 단순하고 예측 가능하게 만들어 유지보수성을 향상시킨다.

## 상세 핵심 내용
OOP 시스템의 복잡성은 클래스 내 코드와 데이터의 혼합으로 인한 클래스 간 과도한 관계, 객체의 가변성으로 인한 예측 불가능한 코드 동작, 데이터 직렬화의 어려움, 그리고 복잡한 클래스 계층 구조로 인한 유지보수 어려움에서 비롯된다. 특히, 멤버 변수의 가변성은 멀티 스레드 환경에서 예측 불가능한 결과를 초래하며, 이를 해결하기 위해 뮤텍스와 같은 동기화 메커니즘을 사용하지만 성능 저하와 데드락의 위험이 있다. JSON 직렬화/역직렬화 과정 또한 클래스에 묶인 데이터 때문에 복잡해진다. DOP는 코드와 데이터를 분리하고, 데이터 불변성을 통해 예측 가능한 코드 동작을 보장하며, 데이터에 대한 일반적인 접근 방식을 제공하여 이러한 복잡성을 완화한다. 또한 상속 대신 구성을 활용하여 클래스 계층 구조를 단순화하고 시스템 변경에 대한 유연성을 확보할 수 있다. DOP는 OOP 및 함수형 프로그래밍(FP)과 호환되며, OOP 시스템에 DOP 원칙을 적용하면 시스템의 복잡성을 효과적으로 줄일 수 있다.

## 상세 정보
*   **복잡성의 원인:**
    *   코드와 데이터의 혼합: 클래스가 많은 관계에 관여하게 되며, 클래스 다이어그램이 복잡해진다. Member 클래스가 Library, BookLending, User 등 다양한 클래스와 관계를 가지는 예시가 있다. Member 클래스를 MemberCode와 MemberData로 분리하여 관계를 단순화할 수 있다.
    *   가변 객체: 코드 이해에 추가적인 사고가 필요하며, 멀티 스레드 환경에서 명시적인 동기화가 요구된다. context switch로 인해 객체의 상태가 예기치 않게 변경될 수 있다. DOP는 데이터 불변성을 통해 이 문제를 해결한다.
    *   데이터의 객체 내 잠금: 데이터 직렬화가 어려워진다. JSON 직렬화/역직렬화를 위해 매번 새로운 클래스와 코드를 작성해야 하는 문제점이 발생한다. DOP는 데이터에 대한 일반적인 접근 방식을 제공하여 이 문제를 해결한다.
    *   코드의 클래스 내 잠금: 클래스 계층 구조가 복잡해진다. VIP 멤버와 Super 멤버 추가 시 클래스 상속 구조가 복잡해지고 다이아몬드 상속 문제가 발생할 수 있다. 상속 대신 구성을 사용하면 이러한 문제를 피할 수 있다.
*   **DOP(Data-Oriented Programming)의 특징:**
    *   코드와 데이터를 분리하여 시스템을 단순화한다. 독립적인 코드 하위 시스템과 데이터 하위 시스템을 구성할 수 있다.
    *   모든 데이터를 불변 값으로 취급하여 예측 가능한 코드 동작을 보장한다. 개발자에게 안정적인 환경을 제공한다.
    *   데이터에 대한 일반적인 접근 방식을 제공하여 데이터 직렬화를 용이하게 한다. JSON 직렬화/역직렬화를 위한 일반적인 방법을 제공한다.
    *   OOP 및 FP와 호환 가능.
*   **OOP의 문제점:**
    *   JSON 직렬화 및 역직렬화에 많은 클래스와 코드 작성이 필요하다. SearchController, SearchQuery, SearchResult와 같은 클래스를 반복적으로 생성해야 한다.
    *   클래스 상속을 통한 코드 재사용이 새로운 요구사항 추가 시 복잡성을 증가시킬 수 있다 (다이아몬드 상속 문제). VIP 멤버와 Super 멤버 추가 시 다중 상속 문제가 발생한다.
*   **Klafim 라이브러리 관리 시스템 예시:**
    *   회원(Member) 클래스를 코드(MemberCode)와 데이터(MemberData)로 분리하여 관계를 단순화한다.
    *   VIP 회원 및 Super 회원 추가 시 클래스 계층 구조의 복잡성 증가 및 다이아몬드 상속 문제 발생. 상속 대신 구성을 사용하여 해결할 수 있다.

## 주요 화제
*   OOP의 복잡성 원인 (코드와 데이터의 결합, 가변성, 데이터 직렬화, 복잡한 상속 구조)

*   클래스 상속의 문제점과 다이아몬드 상속 문제
*   구성(Composition) vs 상속(Inheritance)
*   Klafim 라이브러리 관리 시스템 사례 연구

# 1.2.1_Many_relations_between_classes

## 핵심 내용
객체 지향 프로그래밍(OOP)에서 코드와 데이터가 클래스 내에 혼합되어 있어 클래스 다이어그램이 복잡해지는 경향이 있다. 데이터 중심 프로그래밍(DOP)은 코드와 데이터를 분리하여 시스템을 단순화하고 유지보수성을 높인다. 클래스를 코드와 데이터 엔티티로 분리하면 시스템을 더 단순하고 이해하기 쉽게 만들 수 있다. 분리된 시스템은 독립적인 하위 시스템으로 구성되어 개별적으로 이해할 수 있다는 장점이 있다.

## 상세 핵심 내용
OOP의 특징인 코드와 데이터의 혼합은 클래스 간의 관계를 증가시켜 시스템 복잡성을 증가시킨다. Member 클래스처럼 여러 관계를 가지는 클래스는 이해하기 어렵다. DOP에서는 클래스를 MemberCode(코드)와 MemberData(데이터)로 분리하여 각 엔티티의 관계 수를 줄일 수 있다. 모든 클래스를 코드와 데이터 엔티티로 분리하면 독립적인 코드 하위 시스템과 데이터 하위 시스템을 구성할 수 있어 전체 시스템이 더 단순해진다. 이러한 분리는 시스템의 각 부분을 독립적으로 이해할 수 있게 하여 시스템 복잡성을 효과적으로 관리할 수 있으며, 유지보수성을 향상시킨다.

## 상세 정보
*   **클래스 다이어그램 복잡성**: 클래스 다이어그램의 복잡성은 엔티티와 관계의 수를 통해 평가할 수 있다.
*   **OOP의 복잡성**: OOP에서는 코드와 데이터가 클래스 내에 혼합되어 있어 시스템 복잡성을 증가시킨다. (멤버 변수와 메서드)
*   **Member 클래스 예시**: Member 클래스는 Library, BookLending, User, Librarian, BookItem 과의 관계를 가진다.
*   **클래스 분리**: Member 클래스를 MemberCode(코드)와 MemberData(데이터)로 분리하여 관계 수를 줄일 수 있다.
*   **분리된 시스템**: 모든 클래스를 코드와 데이터 엔티티로 분리하면 독립적인 코드 하위 시스템과 데이터 하위 시스템을 구성할 수 있다.
*   **독립적인 하위 시스템**: 분리된 시스템은 각 하위 시스템을 독립적으로 이해할 수 있어 전체 시스템 이해도를 높인다.

## 주요 화제
*   객체 지향 프로그래밍 (OOP)의 복잡성
*   클래스 다이어그램
*   코드와 데이터의 혼합
*   클래스 분리를 통한 복잡성 감소
*   독립적인 하위 시스템

# 1.2.2_Unpredictable_code_behavior

<부모 노드 반영 완료>

## 핵심 내용
객체 지향 프로그래밍(OOP)에서 데이터의 가변성은 멀티스레드 환경에서 예측 불가능한 코드 동작을 초래할 수 있다. 데이터 불변성을 강조하는 데이터 중심 프로그래밍(DOP)은 이러한 문제를 해결하고 안정적인 개발 환경을 제공하여 유지보수성을 높인다.

## 상세 핵심 내용
OOP에서 객체 멤버의 가변성은 코드의 예측 불가능성을 야기하며, 이는 특히 멀티스레드 환경에서 두드러진다. 두 번의 console.log 호출 사이에 객체의 상태가 변경될 수 있기 때문이다. 이러한 문제를 해결하기 위해 뮤텍스와 같은 동시성 안전 메커니즘을 사용할 수 있지만, 성능 저하 및 데드락의 위험이 따른다. DOP는 모든 데이터를 불변 값으로 취급하여 이러한 문제를 해결하고 개발자에게 안정적인 환경을 제공하며, 데이터 불변성은 DOP 개발자에게 정신적인 평화를 가져다준다. 데이터 불변성은 코드의 예측 가능성을 높여 디버깅 및 유지보수를 용이하게 한다.

## 상세 정보
1.  **예측 불가능한 코드 동작**: OOP 환경에서 객체 멤버의 가변성으로 인해 코드 실행 결과가 예측 불가능해질 수 있다.
2.  **단일 스레드 vs. 멀티 스레드**: 단일 스레드 환경에서는 코드 실행이 예측 가능하지만, 멀티 스레드 환경에서는 context switch로 인해 객체의 상태가 변경될 수 있다.
3.  **자바스크립트의 비동기 코드**: 자바스크립트와 같은 단일 스레드 환경에서도 비동기 코드를 통해 데이터가 수정될 경우 예측 불가능성이 발생할 수 있다.
4.  **원시 타입 vs. 객체 멤버**: 원시 타입은 일반적으로 불변이지만, 객체 멤버는 가변적이다.
5.  **OOP의 문제점**: 가변적인 객체 멤버를 보호하기 위해 뮤텍스를 사용할 수 있지만, 성능 저하 및 데드락 위험이 따른다.
6.  **DOP의 해결책**: DOP는 모든 데이터를 불변 값으로 취급하여 코드의 예측 가능성을 높이고 개발자에게 안정적인 환경을 제공한다. OOP의 복잡성을 줄이는 효과적인 대안이다.

## 주요 화제
*   객체 지향 프로그래밍 (OOP)
*   데이터 가변성
*   예측 불가능한 코드 동작
*   멀티 스레드 환경
*   데이터 불변성
*   데이터 중심 프로그래밍 (DOP)

*   데드락
*   성능 저하

# 1.2.3_Not_trivial_data_serialization

<부모 노드 반영 완료>

## 핵심 내용
객체 지향 프로그래밍(OOP)에서 JSON 데이터 직렬화/역직렬화는 데이터가 클래스에 묶여 있어 일반적인 접근이 어렵기 때문에 복잡하다. 데이터 중심 프로그래밍(DOP)은 이러한 문제를 해결하기 위한 일반적인 데이터 접근 방식을 제공한다.

## 상세 핵심 내용
Theo의 꿈속에서 Nancy는 REST API를 통해 Klafim의 도서관 관리 시스템에 접근할 수 있도록 요청하고, JSON을 전송 계층으로 사용한다. Theo는 `/search` 엔드포인트를 구현해야 하지만, OOP 방식으로는 JSON 직렬화/역직렬화를 위해 매번 새로운 클래스를 생성하고 코드를 반복해야 한다. 이는 데이터가 클래스 멤버에 갇혀 있어 일반적인 접근이 불가능하기 때문이다. 따라서 OOP에서는 데이터 직렬화가 어렵고, 이러한 어려움을 극복하기 위한 일반적인 데이터 접근 방식의 필요성을 제시하며, DOP는 JSON 직렬화 및 역직렬화를 위한 일반적인 방법을 제공한다.

## 상세 정보
*   Theo는 꿈속에서 REST API를 구현해야 하며, JSON을 사용하여 데이터를 주고받는다.
*   `/search` 엔드포인트를 구현하기 위해 SearchController, SearchQuery, SearchResult 클래스를 생성한다.
*   다른 엔드포인트(예: `/add-book-item`)를 구현할 때도 유사한 구조의 클래스(AddBookItemController, BookItemQuery, BookItemResult)를 반복적으로 생성해야 한다.
*   JSON 직렬화 및 역직렬화 코드를 매번 다시 작성해야 하는 문제점이 발생한다.
*   OOP에서는 데이터가 클래스 멤버에 갇혀 있어 일반적인 접근이 어렵다.
*   데이터 직렬화는 데이터 필드를 순회하고 필드 이름과 값을 연결하는 간단한 작업이지만, OOP에서는 복잡해진다.
*   대부분의 OOP 프로그래밍 언어는 JSON 변환의 어려움을 완화하기 위해 리플렉션 또는 코드 장황성을 사용한다.
*   DOP(Data-Oriented Programming)는 JSON 직렬화 및 역직렬화를 위한 일반적인 방법을 제공한다. 이는 OOP의 한계를 극복하는 대안이 될 수 있다.

## 핵심 내용
객체 지향 프로그래밍(OOP)에서 클래스 상속은 초기에는 코드 재사용에 유용하지만, 시스템 요구사항 변경에 따라 클래스 계층 구조를 복잡하게 만들고 다중 상속 문제를 야기할 수 있다. 따라서 상속보다는 구성(composition)을 사용하는 것이 더 유연하고 유지보수가 용이한 설계 방법일 수 있다.

## 상세 핵심 내용
OOP에서 클래스 상속은 코드 재사용에 유용하지만, 시스템 요구사항이 변경될 때 어려움을 야기할 수 있다. VIP 멤버와 Super 멤버 추가 사례에서 보듯이, 새로운 요구사항은 기존 클래스 계층 구조를 복잡하게 만들고 다중 상속으로 인한 "Deadly Diamonds of Death" 문제를 발생시킬 수 있다. Theo는 상속을 사용하여 문제를 해결하려 했지만, 결국 시스템 복잡성 증가로 인해 마감 기한 내에 Super 멤버 기능을 추가하는 데 실패한다. 이러한 문제는 상속 대신 구성을 사용했다면 피할 수 있었을 것이다. 이 사례는 OOP에서 유연하고 유지보수가 용이한 시스템 설계를 위해 구성의 중요성을 강조한다.

## 상세 정보
1.  **초기 시스템 설계**: 도서관 시스템에서 Librarians와 Members는 User 클래스에서 로그인 기능을 상속받는다.
2.  **VIP 멤버 추가**:
*   VIP 멤버는 도서 추가 권한을 가진다.
*   VIPMember 클래스는 Member 클래스에서 상속받고, Librarian 클래스의 addBookItem 기능을 재사용해야 한다.
*   UserWithBookItemRight 클래스를 도입하여 addBookItem 기능을 Librarian과 VIPMember가 공유하도록 한다.
*   다중 상속으로 인해 VIPMember 클래스에 다이아몬드 문제가 발생한다.
3.  **Super 멤버 추가**:
*   Super 멤버는 다른 멤버의 대출 목록을 볼 수 있는 권한을 가진다.
*   Super 멤버 추가는 시스템을 더욱 복잡하게 만들고 클래스 다이어그램에 여러 개의 다이아몬드 문제를 야기한다.
4.  **마감 기한 및 문제 발생**:
*   Theo는 Super 멤버 기능을 마감 기한 내에 추가하는 데 실패한다.
*   다이아몬드 문제를 해결하기 위해 구성을 시도하지만 시간이 부족하다.
5.  **결론**:
*   상속 대신 구성을 사용하는 것이 더 나은 설계 방법일 수 있다.
*   요구사항 변경에 유연하게 대처하기 위해 구성의 중요성을 강조한다. OOP의 복잡성을 관리하는 데 도움이 된다.
