## 7.3 Schema 유연성(flexibility)과 엄격성(strictness)

본 내용은 JSON Schema를 사용하여 데이터의 유효성을 검사하는 과정에서, 스키마의 유연성과 엄격성을 조절하는 방법에 대해 설명합니다.

### 1. 기본 개념: 필드의 선택성과 필수성

*   **JSON Schema의 기본 동작**: 맵(map) 내 필드는 기본적으로 선택적(optional)입니다. 즉, 스키마에 정의되지 않은 필드가 있어도 유효성 검사에서 오류가 발생하지 않습니다.
*   **필수 필드 정의**: `required` 배열을 사용하여 필수 필드를 지정합니다. `required` 배열에 포함된 필드는 반드시 데이터에 존재해야 합니다.

### 2. 스키마 재사용 및 구성 가능성

*   **스키마 분리**: JSON Schema는 맵과 같아서 다른 맵처럼 자유롭게 조작하고 구성할 수 있습니다.
    *   예시: 재사용을 위해 개별 스키마 정의(예: `bookInfoSchema`)를 만들고, 이를 상위 스키마(예: `searchBooksResponseSchema`) 내에서 `items`의 값으로 사용할 수 있습니다.
*   **장점**: 코드의 가독성을 높이고, 스키마의 재사용성을 증대합니다.

### 3. 외부 데이터 유효성 검사

*   **데이터 유효성 검사의 중요성**: 외부 데이터 소스(예: 데이터베이스)에서 가져온 데이터는 유효성 검사를 통해 신뢰성을 확보해야 합니다.
*   **예시**: 데이터베이스 검색 응답의 스키마를 정의하여, 응답에 예상된 필드(title, isbn, available)와 데이터 타입이 포함되어 있는지 검증합니다.

### 4. `additionalProperties` 필드

*   **기본 동작**: JSON Schema는 기본적으로 스키마에 정의되지 않은 추가 필드를 허용합니다.
*   **`additionalProperties` 설정**: `additionalProperties` 필드를 사용하여 추가 필드의 허용 여부를 제어합니다.
    *   `additionalProperties: false`: 스키마에 정의되지 않은 필드는 허용하지 않음(엄격한 모드).
*   **사용 시점**:
    *   응답(response) 스키마: 엄격하게 추가 필드를 허용하지 않도록 설정하는 것이 좋습니다. 서버는 응답을 생성하므로, 불필요한 데이터를 포함하지 않도록 관리할 수 있습니다.
    *   요청(request) 스키마: 유연하게 추가 필드를 허용하는 것이 좋을 수 있습니다. 클라이언트가 보낸 요청에 대해 최대한 유연하게 처리하여, 클라이언트의 편의성을 높일 수 있습니다.

### 5. "Jon Postel의 견고성 원칙"

*   **원칙**: "보내는 데이터는 신중하게 하고, 받는 데이터는 관대하게 하라(Be conservative in what you send, be liberal in what you accept)."
*   **의미**: 서버는 자신이 생성하는 데이터(응답)에 대해 엄격하게 관리하고, 클라이언트로부터 받는 데이터(요청)는 가능한 유연하게 처리해야 합니다.

## 7.3 Schema flexibility and strictness - 추가 상세 정보 및 새로운 내용 분석

**1. JSON Schema의 유연성 (Composability) 강조:**

*   **세부 내용:** JSON Schema는 단순한 맵(map, 즉, 객체)으로 구성되어 있어, 다른 맵처럼 자유롭게 조합하고 조작할 수 있습니다.
*   **예시:** `bookInfoSchema`와 `searchBooksResponseSchema`를 분리하여 재사용성을 높이는 방법. `bookInfoSchema`를 별도로 정의한 후, `searchBooksResponseSchema`에서 이를 `items` 필드로 사용하여 결합합니다.
*   **구현 방법:** JSON Schema는 문자열, 숫자, 객체, 배열 등과 같은 기본적인 JSON 데이터 타입으로 구성되므로, 변수에 할당하고, 다른 스키마 내에서 참조하며, 필요에 따라 조합하여 사용할 수 있습니다.

**2. 외부 데이터 소스(예: 데이터베이스)에서 데이터 검증의 중요성:**

*   **세부 내용:** 외부 데이터 소스에서 받은 데이터는 반드시 유효성 검사를 수행해야 합니다. 외부 데이터 소스는 예상치 못한 형식이나 구조의 데이터를 제공할 수 있으며, 이는 애플리케이션의 오류나 보안 문제를 야기할 수 있습니다.
*   **예시:** 데이터베이스 쿼리 응답의 예시. 응답은 `title`, `isbn`, `available` 필드를 가지며, `title`과 `isbn`은 문자열, `available`은 부울 값으로 정의됩니다.
*   **구현 방법:** 데이터베이스 응답의 스키마를 정의하고, 받은 데이터가 스키마를 준수하는지 JSON Schema 유효성 검사기를 사용하여 확인합니다.

**3. `additionalProperties` 필드의 역할과 중요성:**

*   **세부 내용:** JSON Schema에서 기본적으로 객체에 정의되지 않은 추가적인 필드를 허용합니다. `additionalProperties` 필드를 `false`로 설정하면, 스키마에 명시된 필드 외의 모든 추가 필드를 허용하지 않도록 합니다.
*   **예시:** `dummy_property`를 가진 데이터가 유효하지 않은 경우를 보여주는 예시. 스키마에 정의되지 않은 `dummy_property` 필드가 추가된 데이터는 `additionalProperties`가 `false`로 설정된 경우 유효성 검사에서 실패합니다.
*   **구현 방법:** 스키마 정의 시 `additionalProperties: false`를 설정합니다.
    ```json
    "additionalProperties": false
    ```

**4. 요청(Request)과 응답(Response) 스키마 유연성 차이:**

*   **세부 내용:** 일반적으로 요청에 대해서는 보다 유연하게, 응답에 대해서는 더 엄격하게 스키마를 적용하는 것이 좋습니다.
*   **예시:** 서버는 클라이언트가 보낸 요청에 대해 다양한 형태의 데이터를 수용하고, 응답에서는 명확하게 정의된 데이터만을 반환하도록 합니다.
*   **구현 방법:** 요청 스키마는 `additionalProperties`를 `true` (기본값)로 설정하고, 응답 스키마는 `additionalProperties`를 `false`로 설정합니다. 이는 서버가 예상치 못한 요청 필드에 대해 관대하게 대처하고, 클라이언트에게는 정확한 형식의 응답을 제공하여 상호 운용성을 높이는 데 기여합니다.

**5. Jon Postel의 견고성 원칙 (Robustness Principle):**

*   **세부 내용:** "보내는 데이터에 대해 보수적이고, 받는 데이터에 대해 관대하라." (Be conservative in what you send, be liberal in what you accept.)
*   **의미:** 서버는 클라이언트에게 정확하고 엄격한 형식의 데이터를 보내야 하고, 클라이언트의 요청에 대해서는 가능한 한 유연하게 처리해야 합니다.
*   **구현 방법:** 이는 요청과 응답에 대한 스키마 설정에 반영됩니다. 응답 스키마를 엄격하게 정의하고, 요청 스키마는 좀 더 유연하게 허용하여 이 원칙을 따를 수 있습니다.

**6. 추가 팁:**

*   JSON Schema는 필드 정의 시 `required` 배열을 사용하여 필수 필드를 지정합니다.
*   스키마는 코드에서 변수로 정의되고 조작될 수 있습니다.
*   데이터 유효성 검사는 외부 데이터뿐만 아니라 내부 데이터, 사용자 입력 등 다양한 곳에서 적용될 수 있습니다.

요약하자면, 이 챕터는 JSON Schema를 사용하여 데이터의 유효성을 검사하고, 스키마의 유연성을 활용하여 코드의 재사용성과 유지보수성을 높이는 방법을 보여줍니다. 특히, 요청과 응답에 대한 스키마의 유연성 차이를 강조하며, 외부 데이터 소스에서 데이터를 검증하는 중요성을 강조합니다.


## 주요 화제
- **JSON Schema를 이용한 스키마 유연성:** JSON Schema에서 맵 필드는 기본적으로 선택 사항이며, required 배열을 사용하여 필수 필드를 지정하는 방법, book 정보 스키마와 search response 스키마를 분리하여 스키마를 재사용하고 가독성을 높이는 방법 등 스키마를 유연하게 구성하는 방법을 설명합니다.

- **JSON Schema의 strictness:** JSON Schema의 `additionalProperties` 필드를 사용하여, 스키마에 정의되지 않은 추가적인 필드의 허용 여부를 제어하는 방법과 그 이유를 설명합니다. 기본적으로 추가 필드는 허용되며, `additionalProperties: false`를 설정하여 엄격하게 제한할 수 있습니다.

- **데이터 유효성 검증의 중요성:** 외부 데이터 소스 (예: 데이터베이스)로부터 데이터를 받을 때, 데이터 유효성 검증을 수행하는 것이 좋은 습관임을 강조하고, 그 중요성을 설명합니다.

- **데이터 유효성 검증 시의 엄격성과 유연성:** 응답 (response) 데이터에 대해서는 엄격하게, 요청 (request) 데이터에 대해서는 유연하게 접근하는 것이 좋은 방법이라고 설명합니다. "보내는 데이터는 보수적으로, 받는 데이터는 관대하게"라는 Jon Postel의 원칙을 인용하며, 그 이유와 장점을 설명합니다.


## 부차 화제
- JSON Schema에서 필드의 필수/선택 여부: JSON Schema에서 맵 필드는 기본적으로 선택 사항이며, `required` 배열에 포함시켜야 필수 필드로 지정할 수 있습니다.
- JSON Schema의 재사용성 및 구성 가능성: JSON Schema는 일반적인 맵과 같이 구성하고 조작할 수 있으므로, 재사용 가능한 스키마 조각을 만들 수 있습니다. (예: bookInfoSchema)
- 외부 데이터 검증의 중요성: 외부 데이터 소스 (예: 데이터베이스)로부터 받은 데이터를 검증하는 것은 좋은 관행이며, JSON Schema를 사용하여 데이터 구조를 검증할 수 있습니다.
- `additionalProperties` 필드: JSON Schema에서 기본적으로 스키마에 정의되지 않은 필드는 허용됩니다. `additionalProperties`를 `false`로 설정하여 추가 필드를 금지할 수 있습니다.
- 요청 및 응답 스키마의 엄격함 정도: 응답(서버)은 엄격하게, 요청(클라이언트)는 유연하게 처리하는 것이 일반적인 관행입니다. (Jon Postel의 Robustness Principle)
