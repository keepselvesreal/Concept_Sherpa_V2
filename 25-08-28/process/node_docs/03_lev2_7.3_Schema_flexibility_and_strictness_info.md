## 7.3 Schema flexibility and strictness: 유연성과 엄격성 사이의 균형

### 핵심 내용 및 필드의 유연성
*   **핵심:** JSON Schema의 유연성과 엄격성, 데이터 유효성 검사 모범 사례 (부모 노드 핵심 내용 반영).
*   **필드 필수 여부:** 기본적으로 선택적 (Optional) (부모 노드 재확인).

### 필수 필드 지정 및 예시 (상세화)
*   **필수 필드 지정 (재확인):** "required" 배열 사용. (부모 노드 재확인).
*   **예시 (확장):**
```json
{
  "type": "object",
  "required": ["title", "author"],
  "properties": {
    "title": { "type": "string" },
    "author": { "type": "string" },
    "description": { "type": "string" }
  }
}
```
*   "title", "author"는 필수, "description"은 선택적 (예시 추가).

### 스키마의 재사용 및 구성 (7.4절 연결)
*   **스키마 유연성 (재강조):** 맵(Map) 형태, 변수 할당, 다른 스키마 포함 용이 (부모 노드 재확인).
*   **스키마 분리 (재강조):** 가독성, 유지보수 용이 (부모 노드 재확인).
*   **예시:** "bookInfoSchema", "searchBooksResponseSchema" (부모 노드 예시 재확인, 7.4절 연결).

### 추가 속성 허용 여부 (additionalProperties)
*   **기본 동작 (재확인):** 추가 속성 허용 (부모 노드 재확인).
*   **추가 속성 금지 (재확인):** "additionalProperties: false" (부모 노드 재확인).
*   **예시 (확장):**
```json
{
  "type": "object",
  "required": ["title", "isbn"],
  "additionalProperties": false,
  "properties": {
    "title": { "type": "string" },
    "isbn": { "type": "string" }
  }
}
```
*   "title", "isbn" 외 속성 있으면 오류 발생 (부모 노드 예시 재확인).

### 데이터 유효성 검사 모범 사례 (핵심 강조, 7.1, 7.2, 7.5절 연계)
*   **외부 데이터 검증 (재강조):** 외부 소스 데이터 검증 필수 (부모 노드 재확인).
*   **송신 데이터 엄격성 (강조):** 응답(Response)은 "additionalProperties: false" 권장 (부모 노드 재확인).
*   **수신 데이터 유연성 (강조):** 요청(Request)은 유연하게 처리 (부모 노드 재확인).
*   **Jon Postel의 Robustness Principle (재확인):** "Be conservative in what you send, be liberal in what you accept." (부모 노드 재확인).
*   **요청/응답 차이 (중요성 강조):** 요청은 유연, 응답은 엄격 (부모 노드 재확인).
*   **실패 시 상세 오류 정보:** 시스템 경계에서 유효하지 않은 데이터의 유입을 막고, 오류 메시지를 사용자 친화적으로 제공 (7.1, 7.5절 연계).

## 상세 정보
7.3 Schema flexibility and strictness: **7.3 스키마 유연성 및 엄격성**

이 챕터는 JSON Schema의 유연성과 엄격성을 조절하는 방법을 다룹니다. 부모 노드의 7 Basic data validation 내용과 연계하여, 데이터 전송 원칙과 스키마 디자인의 중요성을 강조합니다.

**1. JSON Schema의 유연성과 엄격함 (부모 노드 반영):**

*   **필드의 기본 설정:** JSON Schema에서 객체 내 필드는 기본적으로 선택 사항입니다. 필수 필드로 지정하려면 `required` 배열에 포함해야 합니다.
*   **스키마의 조립:** JSON Schema는 맵(map, 객체)이므로 다른 맵처럼 구성하고 조작할 수 있습니다. 이를 통해 스키마를 재사용하고 모듈화하여 가독성을 높일 수 있습니다. (예: `bookInfoSchema`를 별도로 정의하여 `searchBooksResponseSchema`에서 사용)
*   **`additionalProperties` 설정:**
    *   JSON Schema에서 객체에 스키마에 정의되지 않은 추가 필드가 있는 경우, 기본적으로 유효한 것으로 간주됩니다.
    *   `additionalProperties: false`를 설정하면 스키마에 명시되지 않은 필드를 허용하지 않아 엄격한 유효성 검사를 수행할 수 있습니다.
*   **엄격함과 유연성의 균형:**
    *   **응답(Response) 데이터:** 서버가 클라이언트에게 보내는 응답 데이터는 가능한 한 엄격하게 검증하는 것이 좋습니다.
    *   **요청(Request) 데이터:** 클라이언트가 보내는 요청 데이터는 유연하게 처리하여 예상치 못한 입력에 대해 오류를 최소화하는 것이 좋습니다. (Jon Postel의 "보내는 것은 보수적으로, 받는 것은 너그럽게" 원칙, 부모 노드 '데이터 전송 원칙' 참고)

**2. 예시 및 구체적인 구현 방법 (부모 노드 예시 활용):**

*   **검색 응답 스키마 리팩토링 (Listing 7.12):** `bookInfoSchema`를 별도로 정의하고 이를 `searchBooksResponseSchema`에서 사용하여 스키마를 모듈화하는 방법을 보여줍니다.
*   **데이터베이스 응답 스키마 (Listing 7.13):** 데이터베이스 응답 데이터의 구조를 정의하는 스키마 예시. 모든 필드가 필수적이며, `title`, `isbn`, `available` 필드만 포함합니다.
*   **`additionalProperties` 예시 (Listing 7.14, 7.15):**
    *   **Listing 7.14:** `dummy_property`를 포함한 유효하지 않은 데이터 예시
    *   **Listing 7.15:** `additionalProperties: false`를 사용하여 추가 필드를 허용하지 않도록 설정하는 예시.

**3. 추가적인 내용 (부모 노드 내용 포함):**

*   **데이터 유효성 검사 중요성:** 외부 데이터 소스(예: 데이터베이스)에서 가져온 데이터는 항상 유효성 검사를 수행하는 것이 좋습니다.
*   **스키마의 목적:** 스키마는 데이터의 구조를 정의하고 유효성을 검사하여 오류를 방지하고 데이터 무결성을 유지하는 데 기여합니다.
*   **JSON Schema의 장점:** JSON Schema는 간단하고 재사용 가능하며, 객체 지향 프로그래밍 언어의 클래스 정의보다 유연하게 구성할 수 있습니다.
*   **"The client is always right" vs. "보내는 것은 보수적으로, 받는 것은 너그럽게":** 클라이언트의 잘못된 요청에 대해 너무 엄격하게 굴기보다는, 가능한 한 클라이언트의 요청을 수용하고 올바르게 처리하는 것이 더 나은 사용자 경험을 제공할 수 있습니다. (부모 노드 '데이터 전송 원칙' 참고)
*   **데이터 전송 원칙:** "보내는 데이터는 엄격하게, 받는 데이터는 유연하게" 원칙을 통해 안정성과 유연성을 모두 확보할 수 있습니다. (부모 노드 '데이터 전송 원칙' 참고)
*   **응답 데이터의 엄격한 검증:** 서버가 클라이언트에게 보내는 응답은 엄격한 검증을 통해 데이터 품질을 보장합니다.
*   **요청 데이터의 유연한 검증:** 클라이언트 요청은 유연하게 처리하여, 예외적인 입력에 대응하고 사용자 경험을 향상시킵니다.
*   **JSON Schema의 조립:** 맵처럼 구성되어 재사용 및 모듈화가 가능하다는 점을 강조합니다.

## 주요 화제
- **JSON Schema를 이용한 데이터 유효성 검사:** JSON Schema를 사용하여 데이터 구조를 정의하고 유효성을 검사하는 방법, 특히 검색 응답 및 데이터베이스 응답의 예시를 통해 보여줍니다.
- **필드 필수 여부 설정:** JSON Schema에서 필드를 필수(required)로 지정하는 방법과 기본적으로 모든 필드가 선택적(optional)이라는 점을 설명합니다.
- **Schema의 재사용 및 구성:** JSON Schema가 단순히 맵(map)이기 때문에 재사용 및 조립이 가능하다는 점을 강조하고, bookInfoSchema를 분리하여 searchBooksResponseSchema에서 사용하는 예시를 제시합니다.
- **외부 데이터 소스(데이터베이스) 데이터 유효성 검사:** 외부 데이터 소스에서 가져온 데이터의 유효성을 검사하는 중요성을 강조하고, 데이터베이스 응답의 예시와 함께 schema를 작성하는 방법을 설명합니다.
- **additionalProperties 필드:** JSON Schema에서 `additionalProperties` 필드를 사용하여 스키마에 정의되지 않은 추가적인 속성의 허용 여부를 제어하는 방법을 설명합니다. 기본적으로 추가적인 속성은 허용되며, `additionalProperties: false`로 설정하여 금지할 수 있습니다.
- **Strictness (엄격함)과 Flexibility (유연성)의 균형:** 요청(request)과 응답(response) 스키마에서 엄격함과 유연성을 조절하는 방법을 설명하고, 클라이언트의 요청은 유연하게, 서버의 응답은 엄격하게 처리하는 것이 좋다는 의견을 제시합니다. Jon Postel의 견고성 원칙(robustness principle)을 인용하며, "보내는 것은 보수적으로, 받는 것은 관대하게"를 강조합니다.

## 부차 화제
- JSON Schema에서의 필수 필드 지정: `required` 배열을 사용하여 필수 필드를 지정하는 방법. JSON Schema에서 맵 필드는 기본적으로 선택 사항임을 강조.
- JSON Schema의 재사용 및 구성: JSON Schema가 일반적인 맵(객체)이므로 다른 맵처럼 자유롭게 조립하고 조작할 수 있다는 점 (예: `bookInfoSchema`를 `searchBooksResponseSchema` 내에서 재사용).
- 외부 데이터 소스에서 받은 데이터의 유효성 검사: 데이터베이스 응답과 같은 외부 데이터 소스에서 받은 데이터를 검증하는 중요성 강조.
- `additionalProperties` 필드 사용: JSON Schema에서 정의되지 않은 추가 속성의 허용 여부를 제어하는 방법. 기본적으로 추가 속성은 허용되며, `additionalProperties: false`를 설정하여 금지.
- 요청과 응답에서의 `additionalProperties` 적용 전략: 요청(클라이언트)에서는 관대하게(추가 속성 허용), 응답(서버)에서는 엄격하게(추가 속성 금지) 사용하는 것이 좋은 관행임을 설명. "보내는 것은 보수적으로, 받는 것은 관대하게"라는 Jon Postel의 원칙 인용.
