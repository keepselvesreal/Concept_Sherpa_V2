## 7.3 Schema flexibility and strictness 상세 내용 정리

이 챕터는 JSON Schema를 사용하여 데이터의 유효성을 검사하는 방법과 관련된 주제를 다룬다. 특히 스키마의 유연성과 엄격함에 초점을 맞추어, 데이터 구조를 정의하고 검증하는 데 있어 다양한 상황에 맞는 접근 방식을 제시한다.

### 1. 기본 개념: 필수 필드와 선택적 필드

*   **JSON Schema에서의 기본:** JSON Schema에서 맵(객체) 내의 필드는 기본적으로 선택적이다.
*   **필수 필드 정의:** `required` 배열을 사용하여 필수 필드를 지정한다. 이 배열에 포함된 필드는 데이터 유효성 검사 시 반드시 존재해야 한다.

### 2. 스키마 재사용 및 구성

*   **JSON Schema의 유연성:** JSON Schema는 맵과 동일하게 취급되므로, 다른 맵처럼 자유롭게 구성하고 조작할 수 있다.
*   **스키마 분리:** 복잡한 스키마는 재사용 및 가독성을 위해 작은 단위로 분리하여 관리할 수 있다. 예를 들어, `bookInfoSchema`와 같이 책 정보 스키마를 별도로 정의한 후, 다른 스키마에서 참조하는 방식이다.

### 3. 외부 데이터 검증

*   **데이터 유효성 검사의 중요성:** 외부 데이터 소스(예: 데이터베이스)에서 가져온 데이터는 항상 유효성을 검사해야 한다. 이는 데이터 무결성을 보장하고 예상치 못한 오류를 방지하는 데 중요하다.
*   **데이터베이스 응답 스키마:** 데이터베이스 응답의 구조를 정의하는 스키마는 데이터의 필수 필드와 데이터 타입을 명시해야 한다.

### 4. `additionalProperties` 속성

*   **기본 동작:** JSON Schema에서 `additionalProperties` 속성을 명시하지 않으면, 스키마에 정의되지 않은 추가 필드가 허용된다.
*   **엄격한 검사:** `additionalProperties: false`를 설정하면, 스키마에 정의된 필드 외의 다른 필드는 허용되지 않도록 할 수 있다.

### 5. 유연성 vs. 엄격함: 실용적인 가이드라인

*   **데이터 송신(응답):** 서버에서 클라이언트로 전송하는 데이터는 엄격하게 검증하는 것이 좋다. (예: `additionalProperties: false`를 사용하여 불필요한 필드를 차단). 이는 데이터의 정확성을 보장하고 클라이언트 측의 예상치 못한 문제를 방지한다.
*   **데이터 수신(요청):** 클라이언트로부터 받는 데이터는 다소 유연하게 처리하는 것이 일반적이다. (예: `additionalProperties`를 설정하지 않거나 `true`로 설정). 이는 클라이언트의 편의성을 높이고, 호환성 문제를 최소화한다.
*   **Postel의 Robustness Principle:** "보내는 데이터는 보수적으로, 받는 데이터는 관대하게" 하는 것이 좋다.

## 7.3 Schema flexibility and strictness 추가 상세 정보 및 새로운 내용 정리

이 섹션은 JSON Schema의 유연성과 엄격성에 대한 내용을 다루며, 특히 데이터 검증과 관련하여 다음과 같은 세부 사항들을 추가적으로 제공합니다.

**1. JSON Schema의 기본 동작 및 설정:**

*   **Map Fields의 기본 동작:** JSON Schema에서 map (object) 내 필드는 기본적으로 선택적(optional)입니다. 이는 schema에 명시되지 않은 필드가 있어도 유효한 데이터로 간주됨을 의미합니다.
*   **필수 필드 지정:** 필드를 필수(required)로 만들기 위해서는 `required` 배열에 해당 필드를 명시해야 합니다.
    ```json
    {
      "type": "object",
      "required": ["title", "available"],
      "properties": {
        "title": {"type": "string"},
        "available": {"type": "boolean"},
        // ... other properties
      }
    }
    ```
*   **`additionalProperties` 설정:**  JSON Schema는 기본적으로 schema에 명시되지 않은 필드를 허용합니다.  `additionalProperties` 속성을 사용하여 이러한 동작을 변경할 수 있습니다.
    *   `additionalProperties: false`:  schema에 정의되지 않은 필드가 있는 경우 유효하지 않은 데이터로 간주합니다.  이는 데이터의 엄격한 검증을 위해 사용됩니다.
    *   `additionalProperties: true` (default): schema에 정의되지 않은 필드를 허용합니다.

**2. Schema의 재사용 및 구성 (composability):**

*   **Schema 분리 및 재사용:** JSON Schema는 단순한 맵(JSON 객체)이므로, 변수에 할당하여 재사용하거나 다른 schema에 포함시킬 수 있습니다. 이를 통해 schema를 모듈화하고 가독성을 높일 수 있습니다.
    ```javascript
    var bookInfoSchema = {
      "type": "object",
      "required": ["title", "available"],
      "properties": {
        "title": {"type": "string"},
        "available": {"type": "boolean"},
        // ... other properties
      }
    };

    var searchBooksResponseSchema = {
      "type": "array",
      "items": bookInfoSchema // bookInfoSchema를 재사용
    };
    ```

**3. 데이터 검증의 중요성과 적용:**

*   **외부 데이터 소스 데이터 검증:** 외부 데이터 소스 (예: 데이터베이스)에서 가져온 데이터는 항상 검증하는 것이 좋습니다. 이는 데이터 무결성을 보장하고 예기치 않은 오류를 방지하는 데 도움이 됩니다.
*   **검증 시기:** 외부 데이터 소스에서 데이터를 받은 직후에 검증을 수행합니다.
*   **데이터베이스 응답 schema 예시:**
    ```json
    {
      "type": "array",
      "items": {
        "type": "object",
        "required": ["title", "isbn", "available"],
        "properties": {
          "title": {"type": "string"},
          "isbn": {"type": "string"},
          "available": {"type": "boolean"}
        }
      }
    }
    ```

**4. 엄격함과 유연함의 균형:**

*   **요청 및 응답에서의 접근 방식:**
    *   **요청 (Requests):**  클라이언트가 생성하는 요청에 대해서는 더 유연하게 접근하는 것이 좋습니다. 이는 클라이언트가 다양한 방식으로 요청을 보낼 수 있도록 하고, 서버가 클라이언트의 요청을 처리할 수 있는 가능성을 높입니다.
    *   **응답 (Responses):**  서버가 생성하는 응답에 대해서는 더 엄격하게 접근하는 것이 좋습니다. 이는 서버가 정확하고 예상된 형식의 데이터를 클라이언트에 제공하도록 보장합니다.
*   **Jon Postel의 Robustness Principle:** "Be conservative in what you send, be liberal in what you accept."  이 원칙은 서버 설계에 있어서 중요한 지침이 될 수 있습니다.  서버는 보내는 데이터(응답)에 대해서는 엄격하게, 받는 데이터(요청)에 대해서는 유연하게 동작하는 것이 바람직합니다.

**5. 추가적인 예시 및 구체적인 구현 방법:**

*   **`dummy_property` 예시:**  schema에 정의되지 않은 `dummy_property`가 있는 데이터는 `additionalProperties`가 false로 설정된 schema에서는 유효하지 않습니다.
*   **`additionalProperties` 사용 시나리오:**
    *   **엄격한 데이터 구조 보장:** 응답 데이터의 정확한 형태를 보장해야 하는 경우.
    *   **보안:**  예상치 못한 데이터가 주입되는 것을 방지해야 하는 경우.
    *   **데이터베이스 스키마 일치:** 데이터베이스 스키마와 일치하는 데이터를 검증해야 하는 경우.
*   **Schema 리팩토링 예시:**  `bookInfoSchema`를 별도로 정의하여 `searchBooksResponseSchema`에서 재사용하는 방법은 schema를 더 깔끔하게 만들고 유지 보수를 용이하게 합니다.

**요약:**

이 섹션은 JSON Schema를 사용하여 데이터의 유효성을 검사하는 방법과, 데이터의 엄격함과 유연성 사이의 균형을 맞추는 방법을 설명합니다.  특히, `additionalProperties` 속성을 사용하여 데이터의 정확성을 보장하고, schema의 재사용성을 통해 코드의 가독성을 향상시키는 방법을 강조합니다.  또한, 외부 데이터 소스로부터 받은 데이터를 검증하는 중요성을 강조하며, 요청과 응답에 대한 서로 다른 접근 방식을 제안합니다.


## 주요 화제
- **JSON Schema를 이용한 데이터 유효성 검사:** JSON Schema를 사용하여 데이터 구조를 정의하고, 필드별 타입, 필수 여부, 추가 속성 허용 여부 등을 설정하여 데이터 유효성을 검사하는 방법.
- **스키마 유연성 (Schema Flexibility) vs. 엄격성 (Strictness):** JSON Schema에서 필드의 기본 동작(선택적 필드, 추가 속성 허용)과 엄격하게 데이터를 검사하기 위한 설정 (required, additionalProperties)에 대한 논의.
- **스키마 재사용 및 구성 (Schema Composition):** JSON Schema가 단순한 맵(map)이므로, 스키마를 재사용하고 조합하여 복잡한 데이터 구조를 정의하는 방법.
- **외부 데이터 소스 (External Data Sources) 데이터 검증:** 외부 데이터 (예: 데이터베이스 응답)를 검증하는 중요성과, 데이터 유효성 검증을 통해 얻는 이점.
- **요청 및 응답 스키마 설계의 엄격성:**  요청과 응답 스키마에 대한 엄격성 정도를 선택하는 기준 (응답은 엄격하게, 요청은 유연하게).
- **JSON Schema의 `additionalProperties` 사용법:** 스키마에 정의되지 않은 추가 속성의 허용 여부를 제어하는 `additionalProperties` 필드의 사용법 및 기본 동작.
- **"Be conservative in what you send, be liberal in what you accept" 원칙:** 데이터를 보낼 때는 엄격하게, 받을 때는 유연하게 접근하는 데이터 처리 원칙.


## 부차 화제
- JSON Schema에서 필드 필수 여부 설정: JSON Schema에서 맵 필드는 기본적으로 선택 사항이며, `required` 배열에 포함시켜 필수 필드로 지정할 수 있습니다.
- JSON Schema의 재사용성 및 조합성: JSON Schema는 일반적인 맵과 같이 조작하고 구성할 수 있으며, 다른 스키마에서 재사용하거나 중첩하여 사용할 수 있습니다.
- 외부 데이터 소스 데이터 유효성 검사: 외부 데이터 소스에서 받은 데이터는 유효성을 검사하는 것이 좋으며, JSON Schema를 사용하여 데이터 구조와 유형을 검증할 수 있습니다.
- `additionalProperties` 필드를 사용한 엄격한 스키마 설정: `additionalProperties` 필드를 사용하여 스키마에 정의되지 않은 추가 속성의 허용 여부를 제어할 수 있습니다. 기본적으로는 허용되지만, `false`로 설정하여 금지할 수 있습니다.
- 요청(request) 및 응답(response) 스키마의 유연성/엄격성: 일반적으로 서버는 응답에서 더 엄격하게, 요청에서는 더 유연하게 동작하는 것이 좋습니다. 이는 "보내는 것은 보수적으로, 받는 것은 관대하게"라는 원칙에 따릅니다.
- JSON Schema의 장점: 클래스 정의보다 간단하며, 재사용 및 조합이 용이합니다.

TIP In JSON Schema, by default, fields not specified in the schema of a map are

Theo Why is that?
Joe The reason is that usually having additional fields in a map doesn't cause
trouble. If your code doesn't care about a field, it simply ignores it. But some-
times we want to be as strict as possible, and we set additionalProperties
to false.
Theo What about the search request and response schema from the previous discus-
sions? Should we set additionalProperties to false?
Joe That's an excellent question. I'd say it's a matter of taste. Personally, I like to
allow additional fields in requests and disallow them in responses.
Theo What's the advantage?
Joe Well, the web server is responsible for the responses it sends to its clients. It
makes sense then to be as strict as possible. However, the requests are created
by the clients, and I prefer to do my best to serve my clients even when they are
not as strict as they should be.
Theo Naturally. "The client is always right."
Joe Actually, I prefer the way Jon Postel formulated his robustness principle: "Be
conservative in what you send, be liberal in what you accept."
TIP It's a good practice to be strict with the data that you send and to be flexible with
the data that you receive.
