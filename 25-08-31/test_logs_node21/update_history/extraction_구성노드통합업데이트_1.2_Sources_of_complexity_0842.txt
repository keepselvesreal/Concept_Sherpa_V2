**부모 노드 (1.2 Sources of complexity)의 업데이트된 내용:**
핵심 내용: 이 문서는 객체 지향 프로그래밍(OOP)의 복잡성 원인을 분석하고, 데이터 중심 프로그래밍(DOP)이 OOP의 복잡성을 완화할 수 있음을 제시한다. OOP에서는 코드와 데이터의 혼합, 객체의 가변성, 데이터 및 코드의 클래스 내 잠금 등이 복잡성을 증가시키는 요인으로 작용한다.
상세 핵심 내용: OOP는 시스템을 이해하기 어렵게 만드는 경향이 있으며, 이는 코드와 데이터의 혼합, 객체의 가변성, 데이터와 코드의 클래스 내 잠금으로 인해 발생한다. 코드와 데이터가 혼합되면 클래스 간의 관계가 증가하고, 객체가 가변적이면 코드 동작을 예측하기 어려워진다. 또한, 데이터가 객체 내에 잠겨 있으면 데이터 직렬화가 복잡해지고, 코드가 클래스 내에 잠겨 있으면 클래스 계층 구조가 복잡해진다. DOP는 이러한 OOP의 복잡성을 줄이기 위해 데이터와 코드를 분리하고, 데이터 불변성을 강조하며, 데이터에 대한 일반적인 접근 방식을 제공한다.
상세 정보: *   **OOP의 복잡성 원인**:
*   코드와 데이터의 혼합: 클래스 간의 관계를 증가시켜 시스템을 복잡하게 만든다. Member 클래스를 MemberCode와 MemberData로 분리하는 예시를 통해 설명한다.
*   객체의 가변성: 다중 스레드 환경에서 코드 동작을 예측하기 어렵게 만든다. isBlocked 상태를 두 번 출력하는 코드 예시를 통해 설명한다.
*   데이터 직렬화의 어려움: JSON 직렬화/역직렬화 과정에서 많은 클래스와 코드가 필요하게 만든다. /search 엔드포인트 구현 예시를 통해 설명한다.
*   복잡한 클래스 계층 구조: 새로운 요구사항 추가 시 기존 계층 구조를 변경해야 하는 어려움을 야기한다. VIP 멤버와 Super 멤버 추가 시 발생하는 문제점을 예시로 설명한다.
*   **DOP(Data-Oriented Programming)의 장점**:
*   코드와 데이터 분리: 시스템을 단순화하고 이해하기 쉽게 만든다.
*   데이터 불변성: 코드의 예측 가능성을 높여 개발자의 인지 부담을 줄인다.
*   일반적인 데이터 접근 방식: 데이터 직렬화/역직렬화를 효율적으로 처리할 수 있게 한다.
*   **OOP vs DOP**: DOP는 OOP와 호환 가능하며, OOP 시스템에서도 DOP 원칙을 적용하여 복잡성을 줄일 수 있다.
*   **주의 사항**: 복잡성과 단순성은 절대적인 개념이 아닌 상대적인 개념이다.

구성노드22 (1.2.1 Many relations between classes):
- 핵심 내용: 객체 지향 프로그래밍(OOP)에서 코드와 데이터가 혼합되어 있을 때 클래스 다이어그램이 복잡해지는 경향이 있다. 클래스를 코드와 데이터 엔티티로 분리하면 시스템이 단순해지고 이해하기 쉬워진다. 독립적인 하위 시스템으로 구성된 시스템은 단일 복잡 시스템보다 덜 복잡하다.
- 상세 핵심 내용: OOP에서는 코드와 데이터가 클래스 내에 혼합되어 있어 클래스 다이어그램이 복잡해지는 경향이 있다. 특히 클래스 간의 관계가 많아지면 시스템 분석이 어려워진다. Member 클래스를 예로 들어, 이를 MemberCode(코드)와 MemberData(데이터)로 분리하면 관련된 관계의 수가 줄어들어 시스템을 더 쉽게 이해할 수 있다. 모든 클래스를 코드와 데이터 엔티티로 분리하면 전체 시스템은 독립적인 코드 하위 시스템과 데이터 하위 시스템으로 나뉘어 각각 이해하기 쉬워진다. 따라서 코드와 데이터를 분리하는 것이 시스템 복잡성을 줄이는 효과적인 방법이다.
- 상세 정보: *   클래스 다이어그램의 복잡성을 평가하는 방법은 엔티티와 관계를 살펴보고 멤버와 메서드를 무시하는 것이다.
*   OOP에서 코드와 데이터는 클래스 내에 혼합되어 있으며, 이는 클래스가 많은 관계에 관여하게 되는 원인이 된다.
*   Member 클래스는 Library, BookLendings, User, Librarian, BookItem 과의 관계로 인해 복잡하다.
*   Member 클래스를 MemberCode와 MemberData로 분리하면 각 엔티티와 관련된 관계의 수가 줄어든다.
*   모든 클래스를 코드와 데이터 엔티티로 분리하면 시스템은 독립적인 코드 하위 시스템과 데이터 하위 시스템으로 구성된다.
*   독립적인 하위 시스템으로 구성된 시스템은 단일 복잡 시스템보다 이해하기 쉽다.
*   시스템을 단순하고 독립적인 부분으로 나누는 것은 시스템을 이해하기 쉽게 만든다.
*   코드와 데이터를 분리하는 것은 시스템 복잡성을 줄이는 논리적인 방법이다.

구성노드23 (1.2.2 Unpredictable code behavior):
- 핵심 내용: 객체지향 프로그래밍(OOP)에서 객체 멤버의 가변성으로 인해 발생하는 예측 불가능한 코드 동작을 설명한다. 특히, 멀티 스레드 환경에서 객체의 상태가 변경될 수 있어 동일한 코드가 다른 결과를 낼 수 있음을 지적하고, 데이터 불변성이 이러한 문제를 해결하고 DOP 개발자에게 안정감을 제공한다고 강조한다.
- 상세 핵심 내용: OOP에서 객체 멤버는 가변적이기 때문에, 멀티 스레드 환경에서 코드의 예측 불가능한 동작이 발생할 수 있다.  두 번의 console.log 호출 사이에 객체의 상태가 변경될 가능성이 있으며, 이는 concurrency safety mechanisms (뮤텍스 등)을 통해 해결할 수 있지만 성능 저하나 데드락 위험을 초래할 수 있다. 반면, DOP에서는 모든 데이터를 불변 값으로 취급하여 이러한 문제를 방지하고 개발자의 인지 부담을 줄인다.  데이터의 가변성은 코드의 예측 불가능성을 야기하며, 데이터 불변성은 DOP 개발자에게 안정감을 제공한다.
- 상세 정보: *   OOP에서 객체 멤버의 가변성으로 인해 코드 동작이 예측 불가능해질 수 있다.
*   싱글 스레드 환경에서는 예측 가능한 결과가 나오지만, 멀티 스레드 환경에서는 context switch로 인해 객체의 상태가 변경되어 다른 결과가 나올 수 있다.
*   자바스크립트와 같은 싱글 스레드 환경에서도 비동기 코드에 의해 데이터가 변경될 경우 예측 불가능한 동작이 발생할 수 있다.
*   primitive 타입은 일반적으로 immutable하지만, 객체 멤버는 mutable하다.
*   이러한 문제를 해결하기 위해 뮤텍스와 같은 concurrency safety mechanisms을 사용할 수 있지만, 성능 저하나 데드락 위험이 발생할 수 있다.
*   DOP에서는 모든 데이터를 immutable 값으로 취급하여 코드의 예측 가능성을 높이고 개발자의 부담을 줄인다.
*   데이터 불변성은 DOP 개발자에게 안정감을 제공한다.

구성노드24 (1.2.3 Not trivial data serialization):
- 핵심 내용: 이 문서는 객체 지향 프로그래밍(OOP)에서 JSON 데이터 직렬화의 어려움을 지적한다. Theo의 꿈을 통해 /search 엔드포인트 구현 시 반복되는 클래스 생성 및 코드 작성을 예시로 보여주며, 데이터가 클래스 멤버에 갇혀 있어 일반적인 접근이 어렵다는 점을 강조한다.
- 상세 핵심 내용: Theo의 꿈에서 Nancy는 Klafim의 도서관 관리 시스템을 JSON을 사용하는 REST API로 접근 가능하게 해달라고 요청한다. Theo는 /search 엔드포인트를 구현해야 하며, 이는 JSON 형식의 쿼리를 받아 JSON 형식으로 결과를 반환해야 한다. 하지만 OOP 환경에서 새로운 엔드포인트가 추가될 때마다 JSON 직렬화 및 역직렬화를 위한 새로운 클래스를 생성하고 동일한 코드를 반복해야 하는 문제가 발생한다. 데이터는 클래스 내부에 고정되어 있어 일반적인 접근이 어려우며, 이는 OOP에서 데이터 직렬화를 어렵게 만드는 주요 원인이다. 다른 프로그래밍 패러다임인 DOP에서는 JSON 직렬화 및 역직렬화를 보다 쉽게 처리할 수 있음을 암시하며, 독자들에게 OOP의 어려움을 인지하고 다른 대안을 고려하도록 유도한다.
- 상세 정보: *   Theo는 꿈에서 Nancy의 요청으로 Klafim의 도서관 관리 시스템에 대한 REST API를 구현해야 한다.
*   /search 엔드포인트는 JSON 형식의 쿼리를 입력받아 검색 결과를 JSON 형식으로 반환해야 한다.
*   OOP 방식으로 /search 엔드포인트를 구현하기 위해 SearchController, SearchQuery, SearchResult 클래스가 필요하다.
*   새로운 엔드포인트 (/add-book-item)를 추가할 때마다 유사한 구조의 AddBookItemController, BookItemQuery, BookItemResult 클래스를 생성하고 코드를 반복해야 한다.
*   OOP에서 데이터는 클래스의 멤버로 고정되어 있어 일반적인 접근이 어렵다.
*   JSON 직렬화 및 역직렬화는 데이터 필드를 반복하고, 필드 이름과 값을 쉼표로 구분하여 연결하는 간단한 과정이지만, OOP에서는 많은 클래스와 코드 작성이 필요하다.
*   대부분의 OOP 프로그래밍 언어는 JSON 변환의 어려움을 완화하기 위해 리플렉션 또는 코드 장황성을 사용한다.
*   DOP(Data-Oriented Programming)는 JSON 직렬화 및 역직렬화를 위한 일반적인 접근 방식을 제공할 수 있다.

구성노드25 (1.2.4 Complex class hierarchies):
- 핵심 내용: 이 문서는 객체 지향 프로그래밍(OOP)에서 클래스 상속의 문제점을 지적하고, 새로운 요구사항 추가 시 발생하는 복잡성을 보여준다. 특히, VIP 멤버와 Super 멤버 기능 추가 과정에서 클래스 상속으로 인해 발생하는 문제점과, 그 대안으로 컴포지션의 활용을 제시한다.
- 상세 핵심 내용: 이 문서는 OOP에서 초기 설계 시 예상치 못한 요구사항 변경이 발생할 경우, 클래스 상속 기반의 설계가 얼마나 취약해질 수 있는지를 보여준다. VIP 멤버와 Super 멤버 기능 추가 요구사항이 발생했을 때, 기존의 Librarian 클래스의 코드를 재사용하기 어렵고, 다중 상속으로 인한 "Deadly Diamonds of Death" 문제가 발생한다. Theo는 마감 기한에 쫓기며 시스템의 복잡성을 감당하지 못하고, 결국 Super 멤버 기능을 추가하지 못한다. 이 사례를 통해 클래스 상속보다는 컴포지션을 사용하는 것이 더 유연한 해결책임을 강조한다.
- 상세 정보: *   OOP에서 클래스 상속은 코드 재사용을 위한 방법이지만, 시스템 요구사항이 변경될 경우 복잡성을 증가시킬 수 있다.
*   VIP 멤버 기능 추가 요구사항은 Librarian 클래스의 addBookItem 기능을 재사용해야 하지만, 클래스 상속 구조로 인해 어려움을 겪는다.
*   다중 상속으로 인해 "Deadly Diamonds of Death" 문제가 발생하여 시스템의 복잡성이 증가한다.
*   Super 멤버 기능 추가 요구사항은 시스템의 복잡성을 더욱 가중시켜 개발자가 마감 기한 내에 완료하지 못하게 만든다.
*   컴포지션은 클래스 상속의 대안으로 제시되며, 더 유연하고 유지보수가 용이한 설계를 가능하게 한다.
*   마감 기한에 쫓기는 상황에서 개발자는 최적의 설계를 하지 못할 수 있으며, 이는 시스템의 품질 저하로 이어질 수 있다.
*   요구사항 변경에 대한 유연한 대처가 가능한 설계의 중요성이 강조된다.

## 핵심 내용
객체 지향 프로그래밍(OOP)에서 코드와 데이터의 혼합은 클래스 간의 관계를 증가시켜 클래스 다이어그램을 복잡하게 만들고 시스템 이해를 어렵게 한다. 데이터 중심 프로그래밍(DOP)의 원칙에 따라 클래스를 코드와 데이터 엔티티로 분리하면 시스템이 단순해지고 이해하기 쉬워진다.

## 상세 핵심 내용
OOP에서는 코드와 데이터가 클래스 내에 혼합되어 있어 클래스 다이어그램이 복잡해지는 경향이 있으며, 특히 클래스 간의 관계가 많아지면 시스템 분석이 어려워진다. Member 클래스를 예로 들어, 이를 MemberCode(코드)와 MemberData(데이터)로 분리하면 관련된 관계의 수가 줄어들어 시스템을 더 쉽게 이해할 수 있다. 코드와 데이터 분리는 독립적인 코드 하위 시스템과 데이터 하위 시스템을 구성하여, 전체 시스템을 더 이해하기 쉽게 만들고 복잡성을 줄이는 효과적인 방법이다. 이러한 접근 방식은 DOP의 핵심 원칙을 반영한다.

## 상세 정보
*   클래스 다이어그램의 복잡성을 평가하는 방법은 엔티티와 관계를 살펴보고 멤버와 메서드를 무시하는 것이다.
*   OOP에서 코드와 데이터는 클래스 내에 혼합되어 있으며, 이는 클래스가 많은 관계에 관여하게 되는 원인이 된다. Member 클래스는 Library, BookLendings, User, Librarian, BookItem 과의 관계로 인해 복잡하다.
*   Member 클래스를 MemberCode와 MemberData로 분리하면 각 엔티티와 관련된 관계의 수가 줄어든다.
*   모든 클래스를 코드와 데이터 엔티티로 분리하면 시스템은 독립적인 코드 하위 시스템과 데이터 하위 시스템으로 구성된다.
*   독립적인 하위 시스템으로 구성된 시스템은 단일 복잡 시스템보다 이해하기 쉽다.
*   시스템을 단순하고 독립적인 부분으로 나누는 것은 시스템을 이해하기 쉽게 만든다.
*   코드와 데이터를 분리하는 것은 시스템 복잡성을 줄이는 논리적인 방법이며, 이는 DOP의 중요한 특징이다.

## 핵심 내용
객체 지향 프로그래밍(OOP)에서 객체 멤버의 가변성은 예측 불가능한 코드 동작의 주요 원인이다. 특히, 멀티 스레드 환경에서 객체의 상태가 변경될 수 있어 동일한 코드가 다른 결과를 낼 수 있다. 데이터 불변성을 강조하는 데이터 중심 프로그래밍(DOP)은 이러한 문제를 해결하고 개발자에게 안정감을 제공한다.

## 상세 핵심 내용
OOP에서 객체 멤버는 가변적이기 때문에, 멀티 스레드 환경에서 코드의 예측 불가능한 동작이 발생할 수 있다. 두 번의 console.log 호출 사이에 객체의 상태가 변경될 가능성이 있으며, 이는 concurrency safety mechanisms (뮤텍스 등)을 통해 해결할 수 있지만 성능 저하나 데드락 위험을 초래할 수 있다. 반면, DOP에서는 모든 데이터를 불변 값으로 취급하여 이러한 문제를 방지하고 개발자의 인지 부담을 줄인다. 데이터의 가변성은 코드의 예측 불가능성을 야기하며, 데이터 불변성은 DOP 개발자에게 안정감을 제공하며, OOP의 복잡성을 완화하는 데 기여한다.

## 상세 정보
*   OOP에서 객체 멤버의 가변성으로 인해 코드 동작이 예측 불가능해질 수 있다.
*   싱글 스레드 환경에서는 예측 가능한 결과가 나오지만, 멀티 스레드 환경에서는 context switch로 인해 객체의 상태가 변경되어 다른 결과가 나올 수 있다.
*   자바스크립트와 같은 싱글 스레드 환경에서도 비동기 코드에 의해 데이터가 변경될 경우 예측 불가능한 동작이 발생할 수 있다.
*   primitive 타입은 일반적으로 immutable하지만, 객체 멤버는 mutable하다.
*   이러한 문제를 해결하기 위해 뮤텍스와 같은 concurrency safety mechanisms을 사용할 수 있지만, 성능 저하나 데드락 위험이 발생할 수 있다.
*   DOP에서는 모든 데이터를 immutable 값으로 취급하여 코드의 예측 가능성을 높이고 개발자의 부담을 줄인다.
*   데이터 불변성은 DOP 개발자에게 안정감을 제공하며, 이는 OOP의 복잡성 문제를 해결하는 데 중요한 역할을 한다.

구성노드24:
## 핵심 내용
객체 지향 프로그래밍(OOP)에서 JSON 데이터 직렬화는 데이터가 클래스 멤버에 갇혀 있어 일반적인 접근이 어렵기 때문에 복잡해진다. 데이터 중심 프로그래밍(DOP)은 이러한 OOP의 복잡성을 완화하기 위해 데이터에 대한 일반적인 접근 방식을 제공하며, JSON 직렬화를 더 효율적으로 처리할 수 있게 한다.

## 상세 핵심 내용
Theo의 꿈에서 Nancy는 Klafim의 도서관 관리 시스템을 JSON을 사용하는 REST API로 접근 가능하게 해달라고 요청한다. Theo는 /search 엔드포인트를 구현해야 하며, 이는 JSON 형식의 쿼리를 받아 JSON 형식으로 결과를 반환해야 한다. 하지만 OOP 환경에서 새로운 엔드포인트가 추가될 때마다 JSON 직렬화 및 역직렬화를 위한 새로운 클래스를 생성하고 동일한 코드를 반복해야 하는 문제가 발생한다. 데이터는 클래스 내부에 고정되어 있어 일반적인 접근이 어려우며, 이는 OOP에서 데이터 직렬화를 어렵게 만드는 주요 원인이다. DOP에서는 데이터와 코드를 분리하고 데이터에 대한 일반적인 접근 방식을 제공함으로써 JSON 직렬화 및 역직렬화를 보다 쉽게 처리할 수 있다.

## 상세 정보
*   Theo는 꿈에서 Nancy의 요청으로 Klafim의 도서관 관리 시스템에 대한 REST API를 구현해야 한다.
*   /search 엔드포인트는 JSON 형식의 쿼리를 입력받아 검색 결과를 JSON 형식으로 반환해야 한다.
*   OOP 방식으로 /search 엔드포인트를 구현하기 위해 SearchController, SearchQuery, SearchResult 클래스가 필요하다.
*   새로운 엔드포인트 (/add-book-item)를 추가할 때마다 유사한 구조의 AddBookItemController, BookItemQuery, BookItemResult 클래스를 생성하고 코드를 반복해야 한다.
*   OOP에서 데이터는 클래스의 멤버로 고정되어 있어 일반적인 접근이 어렵다.
*   JSON 직렬화 및 역직렬화는 데이터 필드를 반복하고, 필드 이름과 값을 쉼표로 구분하여 연결하는 간단한 과정이지만, OOP에서는 많은 클래스와 코드 작성이 필요하다.
*   대부분의 OOP 프로그래밍 언어는 JSON 변환의 어려움을 완화하기 위해 리플렉션 또는 코드 장황성을 사용한다.
*   DOP(Data-Oriented Programming)는 JSON 직렬화 및 역직렬화를 위한 일반적인 접근 방식을 제공할 수 있으며, OOP의 데이터 직렬화 문제를 완화한다.

구성노드25:
## 핵심 내용
객체 지향 프로그래밍(OOP)에서 클래스 상속은 초기 설계 시 예상치 못한 요구사항 변경에 취약하며, 새로운 요구사항 추가 시 복잡성을 증가시킬 수 있다. 데이터 중심 프로그래밍(DOP)은 OOP와 호환 가능하며, OOP 시스템에서도 DOP 원칙을 적용하여 이러한 복잡성을 줄일 수 있다.

## 상세 핵심 내용
이 문서는 OOP에서 초기 설계 시 예상치 못한 요구사항 변경이 발생할 경우, 클래스 상속 기반의 설계가 얼마나 취약해질 수 있는지를 보여준다. VIP 멤버와 Super 멤버 기능 추가 요구사항이 발생했을 때, 기존의 Librarian 클래스의 코드를 재사용하기 어렵고, 다중 상속으로 인한 "Deadly Diamonds of Death" 문제가 발생한다. Theo는 마감 기한에 쫓기며 시스템의 복잡성을 감당하지 못하고, 결국 Super 멤버 기능을 추가하지 못한다. 이 사례를 통해 클래스 상속보다는 컴포지션을 사용하는 것이 더 유연한 해결책임을 강조하며, OOP 시스템에서도 DOP 원칙을 적용하여 복잡성을 줄일 수 있음을 시사한다.

## 상세 정보
*   OOP에서 클래스 상속은 코드 재사용을 위한 방법이지만, 시스템 요구사항이 변경될 경우 복잡성을 증가시킬 수 있다.
*   VIP 멤버 기능 추가 요구사항은 Librarian 클래스의 addBookItem 기능을 재사용해야 하지만, 클래스 상속 구조로 인해 어려움을 겪는다.
*   다중 상속으로 인해 "Deadly Diamonds of Death" 문제가 발생하여 시스템의 복잡성이 증가한다.
*   Super 멤버 기능 추가 요구사항은 시스템의 복잡성을 더욱 가중시켜 개발자가 마감 기한 내에 완료하지 못하게 만든다.
*   컴포지션은 클래스 상속의 대안으로 제시되며, 더 유연하고 유지보수가 용이한 설계를 가능하게 한다.
*   마감 기한에 쫓기는 상황에서 개발자는 최적의 설계를 하지 못할 수 있으며, 이는 시스템의 품질 저하로 이어질 수 있다.
*   요구사항 변경에 대한 유연한 대처가 가능한 설계의 중요성이 강조된다. OOP 시스템에서도 DOP 원칙을 활용하여 이러한 유연성을 확보할 수 있다.
