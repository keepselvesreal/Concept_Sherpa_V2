## 핵심 내용
이 문서는 객체 지향 프로그래밍(OOP)에서 클래스 상속을 사용할 때 발생하는 복잡성과 문제점을 설명합니다. 특히, 요구 사항 변경에 유연하게 대응하기 어렵고, 다중 상속으로 인해 발생하는 '다이아몬드 문제'와 같은 문제점을 보여줍니다. 최종적으로는 상속보다 컴포지션을 사용하는 것이 더 나은 방법임을 강조합니다.

## 상세 핵심 내용
OOP에서 코드 재사용을 위해 클래스 상속을 사용하는 경우, 새로운 요구 사항이 추가되면 기존 코드 수정이 어렵고 클래스 계층 구조가 복잡해질 수 있습니다. VIP 멤버와 Super 멤버를 추가하는 과정에서 VIPMember와 SuperMember 클래스를 설계하는 어려움을 보여줍니다. 특히, 다중 상속으로 인해 발생하는 '다이아몬드 문제'는 코드의 모호성을 증가시키고 시스템의 복잡성을 더욱 증폭시킵니다. 결국, 이 문서에서는 상속 대신 컴포지션을 사용하여 유연하고 유지보수 가능한 코드를 작성하는 것이 중요하다고 강조합니다. 또한, 급하게 기능을 추가하는 것이 시스템 개발에 미치는 영향에 대해서도 언급합니다.

## 상세 정보

*   **상속의 문제점:**
    *   코드 재사용을 위해 상속 사용 시, 새로운 요구 사항 추가에 유연하지 못함
    *   Librarian::addBookItem 코드를 VIPMember에서 재사용하는 문제
    *   VIP 멤버와 Super 멤버를 추가하는 과정에서 클래스 구조가 복잡해짐
    *   다중 상속으로 인한 다이아몬드 문제 발생 (모호성 증가)
*   **해결 방안:**
    *   UserWithBookItemRight 클래스 도입 (addBookItem 메서드 이동)
    *   상속 대신 컴포지션 사용 (권장)
*   **사례:**
    *   VIP 멤버 추가: Member 클래스 상속, add book item 권한 문제
    *   Super 멤버 추가: SuperMember 추가, 다이아몬드 문제 발생
*   **결론:** 상속보다는 컴포지션이 더 나은 해결책

One way to avoid writing the same code twice in OOP involves class inheritance. Indeed,
when every requirement of the system is known up front, you design your class hier-

 Figure 1.15 shows an example of this pattern that focuses on the part of our class
diagram that deals with members and librarians. Both Librarians and Members need

So far, so good, but when new requirements are introduced after the system is imple-

where two days are left before the deadline (Wednesday at midnight).
