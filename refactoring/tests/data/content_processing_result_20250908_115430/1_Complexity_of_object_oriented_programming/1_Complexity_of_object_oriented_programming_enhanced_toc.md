# 1 Complexity of object- oriented programming
## 핵심 내용
이 문서는 객체 지향 프로그래밍의 복잡성에 대해 다루고 있습니다. 객체 지향 프로그래밍의 복잡성을 분석하고, 이해하기 어려운 부분을 파악하여 프로그래밍 생산성 향상에 기여하는 것을 목표로 합니다.

## 상세 핵심 내용
객체 지향 프로그래밍은 코드 재사용성과 유지보수성을 높이는 장점이 있지만, 클래스, 객체, 상속, 다형성 등 다양한 개념으로 인해 복잡성이 증가합니다. 특히, 디자인 패턴과 프레임워크를 사용할 경우, 복잡성은 더욱 심화될 수 있습니다. 이 문서는 이러한 복잡성을 분석하고, 개발자들이 객체 지향 프로그래밍의 어려운 부분을 효과적으로 이해하고 활용할 수 있도록 돕는 것을 목표로 합니다. 복잡성을 줄이기 위한 방법, 예를 들어 코드 구조 개선, 적절한 디자인 패턴 선택, 그리고 린(Lean) 개발 방법론의 적용 등을 제시할 수 있을 것입니다. 이러한 노력은 결과적으로 개발 생산성을 향상시키고, 유지보수 비용을 절감하는 데 기여할 수 있습니다.

### 1.1.2 UML 101
## 핵심 내용
이 문서는 UML 다이어그램의 기본 개념들을 설명하며, 특히 클래스 다이어그램을 중심으로 다양한 관계(composition, association, inheritance, usage)를 소개한다. 객체 지향 프로그래밍(OOP)의 복잡성을 이해하고, UML 다이어그램을 통해 시스템의 구조를 시각적으로 표현하는 방법을 제시한다.

## 상세 핵심 내용
문서는 UML 다이어그램의 종류와 각 관계의 의미를 설명한다. composition은 객체가 다른 객체를 소유하며, 소유 객체가 사라지면 함께 사라지는 관계를 의미한다. association은 객체가 독립적인 생명주기를 가지며 서로 연관된 관계를 나타낸다. inheritance는 상속 관계를 의미하며, 사용 관계는 한 클래스가 다른 클래스의 메서드를 호출하는 경우를 나타낸다. 또한, 다이어그램에서 각 관계를 나타내는 기호(다이아몬드, 화살표 등)를 설명하고, 다양한 예시를 통해 이해를 돕는다.

## 상세 정보
*   **문서 제목:** 18 lev3 1.1.2 UML 101
*   **챕터:** 1.1.2 UML 101, 1.1 OOP design: Classic or classical?, 1.1.3 Explaining each piece of the class diagram
*   **주요 개념:**
*   UML 다이어그램 (클래스 다이어그램)
*   객체 지향 프로그래밍 (OOP)
*   Composition (소유 관계): 한 객체가 다른 객체를 소유하며, 소유 객체가 사라지면 함께 사라짐.
*   Association (연관 관계): 객체들이 독립적인 생명주기를 가지며 서로 연관됨.
*   Inheritance (상속 관계): 한 클래스가 다른 클래스를 상속받음.
*   Usage (사용 관계): 한 클래스가 다른 클래스의 메서드를 호출함.
*   **관계 및 기호:**
*   Composition: plain diamond (one-to-one or one-to-many)
*   Association: empty diamond at both edges (many-to-many)
*   Inheritance: plain arrow with an empty triangle
*   Usage: dashed arrow
*   **예시:**
*   Library와 Catalog: one-to-one composition
*   Library와 Member: one-to-many composition
*   Book과 Author: many-to-many association
*   Librarian::blockMember() 호출 Member::block() : usage
*   Member와 User: inheritance

## 주요 화제
*   UML 다이어그램 소개
*   클래스 다이어그램의 기본 요소 (클래스, 속성, 메서드)
*   다양한 관계 (Composition, Association, Inheritance, Usage) 설명
*   객체 지향 프로그래밍 (OOP) 개념
*   UML 다이어그램을 이용한 시스템 구조 시각화

### 1.1.3 Explaining each piece of the class diagram
## 핵심 내용
이 문서는 클래스 다이어그램의 각 구성 요소를 설명하고, 라이브러리 시스템을 구성하는 다양한 클래스들의 역할과 관계를 자세히 설명합니다. 특히 `Library`, `User`, `Member`, `Librarian`, `Catalog`, `Book`, `BookItem` 클래스를 중심으로 객체 지향 프로그래밍(OOP) 설계 개념을 소개합니다. 각 클래스의 데이터 멤버와 코드(행동)를 설명하며, 클래스 간의 상속, 연관 관계, 그리고 메서드들을 구체적으로 제시합니다.

## 상세 핵심 내용
문서는 라이브러리 시스템의 루트 클래스인 `Library`에서 시작하여, `Member`, `Librarian` 클래스가 `User` 클래스를 상속받는 구조를 설명합니다. 각 클래스는 데이터 멤버(id, email, password 등)와 메서드(login, checkout, returnBook 등)를 가지며, 다른 클래스와의 관계를 통해 기능을 수행합니다. `Catalog` 클래스는 책 관리를 담당하며 `Book` 객체를 소유하고, `BookItem` 클래스는 책의 개별 복사본을 나타냅니다. 각 클래스들의 역할과 책임을 명확히 정의하고, 클래스 간의 상호작용을 통해 라이브러리 시스템이 어떻게 작동하는지 보여줍니다. 예를 들어, `Member`는 `checkout`을 통해 책을 대여하고, `Librarian`은 `blockMember`를 통해 회원을 차단할 수 있습니다.

## 상세 정보
### Library 클래스
*   라이브러리 시스템의 루트 클래스
*   데이터: Multiple Member objects, Multiple Librarian objects, A single Catalog object
*   행동(Code): 자체적으로는 아무것도 하지 않고, 소유한 객체에 위임
### User 클래스
*   라이브러리 사용자 표현
*   데이터: id, email, password
*   행동(Code): login()
### Member 클래스
*   라이브러리 회원 표현, User 클래스 상속
*   데이터: User의 데이터 멤버 상속
*   행동(Code): checkout(), returnBook(), block(), unblock(), isBlocked()
*   소유: Multiple BookLending objects
*   사용: BookItem (checkout 구현)
### Librarian 클래스
*   사서 표현, User 클래스 상속
*   데이터: User의 데이터 멤버 상속
*   행동(Code): blockMember(), unblockMember(), addBookItem(), getBookLendings()
*   사용: Member (blockMember, unblockMember, getBookLendings 구현), BookItem (checkout 구현), BookLending (getBookLendings 구현)
### Catalog 클래스
*   책 관리 담당
*   데이터: Multiple Book objects
*   행동(Code): search(), addBookItem()
*   사용: Librarian (addBookItem 구현)
### Book 클래스
*   책 표현
*   데이터: id, title
*   연관: Multiple Author objects
*   소유: Multiple BookItem objects
### BookItem 클래스
*   책의 복사본 표현
*   데이터: id, libId
*   소유: Multiple BookLending objects
*   행동(Code): checkout

## 핵심 내용

## 상세 핵심 내용
OOP에서 클래스 간의 복잡성은 다양한 관계 때문에 발생합니다. 코드와 데이터가 혼합되어 있어 엔티티가 여러 관계에 연루되기 때문입니다. Member 클래스를 예로 들어, 데이터와 코드 관계를 각각 분리하면 시스템의 복잡성을 줄일 수 있습니다. MemberCode와 MemberData로 분리하는 것이 그 예시입니다. 결과적으로, 독립적인 서브 시스템으로 구성된 시스템은 단일한 복잡한 시스템보다 이해하기 쉽습니다. 이와 같은 분리는 시스템을 단순화하는 논리적인 방법입니다.

*   코드와 데이터가 혼합되어 엔티티가 많은 관계에 연루되어 시스템이 복잡해짐
*   Member 클래스 예시: 5개의 관계 (2개의 데이터, 3개의 코드 관계)

*   코드와 데이터를 분리하면 시스템이 단순해짐

### 1.2.4 Complex class hierarchies
## 핵심 내용
이 문서는 객체 지향 프로그래밍(OOP)에서 클래스 상속을 사용할 때 발생하는 복잡성과 문제점을 설명합니다. 특히, 요구 사항 변경에 유연하게 대응하기 어렵고, 다중 상속으로 인해 발생하는 '다이아몬드 문제'와 같은 문제점을 보여줍니다. 최종적으로는 상속보다 컴포지션을 사용하는 것이 더 나은 방법임을 강조합니다.

## 상세 핵심 내용
OOP에서 코드 재사용을 위해 클래스 상속을 사용하는 경우, 새로운 요구 사항이 추가되면 기존 코드 수정이 어렵고 클래스 계층 구조가 복잡해질 수 있습니다. ## 상세 핵심 내용
문서는 OOP 시스템의 복잡성이 코드와 데이터의 혼합, 데이터의 가변성, 클래스 계층 구조의 복잡성, 데이터 직렬화의 어려움 등과 관련이 있음을 설명합니다. OOP에서 코드와 데이터가 섞여 있으면 클래스 간의 관계가 복잡해지고, 데이터가 변경 가능하면 코드의 동작 예측이 어려워집니다.
