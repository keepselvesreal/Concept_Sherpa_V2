## 핵심 내용
객체 지향 프로그래밍(OOP)에서 클래스 상속은 코드 재사용을 위한 일반적인 방법이지만, 새로운 요구사항이 추가될 때 복잡성을 증가시킬 수 있습니다. 특히 VIP 멤버 및 Super 멤버와 같은 새로운 기능을 추가하는 과정에서 상속 기반의 클래스 계층 구조는 "다이아몬드 문제"와 같은 복잡한 문제로 이어질 수 있으며, 결국 기한 내에 시스템을 완성하는 것을 어렵게 만듭니다.

## 상세 핵심 내용
OOP에서 코드 재사용을 위해 클래스 상속을 사용하는 것은 일반적이지만, 새로운 요구사항이 생길 때 클래스 계층 구조가 복잡해지는 문제가 발생합니다. VIP 멤버 기능을 추가하기 위해 기존의 Member 클래스를 상속받는 VIPMember 클래스를 만들고, addBookItem 기능을 추가하려 했으나, Librarian 클래스에 코드가 묶여 있어 문제가 발생했습니다. 해결책으로 UserWithBookItemRight 클래스를 추가하고, VIPMember와 Librarian이 이를 상속받도록 구조를 변경했지만 "다이아몬드 문제"가 발생하여 시스템 복잡성을 증가시켰습니다. Super 멤버 기능을 추가하려 하자 더욱 복잡해져 결국 기한 내에 시스템을 완성하지 못하게 되었고, 컴포지션(composition)을 상속보다 선호하는 것이 좋다는 교훈을 얻습니다.

## 상세 정보
*   **문제 상황:** 시스템에 VIP 멤버 및 Super 멤버 기능을 추가하는 과정에서 클래스 상속으로 인한 복잡성 증가.
*   **OOP의 문제점:** 코드의 클래스 내 캡슐화로 인한 재사용성 제한, 새로운 기능 추가 시 클래스 계층 구조 복잡화.
*   **해결 시도:** VIP 멤버 추가를 위해 UserWithBookItemRight 클래스 도입 및 다이아몬드 문제 발생. Super 멤버 추가 시도, 시스템의 복잡성 증가 및 기한 내 완료 실패.
*   **결론:** 상속 대신 컴포지션을 활용하여 클래스 계층 구조의 복잡성을 줄이는 것이 중요함.

## 주요 화제

when every requirement of the system is known up front, you design your class hier-
