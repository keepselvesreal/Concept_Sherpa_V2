## 상세 정보
## 1.1 OOP design: Classic or classical? - 문서 상세 정보 정리

**1. 개요**

*   **제목:** 1.1 OOP design: Classic or classical?
*   **주제:** 객체 지향 프로그래밍(OOP) 설계 및 UML 다이어그램 소개
*   **주요 등장인물:**
    *   **Theo:** 소프트웨어 컨설팅 회사 Albatross의 선임 기술 리드, Klafim 프로젝트 담당.
    *   **Dave:** Albatross의 주니어 소프트웨어 개발자.
    *   **Monica:** Theo의 상사.
*   **배경:** Albatross의 Klafim Global Library Management System 프로젝트를 위한 OOP 설계를 진행하는 과정.

**2. 상황 및 목표**

*   Theo는 Klafim Global Library Management System의 설계를 완료하고, 이를 바탕으로 코딩을 시작하려 함.
*   Dave는 Theo의 설계에 대한 질문을 통해 OOP 설계 능력을 향상시키려 함.

**3. 구성 노드 별 상세 정보**

**3.1. 구성 노드 1 (1.1.1 The design phase)**

*   **내용:**
    *   Theo는 Klafim Global Library Management System의 요구 사항을 파악하고 UML 클래스 다이어그램을 작성.
    *   설계는 두 종류의 사용자(도서관 회원, 사서) 및 도서관 시스템의 주요 기능들을 반영.
    *   Theo는 설계 과정에서 클래스 간의 관계를 정의하고, 설계 초안을 완성.
    *   설계는 naive한 OOP 설계를 의도, 코딩 시작을 위한 충분한 정보를 제공하고 전형적인 OOP 시스템의 복잡성을 보여주는 목적.
    *   Dave와의 만남을 통해 설계를 공유하고, OOP 설계에 대한 대화를 시작.
*   **주요 클래스:**
    *   Library
    *   Book
    *   BookItem
    *   BookLending
    *   Member
    *   Librarian
    *   User
    *   Catalog
    *   Author

**3.2. 구성 노드 2 (1.1.2 UML 101)**

*   **내용:**
    *   Theo는 Dave에게 UML 클래스 다이어그램을 설명.
    *   UML 다이어그램의 주요 화살표 종류(composition, association, inheritance, usage)와 의미 설명.
    *   **Composition:** 객체의 생명주기가 종속됨 (한 객체가 죽으면 다른 객체도 죽음).
        *   one-to-one composition (Library - Catalog)
        *   one-to-many composition (Library - Member)
    *   **Association:** 객체의 생명주기가 독립적임 (다대다 관계).
        *   many-to-many association (Book - Author)
    *   **Usage:** 한 클래스가 다른 클래스의 메서드를 호출.
    *   **Inheritance:** 클래스 상속.
*   **UML 다이어그램 요소:**
    *   Composition: plain diamond
    *   Association: empty diamond
    *   Usage: dashed arrow
    *   Inheritance: plain arrow with empty triangle

**3.3. 구성 노드 3 (1.1.3 Explaining each piece of the class diagram)**

*   **내용:**
    *   Theo는 각 클래스에 대한 상세 설명을 제공.
    *   **Library:** 시스템의 root 클래스, Member, Librarian, Catalog 객체를 소유.
    *   **User:** id, email, password, login() 메서드.
    *   **Member:** User 클래스 상속, checkout(), returnBook(), block(), unblock(), isBlocked() 메서드, BookLending 객체 소유, BookItem 사용.
    *   **Librarian:** User 클래스 상속, blockMember(), unblockMember(), getBookLendings(), addBookItem() 메서드, Member, BookItem, BookLending 사용.
    *   **Catalog:** search(), addBookItem() 메서드, Librarian 사용, Book 객체 소유.
    *   **Book:** id, title, Author 객체와 연관, BookItem 객체 소유.
    *   **BookItem:** id, libId, BookLending 객체 소유, checkout() 메서드.

**3.4. 구성 노드 4 (1.1.4 The implementation phase)**

*   **내용:**
    *   Dave는 Theo의 설계를 칭찬하고, 설계의 중요성을 인식.
    *   Theo는 코딩 전에 설계를 상세히 하는 것이 시간 절약에 도움이 된다고 강조.
    *   Theo는 코딩을 시작하기 위해 커피를 마시려고 함.

**4. 핵심 개념 및 용어**

*   **OOP (Object-Oriented Programming):** 객체 지향 프로그래밍.
*   **UML (Unified Modeling Language):** 소프트웨어 시스템의 구조를 시각적으로 표현하는 표준 모델링 언어.
*   **Class:** 객체를 정의하는 틀 (객체의 설계도).
*   **Object:** 클래스에 의해 생성된 실체.
*   **Composition:** 객체 간의 강한 관계, 한 객체가 사라지면 다른 객체도 함께 사라짐.
*   **Association:** 객체 간의 느슨한 관계, 객체들이 독립적인 생명주기를 가짐.
*   **Inheritance:** 상속, 부모 클래스의 속성과 메서드를 자식 클래스가 물려받는 것.
*   **Usage:** 한 클래스가 다른 클래스의 메서드를 사용하는 관계.

**5. 결론**

*   문서는 OOP 설계의 중요성을 강조하고, UML 다이어그램을 사용하여 시스템 설계를 시각적으로 표현하는 방법을 설명.
*   클래스 간의 관계를 이해하고, 각 클래스의 역할과 책임을 명확하게 정의하는 것이 OOP 설계의 핵심.
*   설계 단계의 중요성을 강조하며, 코딩 전에 충분한 시간을 투자하여 설계를 하는 것이 생산성을 향상시키는 데 도움이 됨.
