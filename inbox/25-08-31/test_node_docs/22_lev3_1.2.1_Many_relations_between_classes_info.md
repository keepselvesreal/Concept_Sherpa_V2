## 핵심 내용
객체 지향 프로그래밍에서 클래스 간의 많은 관계는 시스템 복잡성을 증가시키는 주요 원인 중 하나입니다. 특히 코드와 데이터가 섞여 있을 때, Member 클래스를 예시로 들어 코드와 데이터를 분리하면 시스템의 복잡성을 줄일 수 있음을 보여줍니다. 결과적으로, 코드와 데이터를 분리하여 여러 개의 독립적인 부분으로 구성된 시스템은 단일 복잡한 부분으로 구성된 시스템보다 이해하기 쉬워집니다.

## 상세 핵심 내용
이 문서는 객체 지향 프로그래밍(OOP)에서 클래스 간의 관계가 시스템 복잡성에 미치는 영향을 분석합니다. OOP에서는 코드와 데이터가 클래스 내에서 혼합되어, 클래스들이 다양한 관계에 얽히게 됩니다. 특히, Member 클래스를 예시로 들어 데이터 관계 2개와 코드 관계 3개, 총 5개의 관계를 가지는 복잡성을 설명합니다. 이러한 복잡성을 해결하기 위해 각 클래스를 코드와 데이터로 분리하면 시스템을 이해하기 쉬운 독립적인 부분으로 나눌 수 있음을 제시합니다. 코드와 데이터를 분리한 시스템은 각 부분을 별도로 이해할 수 있어 전체 시스템의 복잡성을 감소시키며, 여러 개의 간단하고 독립적인 부분으로 구성된 시스템이 단일하고 복잡한 부분으로 구성된 시스템보다 덜 복잡하다는 점을 강조합니다. 최종적으로, 클래스 분리를 통해 시스템의 이해도를 높일 수 있음을 보여줍니다.

## 상세 정보
## 1.2.1 Many relations between classes - 상세 정보 정리

### 1. 핵심 내용 요약

이 문서는 객체 지향 프로그래밍(OOP)에서 클래스 간의 다양한 관계가 시스템 복잡성에 미치는 영향과, 이를 해결하기 위한 코드와 데이터의 분리 방식을 설명합니다. OOP에서 코드와 데이터가 클래스 내에서 섞여있기 때문에, 클래스는 필연적으로 많은 관계를 맺게 되며, 이는 시스템의 복잡성을 증가시키는 주요 원인 중 하나입니다.

### 2. 주요 개념 및 용어

*   **클래스 다이어그램 (Class Diagram):** 클래스 간의 관계를 시각적으로 표현하는 다이어그램.
*   **엔티티 (Entity):** 시스템 내의 독립적인 구성 요소 (예: 클래스).
*   **멤버 (Member):** 클래스 내의 데이터 (변수).
*   **메소드 (Method):** 클래스 내의 코드 (함수).
*   **데이터 관계 (Data Relations):** 데이터 (멤버)를 기반으로 하는 관계. 예: Library has many Members.
*   **코드 관계 (Code Relations):** 코드 (메소드)를 기반으로 하는 관계. 예: Member extends User.
*   **MemberCode & MemberData:** 클래스를 코드와 데이터로 분리한 예시. MemberCode는 코드 관련, MemberData는 데이터 관련 부분을 담당.

### 3. 시스템 복잡성에 영향을 미치는 OOP의 측면 (표 1.1)

| 측면                      | 복잡성에 미치는 영향                                                     |
| :------------------------ | :------------------------------------------------------------------------ |
| 코드와 데이터 혼합        | 클래스는 많은 관계를 가지는 경향이 있음.                                  |
| 객체 가변성                | 코드 읽기에 추가적인 고려가 필요함.                                      |
| 객체 가변성                | 멀티 스레드 환경에서 명시적인 동기화가 필요함.                           |
| 데이터는 객체 내에 잠김    | 데이터 직렬화가 간단하지 않음.                                             |
| 코드는 클래스 내에 잠김    | 클래스 계층 구조가 복잡해짐.                                             |

### 4. 예시: Klafim's Library Management System (그림 1.10)

*   **클래스 다이어그램**: Librarian, Book, Author, BookItem, Catalog, BookLending, Library, Member, User
*   **문제**: 클래스 간의 복잡한 관계가 시스템 복잡성을 야기함.

### 5. Member 클래스의 상세 분석 (그림 1.11)

*   **Member 클래스**: 5개의 관계를 가짐 (2개의 데이터 관계, 3개의 코드 관계).
    *   **데이터 관계:**
        *   Library has many Members.
        *   Member has many BookLendings.
    *   **코드 관계:**
        *   Member extends User.
        *   Librarian uses Member.
        *   Member uses BookItem.

### 6. 코드와 데이터 분리 (MemberCode & MemberData) (그림 1.12)

*   **개념**: Member 클래스를 MemberCode (코드)와 MemberData (데이터)로 분리.
*   **결과**: MemberCode (3개의 관계)와 MemberData (2개의 관계)로 시스템 단순화.

### 7. 모든 클래스에 코드와 데이터 분리 적용 (그림 1.13)

*   **개념**: Klafim's Library Management System의 모든 클래스에 코드와 데이터 분리 적용.
*   **결과**:
    *   두 개의 독립적인 부분으로 시스템 구성: 데이터 엔티티 부분, 코드 엔티티 부분.
    *   시스템 이해 용이성 증가 (각 부분은 독립적으로 이해 가능).
*   **결론**: 여러 개의 단순하고 독립적인 부분으로 구성된 시스템은 단일의 복잡한 부분으로 구성된 시스템보다 덜 복잡함.

### 8. 핵심 팁 (TIP)

*   코드와 데이터가 혼합된 시스템보다 모든 클래스를 코드와 데이터로 분리한 시스템이 더 단순하다.
*   여러 개의 단순하고 독립적인 부분으로 구성된 시스템은 단일의 복잡한 부분으로 구성된 시스템보다 덜 복잡하다.

### 9. 결론

OOP에서 클래스 간의 다중 관계는 시스템 복잡성을 증가시키는 주요 원인이며, 코드와 데이터를 분리함으로써 시스템의 이해도를 높이고 복잡성을 줄일 수 있다.

makes the system complex in the sense that entities tend to be involved in many rela-

Data relations:
– Library has many Members.
– Member has many BookLendings.
Code relations:
– Member extends User.
– Librarian uses Member.

Imagine for a moment that we were able, somehow, to split the Member class into two
separate entities:

MemberCode for the code

MemberData for the data
Instead of a Member class with five relations, we would have the diagram shown in fig-
ure 1.12 with:
A MemberCode entity and three relations.
A MemberData entity and two relations.

CHAPTER 1
Complexity of object-oriented programming
The class diagram where Member is split into MemberCode and MemberData is made of
two independent parts. Each part is easier to understand than the original diagram.
 Let's split every class of our original class diagram into code and data entities.
Figure 1.13 shows the resulting diagram. Now the system is made of two indepen-
dent parts:
A part that involves only data entities.
A part that involves only code entities.
TIP
A system where every class is split into two independent parts, code and data, is
simpler than a system where code and data are mixed.
The resulting system, made up of two independent subsystems, is easier to understand
than the original system. The fact that the two subsystems are independent means that
each subsystem can be understood separately and in any order. The resulting system
not simpler by accident; it is a logical consequence of separating code from data.
TIP
A system made of multiple simple independent parts is less complex than a sys-
tem made of a single complex part.
