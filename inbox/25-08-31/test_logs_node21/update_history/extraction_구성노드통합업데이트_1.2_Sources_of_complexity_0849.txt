**부모 노드 (1.2 Sources of complexity)의 업데이트된 내용:**
핵심 내용: 이 문서는 객체 지향 프로그래밍(OOP)의 복잡성 원인을 분석하고, 데이터 중심 프로그래밍(DOP)이 OOP의 복잡성을 어떻게 완화할 수 있는지 설명한다. OOP의 주요 복잡성 원인으로 코드와 데이터의 혼합, 가변 객체, 데이터와 코드의 클래스 내 고정, 복잡한 클래스 계층 구조 등을 지적한다.
상세 핵심 내용: OOP는 시스템을 이해하기 어렵게 만드는 경향이 있으며, 이는 코드와 데이터의 혼합, 가변 객체의 사용, 데이터와 코드의 클래스 내 고정 때문에 발생한다. 코드와 데이터가 혼합되면 클래스 간 관계가 많아지고, 가변 객체는 코드의 예측 불가능성을 초래한다. 또한, 데이터가 클래스에 고정되면 데이터 직렬화가 어려워지고, 복잡한 클래스 계층 구조는 시스템 설계를 더욱 복잡하게 만든다. DOP는 이러한 OOP의 복잡성을 줄이기 위해 데이터와 코드를 분리하고, 불변성을 강조하며, 데이터에 대한 일반적인 접근 방식을 제공한다.
상세 정보: - OOP는 시스템을 이해하기 어렵게 만드는 복잡성을 야기하며, 이는 코드와 데이터의 혼합에서 비롯된다.
- OOP에서 코드와 데이터는 클래스 내에 혼합되어 있어 엔터티가 많은 관계에 관여하게 된다.
- 가변 객체는 코드의 예측 불가능성을 초래하며, 다중 스레드 환경에서는 명시적인 동기화가 필요하다.
- OOP에서 데이터는 객체 내에 잠겨 있어 데이터 직렬화가 복잡해진다.
- OOP에서 코드는 클래스 내에 잠겨 있어 클래스 계층 구조가 복잡해진다.
- DOP는 OOP와 FP 모두와 호환되며, OOP 시스템에서 DOP 원칙을 따르면 시스템 복잡성을 줄일 수 있다.
- DOP는 데이터와 코드를 분리하고, 데이터 불변성을 강조하며, 데이터에 대한 일반적인 접근 방식을 제공하여 OOP의 복잡성을 완화한다.
- 복잡한 클래스 계층 구조는 새로운 요구 사항이 추가될 때 시스템 설계를 더욱 복잡하게 만들 수 있다.
- 클래스 상속보다는 컴포지션을 사용하는 것이 OOP에서 복잡성을 줄이는 데 도움이 될 수 있다.

구성노드22 (1.2.1 Many relations between classes):
- 핵심 내용: 클래스 다이어그램의 복잡성은 엔터티와 관계를 통해 평가할 수 있다. 객체 지향 프로그래밍(OOP)에서 코드와 데이터가 혼합되어 있어 클래스가 많은 관계에 관여하게 되고, 이는 시스템 복잡성을 증가시킨다. 코드와 데이터를 분리함으로써 시스템을 더 간단하고 이해하기 쉽게 만들 수 있다.
- 상세 핵심 내용: 객체 지향 프로그래밍에서 코드와 데이터의 혼합은 시스템 복잡성을 증가시키며, 클래스는 여러 관계에 관여하게 된다. Member 클래스를 예로 들면, 데이터 관계와 코드 관계로 나눌 수 있다. 코드와 데이터를 분리하여 Member 클래스를 MemberCode와 MemberData로 나누면, 각 엔터티가 관련된 관계의 수를 줄여 다이어그램을 더 쉽게 이해할 수 있다. 시스템의 모든 클래스를 코드와 데이터 엔터티로 분리하면 시스템이 두 개의 독립적인 부분으로 구성되어 이해하기 쉬워진다. 간단하고 독립적인 부분으로 구성된 시스템은 단일하고 복잡한 부분으로 구성된 시스템보다 덜 복잡하다.
- 상세 정보: *   클래스 다이어그램의 복잡성은 엔터티와 관계를 통해 평가할 수 있다.
*   OOP에서 코드와 데이터는 클래스 내에서 혼합되어 있으며, 이는 시스템 복잡성에 영향을 미친다.
*   코드와 데이터의 혼합은 클래스가 여러 관계에 관여하게 만든다.
*   Member 클래스는 데이터 관계(Library has many Members, Member has many BookLendings)와 코드 관계(Member extends User, Librarian uses Member, Member uses BookItem)를 가진다.
*   Member 클래스를 MemberCode와 MemberData로 분리하면 각 엔터티가 관련된 관계의 수를 줄일 수 있다.
*   시스템 내 모든 클래스를 코드와 데이터 엔터티로 분리하면 시스템은 독립적인 코드 부분과 데이터 부분으로 나뉜다.
*   코드와 데이터를 분리한 시스템은 원래 시스템보다 이해하기 쉽다.
*   간단하고 독립적인 부분으로 구성된 시스템은 단일하고 복잡한 부분으로 구성된 시스템보다 덜 복잡하다.
*   Klafim's Library Management System의 클래스 다이어그램 예시가 제공된다.

구성노드23 (1.2.2 Unpredictable code behavior):
- 핵심 내용: 객체지향 프로그래밍(OOP)에서 객체 멤버의 가변성으로 인해 예측 불가능한 코드 동작이 발생할 수 있다. 단일 스레드 환경에서는 문제가 없지만, 멀티 스레드 환경이나 비동기 코드에서는 객체의 상태가 변경되어 예상치 못한 결과를 초래할 수 있다. 데이터 불변성은 DOP(Data-Oriented Programming) 개발자에게 안정감을 제공한다.
- 상세 핵심 내용: OOP에서 객체 멤버는 가변적이기 때문에 멀티 스레드 환경이나 비동기 코드에서 예측 불가능한 동작을 유발할 수 있다. 이는 두 번의 console.log 호출 사이에 객체의 상태가 변경될 수 있기 때문이다. primitive 타입은 일반적으로 불변이지만 객체 멤버는 가변적이며, 이러한 문제를 해결하기 위해 mutex와 같은 concurrency safety 메커니즘을 사용할 수 있지만 성능 저하 및 deadlock 위험이 따른다. DOP에서는 모든 데이터를 불변으로 취급하여 이러한 문제를 해결하고 개발자에게 안정감을 제공한다. 첫 번째 코드 스니펫은 Boolean 값을 두 번 액세스하는 반면, 두 번째 코드 스니펫은 객체의 멤버를 두 번 액세스하여 문제 발생 가능성을 높인다. 따라서 데이터가 mutable 할 때 코드의 예측 불가능성이 높아진다.
- 상세 정보: *   **Unpredictable Code Behavior:**
*   객체지향 프로그래밍(OOP)에서 객체 멤버의 가변성으로 인해 예측 불가능한 코드 동작이 발생할 수 있다.
*   단일 스레드 환경에서는 문제가 없지만, 멀티 스레드 환경이나 비동기 코드에서는 객체의 상태가 변경되어 예상치 못한 결과를 초래할 수 있다.
*   예제 코드 1.1에서는 Boolean 값을 변수에 할당하여 두 번 출력하므로 예측 가능한 결과를 얻을 수 있다.
*   예제 코드 1.2에서는 객체의 멤버를 직접 두 번 출력하므로 멀티 스레드 환경에서 예측 불가능한 결과를 얻을 수 있다.
*   **Mutability and Immutability:**
*   Primitive 타입은 일반적으로 불변(immutable)이지만 객체 멤버는 가변(mutable)적이다.
*   데이터가 가변적일 때 코드의 예측 불가능성이 높아진다.
*   **Concurrency Safety Mechanisms:**
*   OOP에서 가변적인 객체 멤버로 인한 문제를 해결하기 위해 mutex와 같은 concurrency safety 메커니즘을 사용할 수 있다.
*   하지만 이러한 메커니즘은 성능 저하 및 deadlock 위험을 초래할 수 있다.
*   **Data-Oriented Programming (DOP):**
*   DOP에서는 모든 데이터를 불변으로 취급하여 객체 멤버의 가변성으로 인한 문제를 해결한다.
*   DOP는 개발자에게 안정감을 제공한다.

구성노드24 (1.2.3 Not trivial data serialization):
- 핵심 내용: 이 문서는 객체 지향 프로그래밍(OOP)에서 JSON 직렬화/역직렬화의 어려움을 설명한다. Theo의 꿈을 통해 /search 엔드포인트 구현 시 반복되는 클래스 생성 및 코드 작성의 비효율성을 지적하고, OOP에서 데이터가 클래스에 갇혀 일반적인 접근이 어렵다는 점을 강조한다.
- 상세 핵심 내용: Theo의 꿈에서 Nancy는 Klafim's Library Management System에 JSON 기반 REST API를 구현하도록 요청받는다. /search 엔드포인트를 구현하기 위해 Theo는 SearchController, SearchQuery, SearchResult 클래스를 생성해야 하지만, 다른 엔드포인트(/add-book-item)를 추가할 때마다 동일한 과정을 반복해야 한다. 이는 OOP에서 데이터 직렬화 및 역직렬화가 복잡하고 비효율적임을 보여준다. 데이터가 클래스 멤버에 갇혀 있어 일반적인 접근이 어렵기 때문에, 각 엔드포인트마다 새로운 클래스와 코드를 작성해야 하는 문제점이 있다. DOP(Data-Oriented Programming)는 이러한 문제를 해결할 수 있는 일반적인 방법을 제공할 수 있다.
- 상세 정보: *   **JSON 기반 REST API 구현의 어려움:** Theo는 Klafim's Library Management System을 위해 JSON을 사용하는 REST API를 구현해야 한다.
*   **/search 엔드포인트 예시:** /search 엔드포인트는 JSON 형식으로 쿼리를 받아 결과를 JSON 형식으로 반환한다.
*   **클래스 기반 구현의 반복성:** /search 엔드포인트를 구현하기 위해 SearchController, SearchQuery, SearchResult 클래스를 생성해야 하며, 다른 엔드포인트(/add-book-item)를 구현할 때도 유사한 클래스(AddBookItemController, BookItemQuery, BookItemResult)를 반복적으로 생성해야 한다.
*   **코드 중복 문제:** JSON 직렬화 및 역직렬화 코드를 각 클래스마다 반복적으로 작성해야 한다.
*   **OOP의 데이터 접근 제한:** OOP에서는 데이터가 클래스 멤버에 갇혀 있어 일반적인 접근이 어렵다.
*   **DOP의 가능성:** DOP는 JSON 직렬화 및 역직렬화를 위한 일반적인 방법을 제공할 수 있다.
*   **OOP 언어의 완화 노력:** 대부분의 OOP 언어는 reflection 또는 코드 장황성을 통해 JSON 변환의 어려움을 완화하려 한다.

구성노드25 (1.2.4 Complex class hierarchies):
- 핵심 내용: 이 문서는 객체 지향 프로그래밍(OOP)에서 클래스 상속을 사용하여 코드를 재사용하는 방식의 문제점을 보여준다. 새로운 요구사항이 추가될 때 기존의 클래스 계층 구조가 복잡해지고, 다중 상속으로 인한 문제(다이아몬드 문제)가 발생할 수 있음을 지적한다. 따라서 클래스 상속보다 구성(composition)을 선호해야 함을 강조한다.
- 상세 핵심 내용: OOP에서 클래스 상속은 초기 요구사항을 충족시키는 데 유용하지만, 시스템 구현 후 새로운 요구사항이 추가될 때 문제점을 야기할 수 있다. VIP 멤버와 Super 멤버를 추가하는 과정에서 기존의 Librarian 클래스의 코드를 재사용하기 어렵고, 다중 상속으로 인한 다이아몬드 문제가 발생한다. Theo는 클래스 상속의 한계를 느끼고, 구성(composition)을 사용하려 하지만 시간 제약으로 인해 실패한다. 따라서 OOP에서는 클래스 상속보다 구성(composition)을 사용하는 것이 더 유연하고 유지보수가 용이함을 시사한다.
- 상세 정보: 이 문서는 도서관 시스템 개발 프로젝트를 배경으로 OOP에서 클래스 상속의 문제점을 설명한다. 프로젝트 팀은 초기 요구사항에 따라 클래스 상속을 사용하여 Librarian과 Member 클래스를 User 클래스로부터 상속받도록 설계했다. 하지만 프로젝트 마감 직전에 VIP 멤버와 Super 멤버를 추가해야 하는 새로운 요구사항이 발생한다. VIP 멤버는 도서를 추가할 수 있는 권한을 가지므로 Librarian 클래스의 코드를 재사용해야 하지만, 클래스 상속 구조상 어려움이 발생한다. Super 멤버는 다른 멤버의 대출 목록을 볼 수 있는 권한을 가지므로 시스템은 더욱 복잡해진다. Theo는 다중 상속을 사용하여 문제를 해결하려 하지만, 다이아몬드 문제에 직면하고 결국 마감 기한을 넘기게 된다. Nancy와의 대화를 통해 새로운 기능 추가가 얼마나 어려운 작업인지, 그리고 비즈니스 요구사항 변경에 따른 유연한 대처의 중요성을 보여준다.

## 핵심 내용
객체 지향 프로그래밍(OOP)에서 코드와 데이터의 혼합은 클래스 간의 많은 관계를 유발하여 시스템 복잡성을 증가시킨다. 데이터 중심 프로그래밍(DOP)은 코드와 데이터를 분리함으로써 이러한 복잡성을 완화하고 시스템을 더 간단하게 만든다.

## 상세 핵심 내용
OOP에서 코드와 데이터가 혼합되면 클래스는 다양한 관계에 관여하게 되며, 이는 시스템을 이해하기 어렵게 만든다. 예를 들어 Member 클래스는 데이터 관계와 코드 관계를 모두 가질 수 있다. Member 클래스를 MemberCode와 MemberData로 분리하면 각 엔터티가 관련된 관계의 수를 줄여 시스템을 더 쉽게 이해할 수 있다. DOP는 시스템을 독립적인 코드 부분과 데이터 부분으로 구성하여 복잡성을 줄인다. 간단하고 독립적인 부분으로 구성된 시스템은 단일하고 복잡한 시스템보다 이해하기 쉽다.

## 상세 정보
*   클래스 다이어그램의 복잡성은 엔터티와 관계를 통해 평가할 수 있다.
*   OOP에서 코드와 데이터는 클래스 내에서 혼합되어 있으며, 이는 시스템 복잡성을 증가시킨다.
*   코드와 데이터의 혼합은 클래스가 여러 관계에 관여하게 만든다.
*   Member 클래스는 데이터 관계(Library has many Members, Member has many BookLendings)와 코드 관계(Member extends User, Librarian uses Member, Member uses BookItem)를 가진다.
*   Member 클래스를 MemberCode와 MemberData로 분리하면 각 엔터티가 관련된 관계의 수를 줄일 수 있다.
*   시스템 내 모든 클래스를 코드와 데이터 엔터티로 분리하면 시스템은 독립적인 코드 부분과 데이터 부분으로 나뉜다.
*   코드와 데이터를 분리한 시스템은 원래 시스템보다 이해하기 쉽다.
*   간단하고 독립적인 부분으로 구성된 시스템은 단일하고 복잡한 부분으로 구성된 시스템보다 덜 복잡하다.
*   Klafim's Library Management System의 클래스 다이어그램 예시가 제공된다.

구성노드23:
## 핵심 내용
객체 지향 프로그래밍(OOP)에서 가변 객체 멤버는 예측 불가능한 코드 동작을 초래할 수 있다. 데이터 중심 프로그래밍(DOP)은 데이터 불변성을 통해 이러한 문제를 해결하고 개발자에게 안정성을 제공한다.

## 상세 핵심 내용
OOP에서 객체 멤버의 가변성은 멀티 스레드 환경이나 비동기 코드에서 특히 문제가 된다. 객체의 상태가 예기치 않게 변경될 수 있기 때문이다. Primitive 타입은 일반적으로 불변이지만 객체 멤버는 가변적이며, 이러한 가변성을 관리하기 위해 mutex와 같은 concurrency safety 메커니즘을 사용할 수 있지만 성능 저하 및 deadlock 위험이 따른다. DOP는 모든 데이터를 불변으로 취급하여 이러한 문제를 근본적으로 해결하고, 코드 예측 가능성을 높인다. 데이터가 mutable 할 때 코드의 예측 불가능성이 높아진다.

## 상세 정보
*   **Unpredictable Code Behavior:**
*   객체지향 프로그래밍(OOP)에서 객체 멤버의 가변성으로 인해 예측 불가능한 코드 동작이 발생할 수 있다.
*   단일 스레드 환경에서는 문제가 없지만, 멀티 스레드 환경이나 비동기 코드에서는 객체의 상태가 변경되어 예상치 못한 결과를 초래할 수 있다.
*   예제 코드 1.1에서는 Boolean 값을 변수에 할당하여 두 번 출력하므로 예측 가능한 결과를 얻을 수 있다.
*   예제 코드 1.2에서는 객체의 멤버를 직접 두 번 출력하므로 멀티 스레드 환경에서 예측 불가능한 결과를 얻을 수 있다.
*   **Mutability and Immutability:**
*   Primitive 타입은 일반적으로 불변(immutable)이지만 객체 멤버는 가변(mutable)적이다.
*   데이터가 가변적일 때 코드의 예측 불가능성이 높아진다.
*   **Concurrency Safety Mechanisms:**
*   OOP에서 가변적인 객체 멤버로 인한 문제를 해결하기 위해 mutex와 같은 concurrency safety 메커니즘을 사용할 수 있다.
*   하지만 이러한 메커니즘은 성능 저하 및 deadlock 위험을 초래할 수 있다.
*   **Data-Oriented Programming (DOP):**
*   DOP에서는 모든 데이터를 불변으로 취급하여 객체 멤버의 가변성으로 인한 문제를 해결한다.
*   DOP는 개발자에게 안정감을 제공한다.

구성노드24:
## 핵심 내용
객체 지향 프로그래밍(OOP)에서 데이터가 클래스 내에 고정되어 데이터 직렬화가 복잡해지는 문제를 다룬다. 데이터 중심 프로그래밍(DOP)은 데이터에 대한 일반적인 접근 방식을 제공하여 이러한 문제를 완화할 수 있음을 설명한다.

## 상세 핵심 내용
Klafim's Library Management System의 /search 엔드포인트 구현 예시를 통해 OOP에서 JSON 직렬화/역직렬화의 어려움을 보여준다. 각 엔드포인트마다 SearchController, SearchQuery, SearchResult와 같은 새로운 클래스를 반복적으로 생성해야 하는 비효율성을 지적한다. 데이터가 클래스 멤버에 갇혀 있어 일반적인 접근이 어렵기 때문에 발생하는 문제이다. DOP는 데이터와 코드를 분리하고 데이터에 대한 일반적인 접근 방식을 제공함으로써 이러한 문제를 해결할 수 있다.

## 상세 정보
*   **JSON 기반 REST API 구현의 어려움:** Theo는 Klafim's Library Management System을 위해 JSON을 사용하는 REST API를 구현해야 한다.
*   **/search 엔드포인트 예시:** /search 엔드포인트는 JSON 형식으로 쿼리를 받아 결과를 JSON 형식으로 반환한다.
*   **클래스 기반 구현의 반복성:** /search 엔드포인트를 구현하기 위해 SearchController, SearchQuery, SearchResult 클래스를 생성해야 하며, 다른 엔드포인트(/add-book-item)를 구현할 때도 유사한 클래스(AddBookItemController, BookItemQuery, BookItemResult)를 반복적으로 생성해야 한다.
*   **코드 중복 문제:** JSON 직렬화 및 역직렬화 코드를 각 클래스마다 반복적으로 작성해야 한다.
*   **OOP의 데이터 접근 제한:** OOP에서는 데이터가 클래스 멤버에 갇혀 있어 일반적인 접근이 어렵다.
*   **DOP의 가능성:** DOP는 JSON 직렬화 및 역직렬화를 위한 일반적인 방법을 제공할 수 있다.
*   **OOP 언어의 완화 노력:** 대부분의 OOP 언어는 reflection 또는 코드 장황성을 통해 JSON 변환의 어려움을 완화하려 한다.

구성노드25:
## 핵심 내용
객체 지향 프로그래밍(OOP)에서 복잡한 클래스 계층 구조는 새로운 요구 사항 추가 시 시스템 설계를 더욱 복잡하게 만들 수 있다. 클래스 상속보다는 컴포지션을 사용하는 것이 OOP에서 복잡성을 줄이는 데 도움이 될 수 있다.

## 상세 핵심 내용
클래스 상속은 초기 요구 사항에는 유용하지만, 시스템 구현 후 새로운 요구 사항이 추가될 때 기존 클래스 계층 구조를 복잡하게 만들 수 있다. VIP 멤버와 Super 멤버를 추가하는 과정에서 Librarian 클래스의 코드를 재사용하기 어렵고, 다중 상속으로 인한 다이아몬드 문제가 발생할 수 있다. 이러한 문제를 해결하기 위해 클래스 상속 대신 컴포지션을 사용하는 것이 더 유연하고 유지보수가 용이하다.

## 상세 정보
이 문서는 도서관 시스템 개발 프로젝트를 배경으로 OOP에서 클래스 상속의 문제점을 설명한다. 프로젝트 팀은 초기 요구사항에 따라 클래스 상속을 사용하여 Librarian과 Member 클래스를 User 클래스로부터 상속받도록 설계했다. 하지만 프로젝트 마감 직전에 VIP 멤버와 Super 멤버를 추가해야 하는 새로운 요구사항이 발생한다. VIP 멤버는 도서를 추가할 수 있는 권한을 가지므로 Librarian 클래스의 코드를 재사용해야 하지만, 클래스 상속 구조상 어려움이 발생한다. Super 멤버는 다른 멤버의 대출 목록을 볼 수 있는 권한을 가지므로 시스템은 더욱 복잡해진다. Theo는 다중 상속을 사용하여 문제를 해결하려 하지만, 다이아몬드 문제에 직면하고 결국 마감 기한을 넘기게 된다. Nancy와의 대화를 통해 새로운 기능 추가가 얼마나 어려운 작업인지, 그리고 비즈니스 요구사항 변경에 따른 유연한 대처의 중요성을 보여준다.
