## 핵심 내용

객체 지향 프로그래밍(OOP)에서 코드와 데이터가 클래스 내에 혼합되어 있어 클래스 다이어그램이 복잡해지는 경향이 있다. 클래스를 코드와 데이터 부분으로 분리하면 전체 시스템의 복잡성을 줄이고 이해하기 쉬운 독립적인 하위 시스템으로 구성할 수 있다.

## 상세 핵심 내용

이 문서는 객체 지향 프로그래밍(OOP)에서 클래스 간 관계의 복잡성을 분석하고, 코드와 데이터가 혼합되어 있어 발생하는 복잡성을 지적한다. OOP의 특징인 코드와 데이터의 혼합은 클래스가 여러 관계에 관여하게 만들어 시스템을 복잡하게 만든다. 도서관 관리 시스템의 클래스 다이어그램을 예시로 들어, `Member` 클래스가 데이터 관계(Library, BookLending) 및 코드 관계(User, Librarian, BookItem)를 가지는 것을 보여준다. 이러한 복잡성을 줄이기 위해, `Member` 클래스를 `MemberCode`와 `MemberData`로 분리하여 관계 수를 줄이고 독립적인 부분으로 나누어 시스템을 단순화하는 방안을 제시한다. 궁극적으로 코드와 데이터를 분리함으로써 시스템을 이해하기 쉬운 독립적인 하위 시스템으로 구성하여 전체 복잡도를 낮출 수 있음을 강조한다. 단순하고 독립적인 부분으로 구성된 시스템이 단일하고 복잡한 시스템보다 이해하기 쉽다는 것이 핵심 주장이다.

## 주요 화제

이 문서는 객체 지향 프로그래밍(OOP)의 복잡성에 대한 주제를 다루고 있으며, 특히 클래스 간의 관계가 복잡성에 미치는 영향에 초점을 맞추고 있습니다. 주요 화제는 다음과 같습니다:

*   **클래스 다이어그램의 복잡성**: 클래스 다이어그램에서 엔티티와 관계의 수를 통해 복잡성을 평가하는 방법
*   **코드와 데이터의 결합**: OOP에서 코드와 데이터가 클래스 내에 혼합되어 있어 클래스가 많은 관계에 관여하게 되는 현상
*   **OOP의 복잡성 측면**: 코드-데이터 결합, 객체의 가변성, 데이터 잠금, 코드 잠금 등이 시스템 복잡성에 미치는 영향
*   **Klafim's Library Management System**: 도서관 관리 시스템의 클래스 다이어그램 예시를 통해 클래스 간의 관계를 설명
*   **Member 클래스의 복잡성**: Member 클래스가 여러 관계(데이터 관계, 코드 관계)에 관여하는 사례 분석
*   **코드와 데이터 분리**: Member 클래스를 MemberCode(코드)와 MemberData(데이터)로 분리하여 관계를 단순화하는 방법 제시
*   **독립적인 하위 시스템**: 클래스를 코드와 데이터 엔티티로 분리하여 독립적인 하위 시스템으로 구성하는 것이 시스템 복잡성을 줄이는 방법
*   **시스템 복잡성 감소**: 코드와 데이터를 분리하여 단순하고 독립적인 부분으로 시스템을 구성하는 것이 복잡한 단일 시스템보다 이해하기 쉽다는 점 강조

## 부차 화제

다음은 문서에서 파악된 부차적인 주제들입니다:

*   **객체 지향 프로그래밍(OOP)의 측면과 시스템 복잡도에 미치는 영향:** OOP의 여러 특징(코드와 데이터의 혼합, 객체의 가변성, 데이터 및 코드의 캡슐화)이 시스템의 복잡성에 어떤 영향을 미치는지 분석합니다.
*   **클래스 다이어그램:** 클래스 다이어그램을 통해 클래스와 관계의 복잡성을 시각적으로 평가하고, 시스템 설계를 이해하는 데 활용합니다.
*   **코드와 데이터의 분리:** 클래스를 코드와 데이터 엔티티로 분리하여 시스템의 복잡성을 줄이는 방법을 제안하고, 분리된 시스템이 더 이해하기 쉬운 이유를 설명합니다.
*   **독립적인 하위 시스템:** 시스템을 독립적인 부분(코드 엔티티, 데이터 엔티티)으로 나누어 전체 시스템의 복잡성을 줄이는 전략을 제시합니다.
*   **Klafim's Library Management System:** 도서관 관리 시스템을 예시로 들어 클래스 다이어그램과 관계를 설명하고, 실제 시스템에 적용 가능한 개념을 보여줍니다.
*   **데이터 직렬화:** 객체 안에 데이터가 락인되어 데이터 직렬화가 어렵다는 언급을 통해, 데이터 관리의 어려움을 시사합니다.
*   **다중 스레드 환경:** 객체가 가변적이므로 다중 스레드 환경에서 명시적인 동기화가 필요하다는 점을 지적하며, 동시성 관리의 중요성을 강조합니다.

1.2
Sources of complexity
From a system analysis perspective, the fact that code and data are mixed together
makes the system complex in the sense that entities tend to be involved in many rela-
tions. In figure 1.11, we take a closer look at the Member class. Member is involved in five
relations: two data relations and three code relations.
Data relations:
– Library has many Members.
– Member has many BookLendings.
Code relations:
– Member extends User.
– Librarian uses Member.
– Member uses BookItem.
Imagine for a moment that we were able, somehow, to split the Member class into two
separate entities:

MemberCode for the code

MemberData for the data
Instead of a Member class with five relations, we would have the diagram shown in fig-
ure 1.12 with:
A MemberCode entity and three relations.
A MemberData entity and two relations.

CHAPTER 1
Complexity of object-oriented programming
The class diagram where Member is split into MemberCode and MemberData is made of
two independent parts. Each part is easier to understand than the original diagram.
 Let's split every class of our original class diagram into code and data entities.
Figure 1.13 shows the resulting diagram. Now the system is made of two indepen-
dent parts:
A part that involves only data entities.
A part that involves only code entities.
TIP
A system where every class is split into two independent parts, code and data, is
simpler than a system where code and data are mixed.
The resulting system, made up of two independent subsystems, is easier to understand
than the original system. The fact that the two subsystems are independent means that
each subsystem can be understood separately and in any order. The resulting system
not simpler by accident; it is a logical consequence of separating code from data.
TIP
A system made of multiple simple independent parts is less complex than a sys-
tem made of a single complex part.
