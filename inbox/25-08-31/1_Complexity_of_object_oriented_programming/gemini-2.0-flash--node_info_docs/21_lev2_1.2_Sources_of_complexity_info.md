## 핵심 내용

이 문서는 객체 지향 프로그래밍(OOP)의 복잡성 원인을 분석하고, 데이터 중심 프로그래밍(DOP)이 OOP의 단점을 보완할 수 있음을 설명합니다. OOP에서 코드와 데이터 혼합, 가변 객체, 데이터 및 코드의 캡슐화는 시스템을 이해하기 어렵게 만들고, DOP는 이를 해결하기 위해 데이터와 코드를 분리하고 불변성을 활용합니다.

## 상세 핵심 내용

이 문서는 객체 지향 프로그래밍(OOP)의 복잡성 원인을 분석하고, 데이터 중심 프로그래밍(DOP)을 대안으로 제시한다. OOP는 코드와 데이터를 혼합하고, 객체를 가변적으로 만들어 코드 이해와 동기화를 어렵게 한다. 또한, 데이터가 객체에, 코드가 클래스에 갇혀 데이터 직렬화와 클래스 계층 구조를 복잡하게 만든다. 클래스 간의 과도한 관계 또한 시스템 복잡성을 가중시킨다. DOP는 코드와 데이터를 분리하고, 데이터 불변성을 통해 이러한 복잡성을 줄이는 것을 목표로 한다. DOP는 OOP 및 함수형 프로그래밍(FP)과 호환 가능하며, OOP 시스템에서도 DOP 원칙을 적용하면 복잡성을 완화할 수 있다.

## 주요 화제

이 문서("1.2_Sources_of_complexity")의 주요 화제는 다음과 같습니다.

*   **객체 지향 프로그래밍(OOP)의 복잡성**: OOP가 시스템을 이해하기 어렵게 만드는 경향에 대한 논의가 주를 이룹니다.
*   **복잡성의 정의**: "이해하기 어려움"으로 정의되는 복잡성의 특정 유형에 초점을 맞춥니다. 이는 리소스 소비와 관련된 복잡성과는 다릅니다.
*   **데이터 지향 프로그래밍(DOP)**: OOP에 대한 대안으로 제시되며, DOP가 시스템을 덜 복잡하게 만드는 경향이 있다고 주장합니다. DOP는 OOP 및 함수형 프로그래밍(FP)과 호환됩니다.
*   **OOP 복잡성의 원인**:
    *   코드와 데이터의 혼합
    *   객체의 가변성
    *   객체 내 데이터 잠금
    *   클래스 내 코드 잠금
*   **클래스 간의 관계**: OOP에서 코드와 데이터가 혼합되어 엔터티가 많은 관계에 관여하게 되는 경향을 설명합니다. 클래스를 코드와 데이터 엔터티로 분리하면 시스템을 단순화할 수 있다고 주장합니다.
*   **예측 불가능한 코드 동작**: 가변 데이터로 인해 발생하는 문제점을 강조하며, 다중 스레드 환경에서 코드의 예측 불가능성이 증가합니다. 데이터 불변성이 DOP 개발자에게 평온함을 가져다준다고 주장합니다.
*   **복잡한 데이터 직렬화**: OOP에서 JSON 직렬화 및 역직렬화의 어려움을 설명하며, 데이터를 처리하기 위해 많은 클래스와 코드가 필요하다고 지적합니다. OOP에서 데이터가 클래스 멤버로 잠겨 있어 일반적인 데이터 접근이 어렵다는 점을 비판합니다.
*   **복잡한 클래스 계층**: 새로운 요구 사항이 발생했을 때 클래스 상속의 문제점을 설명하며, 특히 다중 상속으로 인한 "다이아몬드 문제"를 언급합니다. OOP에서 클래스 상속보다 구성(composition)을 선호해야 함을 강조합니다.
*   **사례 연구: Klafim's Library Management System**: OOP의 복잡성을 설명하기 위해 가상의 도서관 관리 시스템 프로젝트를 사용합니다. VIP 멤버 및 Super 멤버 추가와 관련된 요구 사항 변경이 클래스 계층에 미치는 영향을 분석합니다.

## 부차 화제

다음은 문서에 언급된 부차적인 주제들입니다.

*   **테오의 커피 취향:** 카푸치노를 마시는 모습이 언급되며, 이는 가벼운 유머 또는 상황 설정의 요소로 작용합니다.

*   **함수형 프로그래밍 (FP):** DOP와 유사하게 OOP의 문제점을 지적하지만, 접근 방식에서 차이가 있음을 언급합니다.
*   **Klafim 도서 관리 시스템:** OOP의 복잡성을 설명하기 위한 예시 프로젝트로 사용됩니다.
*   **다중 스레드 환경:** 객체의 가변성이 코드의 예측 불가능성을 초래하는 상황을 설명하는 데 사용됩니다.
*   **동시성 안전 메커니즘 (뮤텍스):** OOP에서 가변성으로 인한 문제를 해결하기 위한 방법으로 언급되지만, 성능 저하 및 데드락 위험 등의 단점이 지적됩니다.
*   **JSON 직렬화/역직렬화의 어려움:** OOP에서 데이터가 클래스에 갇혀 있어 일반적인 접근이 어렵다는 점을 설명하는 데 사용됩니다.
*   **클래스 상속과 구성:** 클래스 상속의 문제점을 지적하고, 구성 (composition)을 대안으로 제시합니다.
*   **다이아몬드 문제 (Deadly Diamonds of Death):** 다중 상속으로 인해 발생하는 모호성 문제를 언급합니다.
*   **사용자 인터페이스 (REST API, JSON):** JSON을 이용한 REST API를 구축하는 과정에서 OOP의 복잡성이 드러나는 상황을 제시합니다.
*   **코드 재사용:** OOP에서 코드 재사용이 어려울 수 있다는 점을 지적하며, VIP 멤버와 사서의 기능을 예시로 설명합니다.
*   **소프트웨어 개발 일정 및 마감일:** 새로운 기능 추가로 인해 마감일을 지키지 못하는 상황을 묘사하며, 소프트웨어 개발의 현실적인 어려움을 보여줍니다.
*   **소프트웨어 제품 출시 및 시장 반응:** 새로운 제품의 출시와 시장 반응에 대한 언급은 프로젝트의 성공 여부와 관련된 불확실성을 나타냅니다.
*   **비즈니스 파트너십:** 비즈니스 파트너와의 회의 결과가 시스템 요구 사항 변경에 영향을 미치는 상황을 보여줍니다.

## 1.2_Sources_of_complexity

1.2
Sources of complexity
While Theo is getting himself another cup of coffee (a cappuccino this time), I
would like to challenge his design. It might look beautiful and clear on the paper,
but I claim that this design makes the system hard to understand. It's not that Theo
picked the wrong classes or that he misunderstood the relations among the classes.
It goes much deeper:
It's about the programming paradigm he chose to implement the system.
It's about the object-oriented paradigm.
It's about the tendency of OOP to increase the complexity of a system.
TIP
OOP has a tendency to create complex systems.
Throughout this book, the type of complexity I refer to is that which makes systems
hard to understand as defined in the paper, "Out of the Tar Pit," by Ben Moseley
and Peter Marks (2006), available at http://mng.bz/enzq. It has nothing to do with
the type of complexity that deals with the amount of resources consumed by a pro-
gram. Similarly, when I refer to simplicity, I mean not complex (in other words, easy
to understand).
 Keep in mind that complexity and simplicity (like hard and easy) are not absolute
but relative concepts. We can compare the complexity of two systems and determine
whether system A is more complex (or simpler) than system B.
 NOTE
Complexity in the context of this book means hard to understand.
As mentioned in the introduction of this chapter, there are many ways in OOP to
alleviate complexity. The purpose of this book is not be critical of OOP, but rather
to present a programming paradigm called data-oriented programming (DOP) that
tends to build systems that are less complex. In fact, the DOP paradigm is compati-
ble with OOP.
 If one chooses to build an OOP system that adheres to DOP principles, the system
will be less complex. According to DOP, the main sources of complexity in Theo's sys-
tem (and of many traditional OOP systems) are that
Code and data are mixed.
Objects are mutable.
Data is locked in objects as members.
Code is locked into classes as methods.
This analysis is similar to what functional programming (FP) thinks about traditional
OOP. However, as we will see throughout the book, the data approach that DOP takes
in order to reduce system complexity differs from the FP approach. In appendix A, we
illustrate how to apply DOP principles both in OOP and in FP styles.
TIP
DOP is compatible both with OOP and FP.
