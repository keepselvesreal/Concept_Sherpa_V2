## 7.4 Schema Composition: JSON Schema의 유연성 확장

### 7.4.1 상황 소개: 외부 API 데이터 검증

*   **문제 제기:** 외부 웹 서비스에서 제공하는 데이터의 유효성 검증 필요. 예시: Open Library Books API.
*   **예시 데이터:** "Watchmen" 책의 Open Library Books API 응답 JSON 데이터.
*   **초기 시도:** API 응답 구조에 맞는 JSON Schema를 작성하여 기본적인 유효성 검증 수행.
*   **문제점:** `isbn_10`과 `isbn_13` 필드의 필수 여부 문제 발생. 책의 출판 시기에 따라 두 필드 중 하나 또는 둘 다 존재할 수 있음.

### 7.4.2 JSON Schema Composition의 필요성

*   **목표:** `isbn_10` 또는 `isbn_13` 중 적어도 하나는 반드시 존재해야 하고, 기본 정보(title 등)도 항상 존재해야 함을 표현하는 유효성 검증 규칙 구현.
*   **해결책:** JSON Schema Composition을 활용하여 복잡한 유효성 검증 규칙을 표현.

### 7.4.3 JSON Schema Composition의 개념

*   **개념:** 여러 스키마를 조합하여 더 복잡한 규칙을 정의하는 방법. 논리 연산(AND, OR, NOT)과 유사한 방식으로 스키마를 결합.
*   **연산자:**
    *   `allOf`: 모든 스키마를 만족해야 함 (AND).
    *   `anyOf`: 스키마 중 적어도 하나를 만족해야 함 (OR).
    *   `oneOf`: 정확히 하나의 스키마를 만족해야 함.

### 7.4.4 Open Library Books API 응답 스키마 예시

*   **기본 스키마 (`basicBookInfoSchema`):** `title`을 필수 필드로 하고, 다른 필드(publishers, number_of_pages 등)의 데이터 유형을 정의.
*   **`mandatoryIsbn13` 스키마:** `isbn_13`을 필수 필드로 정의.
*   **`mandatoryIsbn10` 스키마:** `isbn_10`을 필수 필드로 정의.
*   **결합된 스키마 (`bookInfoSchema`):**
    *   `allOf`: `basicBookInfoSchema`를 만족해야 함.
    *   `anyOf`: `mandatoryIsbn13` 또는 `mandatoryIsbn10` 중 하나를 만족해야 함.
*   **결과:** `title`이 필수이고, `isbn_10` 또는 `isbn_13` 중 하나 이상이 존재해야 함을 나타내는 스키마 완성.

### 7.4.5 Schema Composition의 장점

*   **유연성:** 기존 JSON Schema의 단일 스키마만으로는 표현하기 어려운 복잡한 유효성 검증 규칙을 정의할 수 있음.
*   **표현력 향상:** 데이터의 유효성 검증 조건을 클래스 기반의 데이터 표현 방식보다 더 효과적으로 표현 가능.

### 7.4.6 추가 고려사항

*   **검증 실패 시 문제 파악 어려움:**  검증 실패 시 어떤 스키마에서 문제가 발생했는지 명확하게 알기 어려울 수 있음. (추후 개선 필요)
*   **더 많은 기능:** JSON Schema는 이후 챕터에서 다루는 고급 데이터 유효성 검증 기능을 제공.
