## 7 Basic Data Validation 상세 정리

### 7.1 Data Validation in DOP

*   **핵심 개념**: 데이터 중심 프로그래밍(DOP)에서 데이터 유효성 검사의 중요성을 강조하며, 특히 시스템 경계에서의 데이터 검증을 다룬다.
*   **DOP와 데이터 유효성 검증**: DOP는 데이터 유효성 검증을 강제하지 않지만, 데이터를 검증하는 것을 권장한다.
*   **시스템 경계**: 시스템이 데이터를 교환하는 영역. 예시: 클라이언트-서버 경계, 데이터베이스 경계, 웹 서비스 경계.
*   **유효성 검증 유형**:
*   **경계에서의 유효성 검증**: 시스템으로 들어오고 나가는 데이터의 유효성을 검증하여 무효한 데이터의 유입 및 유출을 방지한다.
*   **내부에서의 유효성 검증**: 코드베이스가 커짐에 따라 개발 편의성을 위해 사용된다.
*   **주요 목적**: 무효한 데이터의 유입/유출 방지, 유효하지 않은 데이터를 만났을 때 유용한 오류 메시지 제공.
*   **권장 사항**: 시스템 경계에서 데이터 유효성 검증이 이루어지면, 내부에서의 추가 검증은 필수적이지 않다.

### 7.2 JSON Schema in a Nutshell

*   **JSON Schema 소개**: 데이터의 스키마를 JSON 형식으로 정의하는 언어.
*   **핵심 개념**: 데이터 표현과 데이터 스키마를 분리한다. 스키마는 데이터의 구조와 유효성 규칙을 정의하고, 데이터는 이 규칙에 따라 검증된다.
*   **JSON Schema의 구성**:
*   `type`: 데이터 유형(예: object, string, array).
*   `properties`: 객체의 필드에 대한 스키마 정의. 각 필드에 대한 `type` 정의를 포함한다.
*   `items`: 배열 내 요소의 스키마 정의.
*   `enum`: 허용되는 값의 목록을 정의 (열거형).
*   `required`: 필수 필드 목록.
*   **JSON Schema 유효성 검증**: JSON Schema validator 라이브러리를 사용하여 데이터를 스키마에 따라 검증.
*   **JSON Schema의 장점**: 언어 독립적이며, 클래스를 사용하여 데이터를 표현할 때보다 더 복잡한 유효성 검사 조건을 표현할 수 있다.

### 7.3 Schema Flexibility and Strictness

*   **JSON Schema의 유연성**: 스키마는 JSON 객체이므로, 변수에 할당하거나, 다른 스키마에서 재사용하는 등, 프로그래밍 방식으로 조작 가능하다.
*   **필드의 선택성**: JSON Schema에서 객체의 필드는 기본적으로 선택 사항이다. `required` 배열을 사용하여 필수 필드를 지정한다.
*   **추가 속성**:
*   `additionalProperties`: 스키마에 정의되지 않은 필드의 허용 여부를 결정한다. 기본적으로 `true`로 설정되어 있으며, 추가 필드를 허용한다.
*   `additionalProperties: false`로 설정하면 스키마에 정의되지 않은 필드를 허용하지 않는다.
*   **권장 사항**:
*   보내는 데이터는 엄격하게 검증하고, 받는 데이터는 유연하게 처리한다. (“Be conservative in what you send, be liberal in what you accept.")

### 7.4 Schema Composition

*   **JSON Schema의 조합**: AND, OR, NOT과 같은 논리 연산을 사용하여 스키마를 조합할 수 있다.
*   **조합 연산자**:
*   `allOf`: 모든 스키마를 만족해야 함 (AND).
*   `anyOf`: 하나 이상의 스키마를 만족해야 함 (OR).
*   `oneOf`: 정확히 하나의 스키마를 만족해야 함 (자세한 내용은 생략된 부분 참조)
*   **예시**: ISBN 10 또는 ISBN 13이 필수인 경우.

### 7.5 Details about Data Validation Failures

*   **유효성 검증 실패 정보**: JSON Schema validator 라이브러리는 유효성 검증 실패에 대한 상세 정보를 제공한다.
*   **오류 정보 접근**: 각 라이브러리(예: Ajv)는 자체적인 방식으로 오류 정보를 제공. 일반적으로 오류 배열 형태로 제공된다.
*   **오류 정보 구조**:
*   `instancePath`: 오류가 발생한 데이터 경로.
*   `schemaPath`: 오류가 발생한 스키마 경로.
*   `keyword`: 오류를 발생시킨 JSON Schema 키워드 (예: required, type).
*   `params`: 오류에 대한 추가 파라미터.
*   `message`: 오류에 대한 설명.
*   **Ajv의 특징**:
*   기본적으로 첫 번째 오류만 감지.
*   `allErrors: true` 옵션을 사용하여 모든 오류를 감지할 수 있다.
*   `errorsText()` 유틸리티 함수를 사용하여 오류를 사람이 읽을 수 있는 형식으로 변환한다.

구성노드1: 7.1 Data Validation in DOP:

*   **개선된 상세 핵심 내용**: 데이터 중심 프로그래밍(DOP)에서 데이터 유효성 검증의 중요성을 강조하며, 시스템 경계에서의 데이터 검증에 초점을 맞춘다.
*   **핵심 개념**:
    *   DOP는 데이터 유효성 검증을 강제하지 않지만, 권장한다. 이는 데이터의 무결성을 유지하고 예상치 못한 오류를 방지하는 데 기여한다.
    *   **시스템 경계**: 데이터가 시스템 외부로 나가거나 들어오는 지점 (예: API endpoint, 데이터베이스 인터페이스, 메시지 큐). 이러한 경계에서 데이터 검증은 특히 중요하며, 잘못된 데이터로 인한 문제 발생을 최소화한다.
*   **DOP와 데이터 유효성 검증**: DOP 원칙에 따라, 데이터는 명확하게 정의되고 관리되어야 한다. 데이터 유효성 검증은 이러한 원칙을 뒷받침하며, 데이터의 신뢰성을 확보하는 핵심적인 방법이다.
*   **유효성 검증 유형**:
    *   **경계에서의 유효성 검증**: 외부로부터 유입되는 데이터가 시스템의 기대와 일치하는지 확인하고, 시스템에서 외부로 전송되는 데이터가 올바른 형식과 내용으로 구성되었는지 검증한다.
    *   **내부에서의 유효성 검증**: 시스템 내부의 코드 복잡성이 증가함에 따라, 내부 데이터의 일관성을 유지하고 오류를 조기에 감지하기 위해 사용된다. 불변성 유지를 위한 방어 메커니즘으로 활용할 수 있다.
*   **주요 목적**:
    *   **무효한 데이터의 유입/유출 방지**: 시스템 경계에서 유효성 검증을 수행하여, 잘못된 데이터가 시스템에 영향을 미치지 않도록 보호한다.
    *   **유용한 오류 메시지 제공**: 유효하지 않은 데이터가 감지될 경우, 개발자와 사용자에게 문제의 원인을 명확하게 설명하는 오류 메시지를 제공하여 문제 해결을 돕는다.
*   **권장 사항**: 시스템 경계에서 강력한 데이터 유효성 검증을 수행하면, 내부 검증의 필요성은 줄어들 수 있다. 그러나 내부 데이터의 일관성을 유지하기 위해 선택적으로 내부 유효성 검증을 적용할 수 있다.

구성노드2: 7.2 JSON Schema in a nutshell:

*   **개선된 상세 핵심 내용**: JSON Schema는 JSON 데이터의 구조와 유효성을 정의하는 강력한 도구로서, 데이터 유효성 검증을 위한 효율적인 방법을 제공한다.
*   **JSON Schema 소개**: JSON 데이터의 스키마를 JSON 형식으로 정의하여 데이터 구조를 명확하게 하고, 데이터 유효성을 검증할 수 있도록 한다.
*   **핵심 개념**:
    *   **데이터 표현과 스키마 분리**: 데이터 자체와 데이터의 구조 및 규칙을 분리함으로써, 데이터 구조 변경에 유연하게 대처하고, 다양한 데이터 형식에 대해 일관된 유효성 검증을 수행할 수 있다.
    *   스키마는 데이터의 구조(필드, 타입, 관계 등)와 유효성 규칙(필수 여부, 허용 값 등)을 정의한다.
    *   데이터는 정의된 스키마에 따라 검증되며, 유효하지 않은 데이터는 거부되거나 적절한 오류를 발생시킨다.
*   **JSON Schema의 구성**:
    *   `type`: 데이터의 기본 유형(예: `object`, `string`, `array`, `number`, `boolean`, `null`).
    *   `properties`: 객체 내 각 필드의 스키마를 정의. 각 필드의 `type`을 포함하여 세부적인 유효성 규칙을 지정할 수 있다.
    *   `items`: 배열 내 요소의 스키마를 정의. 배열 내 모든 요소가 동일한 유형을 가질 경우 유용하다.
    *   `enum`: 허용되는 값들의 목록을 정의 (열거형). 특정 값들만 허용하도록 제한한다.
    *   `required`: 객체에서 반드시 포함되어야 하는 필수 필드 목록을 정의.
    *   **추가 키워드**: `format`, `minLength`, `maxLength`, `pattern` 등 다양한 키워드를 사용하여 더 세밀한 유효성 검증 규칙을 정의할 수 있다.
*   **JSON Schema 유효성 검증**: JSON Schema validator 라이브러리 (예: Ajv, tv4)를 사용하여 JSON 데이터를 스키마에 따라 검증한다.
*   **JSON Schema의 장점**:
    *   **언어 독립성**: JSON 형식으로 정의되므로, 다양한 프로그래밍 언어에서 사용할 수 있다.
    *   **표현력**: 클래스를 사용하여 데이터를 표현하는 것보다 더 복잡하고 유연한 유효성 검사 조건을 정의할 수 있다. (예: 정규 표현식, 범위 검사)
    *   **재사용성**: 스키마를 재사용하고, 조합하여 복잡한 데이터 구조를 표현할 수 있다.

구성노드3: 7.3 Schema flexibility and strictness:

*   **개선된 상세 핵심 내용**: 데이터 유효성 검증 시, 보내는 데이터는 엄격하게, 받는 데이터는 유연하게 처리하는 전략을 통해 시스템의 안정성과 유연성을 확보한다.
*   **JSON Schema의 유연성**: JSON Schema는 JSON 객체이므로, 변수에 할당하거나, 다른 스키마에서 재사용하는 등, 프로그래밍 방식으로 유연하게 조작하고 관리할 수 있다.
*   **필드의 선택성**: JSON Schema에서 객체의 필드는 기본적으로 선택 사항(optional)으로 간주된다.
    *   `required` 배열을 사용하여 필수 필드를 명시적으로 지정한다.
*   **추가 속성**:
    *   `additionalProperties`: 스키마에 정의되지 않은 필드의 허용 여부를 결정한다.
        *   기본적으로 `true`로 설정되어 있어, 스키마에 정의되지 않은 필드를 허용한다.
        *   `additionalProperties: false`로 설정하면, 스키마에 정의되지 않은 필드를 허용하지 않도록 엄격하게 제한할 수 있다.
*   **권장 사항**:
    *   **보내는 데이터는 엄격하게 검증**: 시스템에서 외부로 전송하는 데이터는 엄격한 스키마 검증을 통해 정확성과 완전성을 보장한다. 이는 외부 시스템에서 데이터 처리 오류를 방지하고, 시스템 간의 상호 운용성을 향상시킨다.
    *   **받는 데이터는 유연하게 처리**: ("Be conservative in what you send, be liberal in what you accept.") 시스템이 외부에서 데이터를 수신할 때는, 유연하게 처리하여, 사소한 스키마 불일치로 인해 데이터 처리가 실패하는 상황을 최소화한다. 예를 들어, 새로운 필드가 추가되어도 기존 로직에 영향을 미치지 않도록 설계할 수 있다.

구성노드4: 7.4 Schema composition:

*   **개선된 상세 핵심 내용**: JSON Schema의 조합 기능을 활용하여, 복잡한 데이터 구조와 유효성 규칙을 간결하고 효율적으로 정의한다.
*   **JSON Schema의 조합**: AND, OR, NOT과 같은 논리 연산을 사용하여 스키마를 조합하여, 보다 복잡한 데이터 구조와 유효성 규칙을 정의할 수 있다.
*   **조합 연산자**:
    *   `allOf`: 모든 스키마를 만족해야 함 (AND). 모든 조건을 만족해야만 유효한 데이터로 간주된다.
    *   `anyOf`: 하나 이상의 스키마를 만족해야 함 (OR). 적어도 하나의 조건을 만족하면 유효한 데이터로 간주된다.
    *   `oneOf`: 정확히 하나의 스키마를 만족해야 함. (자세한 내용은 생략된 부분 참조): 정확히 하나의 조건을 만족해야 한다. 여러 조건을 만족하거나, 아무 조건도 만족하지 않으면 유효하지 않다.
    *   `not`: 지정된 스키마를 만족하지 않아야 함.
*   **예시**: ISBN 10 또는 ISBN 13이 필수인 경우: `anyOf`를 사용하여, ISBN 10 형식의 스키마 또는 ISBN 13 형식의 스키마를 만족하는 경우 유효한 것으로 정의할 수 있다.

구성노드5: 7.5 Details about data validation failures:

*   **개선된 상세 핵심 내용**: 데이터 유효성 검증 실패 시 발생하는 오류 정보를 이해하고, 이를 효과적으로 활용하여 문제 해결 및 사용자 경험 향상에 기여한다.
*   **유효성 검증 실패 정보**: JSON Schema validator 라이브러리는 유효성 검증 실패에 대한 상세 정보를 제공하여, 문제의 원인을 파악하고 수정하는 데 도움을 준다.
*   **오류 정보 접근**: 각 JSON Schema validator 라이브러리(예: Ajv, tv4)는 자체적인 방식으로 오류 정보를 제공한다. 일반적으로 오류 객체의 배열 형태로 제공된다.
*   **오류 정보 구조**:
    *   `instancePath`: 오류가 발생한 데이터 경로. (예: `"/address/street"`) 오류가 발생한 데이터 내 위치를 나타낸다.
    *   `schemaPath`: 오류를 발생시킨 스키마 경로. (예: `"/properties/street/type"`) 오류와 관련된 스키마 내 위치를 나타낸다.
    *   `keyword`: 오류를 발생시킨 JSON Schema 키워드 (예: `required`, `type`, `minLength`). (예: `type`은 데이터 타입 불일치, `required`는 필수 필드 누락을 의미)
    *   `params`: 오류에 대한 추가 파라미터. (예: `minLength`의 경우, 최소 길이를 초과하지 못한 문자열의 실제 길이)
    *   `message`: 오류에 대한 설명. (예: "must be string" - 타입 오류)
*   **Ajv의 특징**:
    *   기본적으로 첫 번째 오류만 감지. (성능 최적화를 위해)
    *   `allErrors: true` 옵션을 사용하여 모든 오류를 감지하도록 설정 가능. (모든 오류를 한 번에 확인하고 싶을 때)
    *   `errorsText()` 유틸리티 함수를 사용하여 오류를 사람이 읽을 수 있는 형식으로 변환하여, 오류 메시지의 가독성을 높인다. (예: "address.street must be string")
    *   **실용적인 내용 추가**: 오류 정보를 활용하여 사용자에게 더 친절하고 구체적인 오류 메시지를 제공함으로써, 데이터 입력 오류를 쉽게 수정하도록 돕고, 사용자 경험을 향상시킬 수 있다. 예를 들어, 잘못된 입력 필드를 강조하거나, 올바른 형식의 예시를 제공할 수 있다.

구성노드6: Summary:

*   **개선된 상세 핵심 내용**: 데이터 유효성 검증은 DOP의 핵심 원칙을 실천하고 데이터 품질을 보장하는 중요한 방법이다. JSON Schema는 유연하고 강력한 도구로서 데이터 검증을 효율적으로 수행하도록 돕는다.
*   **요약**:
    *   DOP에서 데이터 유효성 검증은 데이터의 신뢰성을 확보하고, 시스템의 안정성을 유지하는 데 필수적이다.
    *   JSON Schema는 데이터의 구조와 유효성 규칙을 정의하고, 데이터 검증을 수행하는 데 매우 효과적인 도구이다.
    *   엄격한 검증과 유연한 처리를 통해 데이터의 무결성을 보장하고 시스템의 유연성을 확보한다.
    *   오류 정보를 효과적으로 활용하여 사용자 경험을 개선하고, 문제 해결을 돕는다.
*   **학습 목표**: 이 자료를 통해,
    *   데이터 유효성 검증의 중요성을 이해하고, DOP 원칙에 따라 데이터 검증을 적용할 수 있다.
    *   JSON Schema를 사용하여 JSON 데이터의 구조를 정의하고 유효성을 검증하는 방법을 익힌다.
    *   엄격한 검증과 유연한 처리를 통해 데이터 품질을 관리하는 방법을 습득한다.
    *   유효성 검증 실패 시 발생하는 오류 정보를 분석하고, 문제 해결 및 사용자 경험 향상에 활용할 수 있다.
