## 7 Basic Data Validation - 추가 상세 정보 및 새로운 내용 정리

다음은 "7 Basic data validation" 내용에서 추출한 추가적인 상세 정보와 새로운 내용입니다. 기존 핵심 내용 요약에 포함되지 않은 내용들을 중심으로 정리했습니다.

**1. DOP 원칙 및 데이터 검증의 중요성 재강조**

*   **DOP 원칙 #4 재확인 (915행):** 데이터 스키마와 데이터 표현의 분리. 이 원칙은 DOP에서 데이터 검증을 가능하게 하며, 데이터 구조와 검증 로직을 분리하여 유연성을 제공합니다.

**2. 시스템 경계 및 데이터 교환 (916-918행):**

*   **시스템 경계의 정의:** 시스템이 데이터를 교환하는 모든 지점. 예를 들어, 웹 서버의 경우 클라이언트, 데이터베이스, 외부 웹 서비스와의 통신 지점이 경계가 됩니다. 그림 7.1 (170페이지)에서 웹 서버 아키텍처를 예시로 보여줌.

**3. 경계에서의 검증 예시 및 목적 (919-921, 925-927행):**

*   **경계 검증 예시:** 클라이언트 요청, 데이터베이스 응답, 외부 웹 서비스 응답 등 시스템 외부와의 데이터 교환 지점에서 데이터의 유효성을 검사합니다.
*   **경계 검증의 목적:** 시스템으로 유효하지 않은 데이터가 들어오거나 나가는 것을 막고, 오류 발생 시 사용자에게 이해하기 쉬운 방식으로 오류를 표시합니다.
*   **내부 검증의 필요성 (926행):** 경계에서 검증이 이루어진 경우 내부에서의 검증은 선택사항이 될 수 있지만, 코드의 유지 보수성을 높이기 위해 내부 검증을 수행할 수 있습니다.

**4. JSON Schema 상세 정보 (927-937행):**

*   **JSON Schema의 특징:**
*   **언어 독립성:** 다양한 프로그래밍 언어에서 사용할 수 있는 JSON 기반 스키마 정의 언어입니다. (177페이지 표 7.2 참고)
*   **표현력:** 클래스 기반 데이터 구조보다 훨씬 강력한 유효성 검사 조건을 표현할 수 있습니다. (예: 범위, 정규식 등)
*   **구조:** JSON 객체를 사용하여 스키마를 정의하며, `type`, `properties`, `required`, `items`, `enum`, `additionalProperties` 등의 키워드를 사용합니다. (172-175페이지에서 예시 확인)
*   **조작성:** JSON 객체이므로 스키마를 변수에 저장하고, 다른 스키마를 구성하는 데 사용할 수 있습니다. (179페이지)

**5. JSON Schema 예시 (171-181페이지):**

*   **검색 요청 스키마:** (171-176페이지, Listing 7.1-7.6)
*   `type: "object"` (map)
*   `properties`:  `title: {type: "string"}`, `fields: {type: "array", items: {enum: [...]}}`
*   `required: ["title", "fields"]`
*   **검색 응답 스키마:** (177-179페이지, Listing 7.10-7.12)
*   `type: "array"` (배열)
*   `items`: `{type: "object", required: ["title", "available"], properties: {...}}`
*   `bookInfoSchema` (스키마 재사용)
*   **데이터베이스 응답 스키마:** (180-181페이지, Listing 7.13-7.15)
*   `type: "array"`
*   `items`: `{type: "object", required: ["title", "isbn", "available"], additionalProperties: false, properties: {...}}`
*   `additionalProperties: false` (추가 속성 허용 여부)

**6. JSON Schema의 유연성 및 엄격성 (935-941행):**

*   **필드 기본값:** JSON Schema에서는 맵의 필드가 기본적으로 선택 사항입니다. 필수 필드는 `required` 배열에 명시해야 합니다.
*   **추가 속성 (additionalProperties):**  JSON Schema에서 `additionalProperties`를 `false`로 설정하면 스키마에 정의되지 않은 추가 필드를 허용하지 않습니다. 요청에서는 유연하게, 응답에서는 엄격하게 설정하는 것이 좋습니다.
*   **데이터 전송 원칙:** "보내는 데이터는 엄격하게, 받는 데이터는 유연하게"

**7. Schema composition (182-185페이지):**

*   **스키마 조합 (allOf, anyOf):** 여러 스키마를 조합하여 더 복잡한 유효성 검사 조건을 만들 수 있습니다. (183-185페이지, Listing 7.18-7.19)
*   `allOf`: 모든 스키마를 만족해야 함 (AND)
*   `anyOf`: 최소한 하나의 스키마를 만족해야 함 (OR)
*   `oneOf`: 정확히 하나의 스키마를 만족해야 함 (NOT 언급)

**8. 데이터 검증 실패 정보 (923-925, 186-188페이지):**

*   **상세 오류 정보:** JSON Schema 유효성 검사 실패 시, 실패 이유에 대한 상세 정보를 얻을 수 있습니다.
*   **Ajv (JavaScript JSON Schema Validator) 예시:**

*   `ajv.errorsText(ajv.errors)` 함수를 사용하여 오류 정보를 사람이 읽기 쉬운 형식으로 변환할 수 있습니다. (Listing 7.22)
*   `allErrors: true` 옵션을 사용하여 여러 오류를 한 번에 감지할 수 있습니다. (Listing 7.23)

**9. JSON Schema Cheat Sheet (188-189페이지):**

*   간결한 JSON Schema 정의 예시와 유효한 데이터 예시를 제공하여 JSON Schema 학습에 도움을 줍니다. (Listing 7.24-7.25)

구성노드1(7.1 Data validation in DOP): ## 7.1 Data validation in DOP 분석 및 추가 정보 정리
이 문서에서는 DOP(Data-Oriented Programming)에서의 데이터 유효성 검증에 대한 내용을 다루고 있습니다. OOP(Object-Oriented Programming)와 비교하여 DOP에서 데이터 유효성 검증의 중요성과 방법에 대한 설명을 제공합니다.
**핵심 내용 요약:**
*   **DOP에서의 데이터 유효성 검증의 필요성:** OOP와 달리 DOP에서는 데이터 구조가 유연하기 때문에, 데이터 필드 이름이나 타입에 작은 실수로 인해 데이터 일관성 문제가 발생할 수 있습니다.
*   **시스템 경계에서의 데이터 유효성 검증의 중요성:** DOP에서는 시스템 경계에서 데이터 유효성 검증을 가장 중요하게 생각합니다. 시스템 경계는 클라이언트, 데이터베이스, 웹 서비스 등과 같이 시스템이 데이터를 주고받는 영역을 의미합니다.
*   **시스템 경계와 내부 데이터 유효성 검증의 구분:** 시스템 경계에서의 데이터 유효성 검증은 주로 유효하지 않은 데이터의 유입 및 유출을 막는 것을 목표로 하며, 내부 데이터 유효성 검증은 개발 편의성을 위해 사용됩니다.
*   **데이터 유효성 검증 목적:**
*   **경계:** 유효하지 않은 데이터의 유입/유출 방지 및 오류 정보 표시
*   **내부:** 개발 용이성 (코드베이스가 커질 때)
**추가적인 상세 정보 및 새로운 내용:**
1.  **데이터 유효성 검증의 중요성 강조:**
*   **OOP와의 비교:** OOP에서는 클래스 인스턴스화 시 멤버 필드의 이름과 타입이 보장되지만, DOP에서는 이 보장이 없기 때문에 데이터 유효성 검증이 더욱 중요합니다.
*   **문제 발생 가능성:** 필드 이름이나 타입의 작은 실수로 인해 데이터 일관성 문제가 발생할 수 있습니다.
2.  **시스템 경계의 정의 및 예시:**
*   **정의:** 시스템이 데이터를 주고받는 영역
*   **예시:**
*   **클라이언트 경계:** 웹 브라우저와 같은 클라이언트
*   **데이터베이스 경계:** 데이터베이스와의 통신
*   **웹 서비스 경계:** 웹 서비스와의 통신
3.  **시스템 경계에서의 데이터 유효성 검증의 구체적인 목적:**
*   **유효하지 않은 데이터의 유입/유출 방지:** 시스템에 들어오거나 나가는 데이터의 무결성을 유지합니다.
*   **오류 정보 표시:** 유효하지 않은 데이터가 발견될 경우, 사용자에게 정확하고 이해하기 쉬운 오류 메시지를 제공합니다.
4.  **두 가지 종류의 데이터 유효성 검증의 차이점 (Table 7.1):**
*   **경계:**
*   **목적:** 유효하지 않은 데이터의 유입/유출 방지 및 오류 정보 표시
*   **환경:** 프로덕션 환경에서 데이터의 무결성을 유지 (Guardian 역할)
*   **내부:**
*   **목적:** 개발 편의성
*   **환경:** 개발 환경에서 코드의 가독성과 유지 보수성을 향상 (개발 편의성)
5.  **DOP에서의 데이터 유효성 검증의 구현 방식 (암시적):**
*   DOP에서는 데이터 스키마와 데이터 표현이 분리되어 있기 때문에, JSON Schema와 같은 스키마 정의 언어를 활용하여 데이터 유효성 검증을 구현할 수 있습니다. (7.2 절에서 자세히 다룰 예정)
*   시스템 경계에서 JSON Schema를 사용하여 데이터의 구조와 타입을 정의하고, 들어오고 나가는 데이터를 이 스키마에 따라 검증합니다.
**결론:**
이 챕터는 DOP에서 데이터 유효성 검증의 필요성을 강조하고, 시스템 경계에서의 검증의 중요성을 설명합니다. 또한, 두 종류의 데이터 유효성 검증의 목적과 환경을 비교하고, 다음 챕터에서 JSON Schema를 활용한 구체적인 구현 방법을 제시할 것을 암시합니다.
구성노드2(7.2 JSON Schema in a nutshell): ## 7.2 JSON Schema in a nutshell 상세 정보 및 새로운 내용 분석
이 내용은 JSON Schema의 기본적인 개념과 사용법을 소개하는 챕터입니다. 다음은 해당 내용에서 추가적으로 파악할 수 있는 상세 정보와 새로운 내용입니다.
**1. JSON Schema의 역할과 중요성:**
*   **데이터 유효성 검사:** JSON Schema는 데이터 표현(data representation)과 데이터 스키마(data schema)를 분리하여, 데이터가 스키마에 정의된 규칙을 준수하는지 검사하는 데 사용됩니다.
*   **DOP(Data Oriented Programming)에서의 중요성:** 데이터 스키마는 데이터 유효성 검사의 핵심이며, DOP 패러다임에서 데이터의 정확성을 보장하는 데 중요한 역할을 합니다.
*   **언어 독립성:** JSON Schema는 언어에 독립적이며, 다양한 프로그래밍 언어에서 사용할 수 있는 유효성 검사 라이브러리가 존재합니다.
**2. JSON Schema의 기본 구조:**
*   **최상위 구조:** JSON Schema는 JSON 객체이며, "type"과 "properties" 필드를 갖습니다.
*   `type`: 데이터의 유형을 정의합니다 (예: "object", "string", "array").
*   `properties`: 객체 내 필드의 스키마를 정의합니다.
*   **객체(object) 타입 스키마:**
*   `type`: "object"
*   `properties`: 객체의 각 필드에 대한 스키마 정의
*   **배열(array) 타입 스키마:**
*   `type`: "array"
*   `items`: 배열의 각 요소에 대한 스키마 정의
*   **ENUM 사용:** "enum" 키워드를 사용하여 허용되는 값의 목록을 지정합니다. (예: `{"enum": ["value1", "value2"]}`).
*   **필수(required) 필드 지정:** "required" 필드를 사용하여 필수 필드를 정의합니다. (예: `{"required": ["field1", "field2"]}`).
**3. JSON Schema를 사용한 검색 요청 스키마 예시:**
*   **검색 요청 데이터:**
```json
{
"title": "habit",
"fields": ["title", "weight", "number_of_pages"]
}
```
*   **검색 요청 스키마:**
```json
var searchBooksRequestSchema = {
"type": "object",
"properties": {
"title": {"type": "string"},
"fields": {
"type": "array",
"items": {
"enum": [
"publishers",
"number_of_pages",
"weight",
"physical_format",
"subjects",
"publish_date",
"physical_dimensions"
]
}
}
},
"required": ["title", "fields"]
};
```
**4. JSON Schema 유효성 검사:**
*   **유효성 검사 라이브러리:** 다양한 프로그래밍 언어에서 JSON Schema 유효성 검사 라이브러리를 사용할 수 있습니다. (예: Ajv (JavaScript), Snow (Java), JSON.net Schema (C#), jschon (Python), JSONSchemer (Ruby))
*   **validate 함수:**  일반적으로 유효성 검사 라이브러리는 스키마와 데이터를 입력으로 받아 유효성 검사 결과를 반환하는 `validate` 함수를 제공합니다. (유효하면 `true`, 유효하지 않으면 `false`)
*   **유효하지 않은 경우:** 유효성 검사 실패 시 오류 정보를 얻는 방법은 언급되지 않았지만, 이후 챕터에서 다룰 예정임을 암시합니다.
**5. JSON Schema의 장점:**
*   **언어 독립성:** 여러 프로그래밍 언어에서 사용 가능.
*   **표현력:** 클래스 기반의 데이터 정의보다 훨씬 더 복잡한 유효성 검사 조건을 표현할 수 있습니다. (예: 숫자 범위, 정규 표현식)
**6. 추가적인 내용:**
*   **스키마 구성(schema composition):** 아직 자세히 다루지 않았지만, 나중에 소개될 예정입니다.
*   **고급 유효성 검사:** 숫자 범위, 정규 표현식 등을 사용한 유효성 검사를 포함하며, 챕터 12에서 다룰 예정입니다.
*   **오류 정보:** 유효성 검사 실패 시 오류에 대한 상세 정보를 얻는 방법은 이후에 다룰 예정입니다.
*   **응답 유효성 검사:** 서버 응답의 유효성을 검사하는 방법에 대한 간략한 언급이 있었습니다.
**7. 새로운 내용 (구체적인 예시나 구현 방법 등):**
*   JSON Schema의 기본 요소들을 조합하여 복잡한 데이터 구조를 정의하는 방법을 보여줍니다.
*   JSON Schema를 사용하여 API 요청과 응답의 형식을 정의하고, 데이터 유효성을 검사하는 전반적인 과정을 설명합니다.
*   실제 검색 요청과 그에 대한 스키마 예시를 제공하여 JSON Schema의 활용 방안을 구체적으로 보여줍니다.
*   다양한 언어에서 사용 가능한 JSON Schema 유효성 검사 라이브러리의 목록을 제시하여 실제 구현에 대한 가이드라인을 제공합니다.
*   데이터 유효성 검사의 중요성을 강조하며, 데이터 중심 프로그래밍(DOP)에서의 역할을 명확히 합니다.
구성노드3(7.3 Schema flexibility and strictness): ## 7.3 Schema Flexibility and Strictness 상세 정보 및 새로운 내용 정리
**1. JSON Schema의 유연성과 엄격함:**
*   **필드의 기본 설정:** JSON Schema에서 객체 내 필드는 기본적으로 선택 사항입니다. 필수 필드로 지정하려면 `required` 배열에 포함해야 합니다.
*   **스키마의 조립:** JSON Schema는 단순히 맵(map, 객체)이므로 다른 맵처럼 구성하고 조작할 수 있습니다. 이를 통해 스키마를 재사용하고 모듈화하여 가독성을 높일 수 있습니다. (예: `bookInfoSchema`를 별도로 정의하여 `searchBooksResponseSchema`에서 사용)
*   **`additionalProperties` 설정:**
*   JSON Schema에서 객체에 스키마에 정의되지 않은 추가 필드가 있는 경우, 기본적으로 유효한 것으로 간주됩니다.
*   `additionalProperties: false`를 설정하면 스키마에 명시되지 않은 필드를 허용하지 않아 엄격한 유효성 검사를 수행할 수 있습니다.
*   **엄격함과 유연성의 균형:**
*   **응답(Response) 데이터:** 서버가 클라이언트에게 보내는 응답 데이터는 가능한 한 엄격하게 검증하는 것이 좋습니다.
*   **요청(Request) 데이터:** 클라이언트가 보내는 요청 데이터는 유연하게 처리하여 예상치 못한 입력에 대해 오류를 최소화하는 것이 좋습니다. (Jon Postel의 "보내는 것은 보수적으로, 받는 것은 너그럽게" 원칙)
**2. 예시 및 구체적인 구현 방법:**
*   **검색 응답 스키마 리팩토링 (Listing 7.12):** `bookInfoSchema`를 별도로 정의하고 이를 `searchBooksResponseSchema`에서 사용하여 스키마를 모듈화하는 방법을 보여줍니다.
*   **데이터베이스 응답 스키마 (Listing 7.13):** 데이터베이스 응답 데이터의 구조를 정의하는 스키마 예시. 모든 필드가 필수적이며, `title`, `isbn`, `available` 필드만 포함합니다.
*   **`additionalProperties` 예시 (Listing 7.14, 7.15):**
*   **Listing 7.14:** `dummy_property`를 포함한 유효하지 않은 데이터 예시
*   **Listing 7.15:** `additionalProperties: false`를 사용하여 추가 필드를 허용하지 않도록 설정하는 예시.
**3. 추가적인 내용:**
*   **데이터 유효성 검사 중요성:** 외부 데이터 소스(예: 데이터베이스)에서 가져온 데이터는 항상 유효성 검사를 수행하는 것이 좋습니다.
*   **스키마의 목적:** 스키마는 데이터의 구조를 정의하고 유효성을 검사하여 오류를 방지하고 데이터 무결성을 유지하는 데 기여합니다.
*   **JSON Schema의 장점:** JSON Schema는 간단하고 재사용 가능하며, 객체 지향 프로그래밍 언어의 클래스 정의보다 유연하게 구성할 수 있습니다.
*   **"The client is always right" vs. "보내는 것은 보수적으로, 받는 것은 너그럽게":** 클라이언트의 잘못된 요청에 대해 너무 엄격하게 굴기보다는, 가능한 한 클라이언트의 요청을 수용하고 올바르게 처리하는 것이 더 나은 사용자 경험을 제공할 수 있습니다.
구성노드4(7.4 Schema composition): ## 7.4 Schema composition 상세 분석 및 새로운 내용
이 챕터는 외부 API 응답 데이터의 유효성 검사를 위한 JSON Schema 구성(Schema composition) 기법을 소개합니다. 기존 내용에서 다루지 않은 추가적인 상세 정보와 새로운 내용은 다음과 같습니다.
**1. 문제 제기:**
*   **외부 API 데이터의 유효성 검사 필요성:** 외부 웹 서비스(예: Open Library Books API)로부터 수신된 데이터의 유효성을 검사해야 하는 상황을 제시하며, 이는 데이터의 무결성을 보장하고 애플리케이션의 안정성을 높이는 데 중요합니다.
*   **`isbn_10` 및 `isbn_13` 필드의 특수성:** `isbn_10`과 `isbn_13` 필드가 모두 필수적인 것은 아니며, 책의 출판 연도에 따라 하나 또는 둘 다 존재할 수 있다는 점을 지적합니다. 이러한 상황은 단순한 스키마로는 표현하기 어렵습니다.
**2. Schema Composition 소개:**
*   **개념:** 스키마 구성은 여러 스키마를 조합하여 복잡한 데이터 구조의 유효성을 검사하는 기법입니다. 이는 `AND`, `OR`, `NOT`과 같은 논리 연산을 사용하여 스키마를 결합하는 방식으로 작동합니다.
*   **`allOf`, `anyOf`, `oneOf` 키워드:**
*   `allOf`: 모든 스키마를 만족해야 합니다 (AND).
*   `anyOf`: 최소한 하나의 스키마를 만족해야 합니다 (OR).
*   `oneOf`: 정확히 하나의 스키마를 만족해야 합니다. (NOTE 부분에서 언급)
*   **구체적인 예시: Open Library Books API 응답 스키마 구성**
*   `basicBookInfoSchema`: 제목(`title`)만 필수적으로 요구하는 기본 정보 스키마.
*   `mandatoryIsbn13`: `isbn_13`만 필수적으로 요구하는 스키마.
*   `mandatoryIsbn10`: `isbn_10`만 필수적으로 요구하는 스키마.
*   `bookInfoSchema`: `basicBookInfoSchema`를 만족하고, `mandatoryIsbn13` 또는 `mandatoryIsbn10` 중 하나 이상을 만족해야 합니다. 즉, 제목은 반드시 있어야 하고, `isbn_10` 또는 `isbn_13`은 최소한 하나는 있어야 합니다.
**3. 구현 예시 (Listing 7.18 & 7.19):**
*   **스키마 정의 (Listing 7.18):** `basicBookInfoSchema`, `mandatoryIsbn13`, `mandatoryIsbn10` 및 `bookInfoSchema`의 JSON Schema 정의를 보여줍니다.
*   **데이터 검증 (Listing 7.19):** 실제 API 응답 데이터 (`bookInfo`)를 `bookInfoSchema`로 검증하는 예시를 제시합니다. 이 예시는 Watchmen 책에 대한 데이터를 사용하며, `isbn_10`과 `isbn_13` 모두를 포함하고 있습니다.
**4. 추가 정보 및 개선점:**
*   **스키마 구성의 장점:** 스키마 구성은 복잡한 데이터 유효성 검사 규칙을 표현하는 데 강력한 기능을 제공하며, 클래스를 사용하여 데이터를 표현하는 것보다 더 유연합니다.
*   **유효성 검사 오류 메시지의 중요성:** 유효성 검사 실패 시, 오류 메시지가 불명확하다는 문제점을 지적하며, 이는 데이터 검증의 한계로 이어질 수 있음을 암시합니다. (데이터 유효성 검사 실패 시, 어떤 부분이 잘못되었는지 명확하게 알 수 있어야 합니다.)
*   **고급 데이터 유효성 검사:** 챕터 12에서 다룰 고급 데이터 유효성 검사 기술에 대한 언급을 통해, JSON Schema의 더 강력한 기능을 기대하게 합니다.
**5. 추가적인 세부 사항 및 예시:**
*   **`oneOf`의 활용:** 데이터가 정확히 하나의 스키마에 부합해야 하는 경우(예: enum 타입의 값 중 하나만 선택), `oneOf`를 사용하여 유효성을 검사할 수 있습니다.
*   **복잡한 조건:** 스키마 구성은 여러 개의 `allOf`, `anyOf`, `oneOf`를 중첩하여 사용함으로써 매우 복잡한 유효성 검사 규칙을 정의할 수 있습니다. 예를 들어, 특정 조건에서 특정 필드가 필수적인 경우와 같은 규칙을 표현할 수 있습니다.
*   **실용적인 예시:**  온라인 쇼핑몰의 상품 데이터를 검증한다고 가정해 봅시다. 상품은 카테고리, 가격, 재고 수량 등 다양한 정보를 포함합니다. 각 카테고리별로 필요한 정보가 다르므로, 스키마 구성을 사용하여 카테고리에 따라 다른 필드를 필수적으로 요구하도록 정의할 수 있습니다. 예를 들어, "전자제품" 카테고리의 상품에는 "전원 소비량" 필드가 필수적일 수 있습니다.
구성노드5(7.5 Details about data validation failures): ## 7.5 Details about data validation failures - 추가 정보 정리
이 문서의 주요 내용은 JSON Schema validation 실패 시, 실패 이유에 대한 상세 정보를 얻는 방법과 그 유용성에 대한 것입니다. 다음은 이 내용에서 다루지 않았던, 추가적으로 주목할 만한 세부 정보, 예시, 구현 방법입니다.
**1. 오류 정보의 구조와 해석:**
*   **오류 정보의 형태:** Ajv (JavaScript validator)를 예시로, validation 실패 시 오류 정보는 배열 형태로 반환됩니다. 각 배열 요소는 오류에 대한 상세 정보를 담은 객체입니다.
*   **객체 내부 구조:** 각 오류 객체는 다음과 같은 속성을 가질 수 있습니다.
*   `instancePath`: 오류가 발생한 데이터 내의 위치 (예: ""는 root, "/fields/0"은 fields 배열의 첫 번째 요소).
*   `schemaPath`: 스키마 내에서 오류가 발생한 부분의 위치.
*   `keyword`: 발생한 오류의 유형 (예: "required", "type").
*   `params`: 오류 유형에 따른 추가적인 정보 (예: `missingProperty` - 누락된 필드의 이름).
*   `message`: 오류에 대한 설명 (인간 친화적인 텍스트).
*   **오류 정보의 난해함:** 원시적인 오류 정보는 이해하기 어려울 수 있습니다.
**2. 오류 정보를 활용하는 방법:**
*   **오류 정보의 가독성 향상:** Ajv는 `errorsText` 유틸리티 함수를 제공하여 오류 정보를 사람이 읽기 쉬운 형태로 변환합니다.
*   **다중 오류 처리 (allErrors 옵션):** 기본적으로 Ajv는 첫 번째 오류만 감지하지만, `allErrors: true` 옵션을 Ajv 생성자에 전달하면 모든 오류를 감지할 수 있습니다. 이 옵션은 여러 오류를 동시에 처리해야 하는 경우에 유용합니다.
*   **실제 사용 사례:** 시스템 경계(boundaries)에서 데이터 유효성 검사를 수행하여, 웹 서버로의 변환과 같은 시나리오에서 유용함을 강조합니다.

**4. 새로운 내용과 추가 정보:**
*   **Ajv 이외의 다른 Validator Library:** 다른 validator library들은 각자 오류 정보를 노출하는 방식이 다를 수 있다는 점을 간접적으로 시사합니다. (예: Java의 `javax.validation` framework나 Python의 `jsonschema` 등) 각 라이브러리의 문서와 API를 참조하여 오류 처리 방법을 파악해야 합니다.
*   **오류 처리 전략:**
*   **프론트엔드에서의 유효성 검사:** 사용자가 입력한 데이터의 유효성을 검사하여 사용자 경험을 향상시키고, 서버에 불필요한 요청을 줄일 수 있습니다.
*   **백엔드에서의 유효성 검사:** 데이터베이스에 저장되기 전에 데이터의 유효성을 검사하여 데이터 무결성을 유지하고, 악의적인 데이터를 방지할 수 있습니다.
*   **오류 메시지 커스터마이징:** validator가 제공하는 기본 오류 메시지 외에, 애플리케이션의 요구사항에 맞춰 사용자 정의 오류 메시지를 제공할 수 있습니다. (예: 국제화, 상세한 설명 추가)
*   **성능 고려 사항:** `allErrors: true` 옵션을 사용하면 여러 오류를 감지할 수 있지만, 유효성 검사 시간이 증가할 수 있습니다. 성능이 중요한 경우에는, 필요한 경우에만 사용하거나, 오류 발생 시 특정 시점까지만 검사하는 등의 최적화를 고려해야 합니다.
*   **JSON Schema Cheat Sheet의 활용:** JSON Schema cheat sheet는 JSON Schema를 처음 접하는 사람들에게 유용한 가이드가 될 수 있으며, 자주 사용되는 schema 구조와 패턴을 빠르게 파악하는 데 도움을 줍니다.
*   **유효한 데이터의 중요성:** Listing 7.25와 같이 유효한 데이터 예시는, 데이터가 예상대로 구조화되었는지 확인하고, 유효성 검사 규칙이 올바르게 작동하는지 테스트하는 데 도움이 됩니다.
*   **테스트:** 데이터 유효성 검사는 소프트웨어의 안정성을 높이는 데 중요한 역할을 합니다. 유효성 검사 로직을 테스트하여 예상대로 작동하는지 확인해야 합니다.
이러한 정보들을 통해 텍스트 분석 전문가는 데이터 유효성 검사 실패 시, 더 자세하고 유용한 정보를 얻고, 실질적인 구현에 적용할 수 있습니다.

구성노드2: 7.2 JSON Schema in a nutshell: **7.2 JSON Schema: 기본 개념 및 활용**

이 챕터는 JSON Schema의 기본 개념과 사용법을 소개합니다. 부모 노드에서 설명된 7 Basic data validation 내용과 연계하여, JSON Schema가 데이터 유효성 검증에 어떻게 활용되는지 구체적으로 설명합니다.

**1. JSON Schema의 역할과 중요성 (부모 노드 반영):**

*   **데이터 유효성 검사:** JSON Schema는 데이터 표현과 데이터 스키마를 분리하여, 데이터가 스키마에 정의된 규칙을 준수하는지 검사합니다.
*   **DOP(Data Oriented Programming)에서의 중요성:** DOP에서 데이터의 정확성을 보장하는 데 중요한 역할을 합니다.
*   **언어 독립성:** 다양한 프로그래밍 언어에서 사용할 수 있는 유효성 검사 라이브러리가 존재합니다. (부모 노드 'JSON Schema의 특징' 참고)
*   **검증 실패 시:** Ajv와 같은 Validator Library는 오류 정보를 상세하게 제공하여 문제 해결을 돕습니다. (부모 노드의 '데이터 검증 실패 정보' 참고)

**2. JSON Schema의 기본 구조 (부모 노드 반영):**

*   **최상위 구조:** JSON 객체이며, `type` 과 `properties` 필드를 갖습니다.
    *   `type`: 데이터의 유형을 정의합니다 (예: "object", "string", "array").
    *   `properties`: 객체 내 필드의 스키마를 정의합니다.
*   **객체(object) 타입 스키마:**
    *   `type`: "object"
    *   `properties`: 객체의 각 필드에 대한 스키마 정의
*   **배열(array) 타입 스키마:**
    *   `type`: "array"
    *   `items`: 배열의 각 요소에 대한 스키마 정의
*   **ENUM 사용:** "enum" 키워드를 사용하여 허용되는 값의 목록을 지정합니다. (예: `{"enum": ["value1", "value2"]}`).
*   **필수(required) 필드 지정:** "required" 필드를 사용하여 필수 필드를 정의합니다. (예: `{"required": ["field1", "field2"]}`).

**3. JSON Schema를 사용한 검색 요청 스키마 예시 (부모 노드 예시 활용):**

*   **검색 요청 데이터:**
```json
{
"title": "habit",
"fields": ["title", "weight", "number_of_pages"]
}
```
*   **검색 요청 스키마:**
```json
var searchBooksRequestSchema = {
"type": "object",
"properties": {
"title": {"type": "string"},
"fields": {
"type": "array",
"items": {
"enum": [
"publishers",
"number_of_pages",
"weight",
"physical_format",
"subjects",
"publish_date",
"physical_dimensions"
]
}
}
},
"required": ["title", "fields"]
};
```

**4. JSON Schema 유효성 검사 (부모 노드 내용과 연결):**

*   **유효성 검사 라이브러리:** 다양한 프로그래밍 언어에서 JSON Schema 유효성 검사 라이브러리를 사용할 수 있습니다. (예: Ajv (JavaScript), Snow (Java), JSON.net Schema (C#), jschon (Python), JSONSchemer (Ruby))
*   **validate 함수:**  일반적으로 유효성 검사 라이브러리는 스키마와 데이터를 입력으로 받아 유효성 검사 결과를 반환하는 `validate` 함수를 제공합니다. (유효하면 `true`, 유효하지 않으면 `false`)
*   **유효하지 않은 경우:** 오류 발생 시, Ajv와 같은 라이브러리를 통해 상세한 오류 정보를 얻을 수 있습니다. (부모 노드의 '데이터 검증 실패 정보' 참고)

**5. JSON Schema의 장점 (부모 노드 내용 포함):**

*   **언어 독립성:** 여러 프로그래밍 언어에서 사용 가능.
*   **표현력:** 클래스 기반의 데이터 정의보다 훨씬 더 복잡한 유효성 검사 조건을 표현할 수 있습니다 (예: 숫자 범위, 정규 표현식).
*   **유연성:** 스키마는 객체처럼 조작하고, 스키마를 재사용하여 모듈화를 통해 가독성을 향상시킬 수 있습니다. (부모 노드의 'JSON Schema의 유연성 및 엄격성' 참고)

**6. 추가적인 내용 (부모 노드 내용 참조):**

*   **스키마 구성(schema composition):** 여러 스키마를 조합하여 유효성 검사 규칙을 정의할 수 있습니다. (7.4절에서 자세히 다룰 예정)
*   **고급 유효성 검사:** 숫자 범위, 정규 표현식 등을 사용한 유효성 검사를 12장에서 다룰 예정입니다.
*   **응답 유효성 검사:** 서버 응답의 유효성을 검사하는 방법, 즉 "보내는 것은 엄격하게, 받는 것은 유연하게" 원칙을 적용하는 방법에 대한 간략한 언급이 있었습니다.
*   **오류 정보:** 유효성 검사 실패 시 오류에 대한 상세 정보를 얻는 방법, Ajv와 같은 라이브러리의 활용 (7.5절)

**7. 새로운 내용 (부모 노드 내용을 기반으로 함):**

*   **JSON Schema는 데이터 구조를 정의하고 검증하는 데 사용되며, DOP에서 데이터의 정확성을 보장하는 핵심 요소입니다.**
*   **API 요청 및 응답의 형식을 정의하고, 데이터 유효성을 검사하는 전반적인 과정을 설명하며, 실제 예시를 통해 활용 방안을 제시합니다.**
*   **JSON Schema를 사용하여 API 요청과 응답의 형식을 정의하고, 데이터 유효성을 검사하는 전반적인 과정을 설명합니다. 다양한 언어에서 사용 가능한 JSON Schema 유효성 검사 라이브러리의 목록을 제시하여 실제 구현에 대한 가이드라인을 제공합니다.** ( 부모 노드의 'JSON Schema 유효성 검사' 부분 참고)

구성노드3: 7.3 Schema flexibility and strictness: **7.3 스키마 유연성 및 엄격성**

이 챕터는 JSON Schema의 유연성과 엄격성을 조절하는 방법을 다룹니다. 부모 노드의 7 Basic data validation 내용과 연계하여, 데이터 전송 원칙과 스키마 디자인의 중요성을 강조합니다.

**1. JSON Schema의 유연성과 엄격함 (부모 노드 반영):**

*   **필드의 기본 설정:** JSON Schema에서 객체 내 필드는 기본적으로 선택 사항입니다. 필수 필드로 지정하려면 `required` 배열에 포함해야 합니다.
*   **스키마의 조립:** JSON Schema는 맵(map, 객체)이므로 다른 맵처럼 구성하고 조작할 수 있습니다. 이를 통해 스키마를 재사용하고 모듈화하여 가독성을 높일 수 있습니다. (예: `bookInfoSchema`를 별도로 정의하여 `searchBooksResponseSchema`에서 사용)
*   **`additionalProperties` 설정:**
    *   JSON Schema에서 객체에 스키마에 정의되지 않은 추가 필드가 있는 경우, 기본적으로 유효한 것으로 간주됩니다.
    *   `additionalProperties: false`를 설정하면 스키마에 명시되지 않은 필드를 허용하지 않아 엄격한 유효성 검사를 수행할 수 있습니다.
*   **엄격함과 유연성의 균형:**
    *   **응답(Response) 데이터:** 서버가 클라이언트에게 보내는 응답 데이터는 가능한 한 엄격하게 검증하는 것이 좋습니다.
    *   **요청(Request) 데이터:** 클라이언트가 보내는 요청 데이터는 유연하게 처리하여 예상치 못한 입력에 대해 오류를 최소화하는 것이 좋습니다. (Jon Postel의 "보내는 것은 보수적으로, 받는 것은 너그럽게" 원칙, 부모 노드 '데이터 전송 원칙' 참고)

**2. 예시 및 구체적인 구현 방법 (부모 노드 예시 활용):**

*   **검색 응답 스키마 리팩토링 (Listing 7.12):** `bookInfoSchema`를 별도로 정의하고 이를 `searchBooksResponseSchema`에서 사용하여 스키마를 모듈화하는 방법을 보여줍니다.
*   **데이터베이스 응답 스키마 (Listing 7.13):** 데이터베이스 응답 데이터의 구조를 정의하는 스키마 예시. 모든 필드가 필수적이며, `title`, `isbn`, `available` 필드만 포함합니다.
*   **`additionalProperties` 예시 (Listing 7.14, 7.15):**
    *   **Listing 7.14:** `dummy_property`를 포함한 유효하지 않은 데이터 예시
    *   **Listing 7.15:** `additionalProperties: false`를 사용하여 추가 필드를 허용하지 않도록 설정하는 예시.

**3. 추가적인 내용 (부모 노드 내용 포함):**

*   **데이터 유효성 검사 중요성:** 외부 데이터 소스(예: 데이터베이스)에서 가져온 데이터는 항상 유효성 검사를 수행하는 것이 좋습니다.
*   **스키마의 목적:** 스키마는 데이터의 구조를 정의하고 유효성을 검사하여 오류를 방지하고 데이터 무결성을 유지하는 데 기여합니다.
*   **JSON Schema의 장점:** JSON Schema는 간단하고 재사용 가능하며, 객체 지향 프로그래밍 언어의 클래스 정의보다 유연하게 구성할 수 있습니다.
*   **"The client is always right" vs. "보내는 것은 보수적으로, 받는 것은 너그럽게":** 클라이언트의 잘못된 요청에 대해 너무 엄격하게 굴기보다는, 가능한 한 클라이언트의 요청을 수용하고 올바르게 처리하는 것이 더 나은 사용자 경험을 제공할 수 있습니다. (부모 노드 '데이터 전송 원칙' 참고)
*   **데이터 전송 원칙:** "보내는 데이터는 엄격하게, 받는 데이터는 유연하게" 원칙을 통해 안정성과 유연성을 모두 확보할 수 있습니다. (부모 노드 '데이터 전송 원칙' 참고)
*   **응답 데이터의 엄격한 검증:** 서버가 클라이언트에게 보내는 응답은 엄격한 검증을 통해 데이터 품질을 보장합니다.
*   **요청 데이터의 유연한 검증:** 클라이언트 요청은 유연하게 처리하여, 예외적인 입력에 대응하고 사용자 경험을 향상시킵니다.
*   **JSON Schema의 조립:** 맵처럼 구성되어 재사용 및 모듈화가 가능하다는 점을 강조합니다.

구성노드4: 7.4 Schema composition: **7.4 스키마 조합을 통한 유효성 검사**

이 챕터는 스키마 조합(Schema Composition) 기술을 소개하며, 외부 API 응답 데이터의 유효성을 검사하는 데 초점을 맞춥니다. 부모 노드의 '7 Basic data validation' 내용과 연결하여, JSON Schema의 강력한 기능과 외부 데이터 검증의 중요성을 강조합니다.

**1. 문제 제기 (부모 노드 내용 반영):**

*   **외부 API 데이터의 유효성 검사 필요성:** 외부 웹 서비스 (예: Open Library Books API)로부터 수신된 데이터의 유효성을 검사해야 하는 상황을 제시하며, 데이터의 무결성 보장, 애플리케이션 안정성 향상, 보안 강화에 기여합니다. (부모 노드 '경계에서의 검증 예시' 참고)
*   **`isbn_10` 및 `isbn_13` 필드의 특수성:** `isbn_10`과 `isbn_13` 필드가 선택적이며, 둘 중 하나 또는 둘 다 존재할 수 있다는 점을 지적합니다. 단순한 스키마로는 이러한 조건을 표현하기 어렵습니다.

**2. Schema Composition 소개 (부모 노드 내용 반영):**

*   **개념:** 스키마 조합은 여러 스키마를 조합하여 복잡한 데이터 구조의 유효성을 검사하는 기법입니다. `allOf`, `anyOf`, `oneOf` 와 같은 키워드를 사용하여 스키마를 결합합니다. (부모 노드 'Schema composition' 참고)
*   **`allOf`, `anyOf`, `oneOf` 키워드:**
    *   `allOf`: 모든 스키마를 만족해야 합니다 (AND).
    *   `anyOf`: 최소한 하나의 스키마를 만족해야 합니다 (OR).
    *   `oneOf`: 정확히 하나의 스키마를 만족해야 합니다.
*   **구체적인 예시: Open Library Books API 응답 스키마 구성:**
    *   `basicBookInfoSchema`: 제목(`title`)만 필수적으로 요구하는 기본 정보 스키마.
    *   `mandatoryIsbn13`: `isbn_13`만 필수적으로 요구하는 스키마.
    *   `mandatoryIsbn10`: `isbn_10`만 필수적으로 요구하는 스키마.
    *   `bookInfoSchema`: `basicBookInfoSchema`를 만족하고, `mandatoryIsbn13` 또는 `mandatoryIsbn10` 중 하나 이상을 만족해야 합니다. 즉, 제목은 반드시 있어야 하고, `isbn_10` 또는 `isbn_13`은 최소한 하나는 있어야 합니다.

**3. 구현 예시 (Listing 7.18 & 7.19, 부모 노드 내용 활용):**

*   **스키마 정의 (Listing 7.18):** `basicBookInfoSchema`, `mandatoryIsbn13`, `mandatoryIsbn10` 및 `bookInfoSchema`의 JSON Schema 정의를 보여줍니다.
*   **데이터 검증 (Listing 7.19):** 실제 API 응답 데이터 (`bookInfo`)를 `bookInfoSchema`로 검증하는 예시를 제시합니다. 이 예시는 Watchmen 책에 대한 데이터를 사용하며, `isbn_10`과 `isbn_13` 모두를 포함하고 있습니다.

**4. 추가 정보 및 개선점 (부모 노드 내용 및 추가 보충):**

*   **스키마 구성의 장점:** 복잡한 데이터 유효성 검사 규칙을 표현하는 데 강력한 기능을 제공하며, 클래스를 사용하여 데이터를 표현하는 것보다 더 유연합니다. (부모 노드 '스키마 구성의 장점' 참고)
*   **유효성 검사 오류 메시지의 중요성:** 오류 메시지가 불명확할 경우 문제 해결이 어려우므로, 명확한 오류 메시지를 제공해야 합니다. (7.5절에서 자세히 다룸, 부모 노드 '데이터 검증 실패 정보' 참고)
*   **고급 데이터 유효성 검사:** 12장에서 다룰 고급 데이터 유효성 검사 기술에 대한 언급을 통해, JSON Schema의 더 강력한 기능을 기대하게 합니다.
*   **유연한 스키마 설계:** `allOf`, `anyOf`와 같은 키워드를 활용하여, 데이터의 변화에 유연하게 대응할 수 있는 스키마를 설계합니다. (부모 노드 '필드 기본값과 모범 사례' 참고)
*   **실용적인 예시:** 쇼핑몰 상품 데이터 검증 시, 각 카테고리에 따라 다른 필수 필드를 요구하도록 스키마를 구성하는 예시를 제시합니다. (부모 노드의 '추가적인 세부 사항 및 예시' 참고)

구성노드5: 7.5 Details about data validation failures: **7.5 유효성 검사 실패 시 상세 정보 분석 및 활용**

이 챕터는 JSON Schema validation 실패 시, 실패 이유에 대한 상세 정보를 얻는 방법과 그 유용성을 다룹니다. 부모 노드의 7 Basic data validation 내용과 연결하여, 오류 처리 및 사용자 경험 개선의 중요성을 강조합니다.

**1. 오류 정보의 구조와 해석 (부모 노드 내용 반영):**

*   **오류 정보의 형태:** Ajv (JavaScript validator)를 예시로, validation 실패 시 오류 정보는 배열 형태로 반환됩니다. 각 배열 요소는 오류에 대한 상세 정보를 담은 객체입니다.
*   **객체 내부 구조:** 각 오류 객체는 다음과 같은 속성을 가질 수 있습니다.
    *   `instancePath`: 오류가 발생한 데이터 내의 위치.
    *   `schemaPath`: 스키마 내에서 오류가 발생한 부분의 위치.
    *   `keyword`: 발생한 오류의 유형 (예: "required", "type").
    *   `params`: 오류 유형에 따른 추가적인 정보.
    *   `message`: 오류에 대한 설명 (인간 친화적인 텍스트).
*   **오류 정보의 난해함:** 원시적인 오류 정보는 이해하기 어려울 수 있습니다.

**2. 오류 정보를 활용하는 방법 (부모 노드 내용 반영):**

*   **오류 정보의 가독성 향상:** Ajv는 `errorsText` 유틸리티 함수를 제공하여 오류 정보를 사람이 읽기 쉬운 형태로 변환합니다.
*   **다중 오류 처리 (allErrors 옵션):** `allErrors: true` 옵션을 통해 모든 오류를 감지하고, 한 번에 처리합니다.
*   **실제 사용 사례:** 시스템 경계 (boundaries)에서 데이터 유효성 검사를 수행하여, 오류 발생 시 사용자에게 명확한 정보를 제공합니다.

**4. 새로운 내용과 추가 정보 (부모 노드 내용 및 추가 보충):**

*   **Ajv 이외의 다른 Validator Library:** 각 라이브러리마다 오류 정보 노출 방식이 다르므로, 해당 라이브러리의 문서를 참조하여 오류 처리 방법을 파악해야 합니다.
*   **오류 처리 전략:** (부모 노드 '오류 처리 전략' 참고)
    *   **프론트엔드:** 사용자가 입력한 데이터의 유효성을 검사하여 사용자 경험을 향상시키고 서버에 불필요한 요청을 줄입니다.
    *   **백엔드:** 데이터베이스 저장 전 데이터의 유효성을 검사하여 데이터 무결성을 유지합니다.
*   **오류 메시지 커스터마이징:** validator가 제공하는 기본 오류 메시지 외에, 애플리케이션 요구사항에 맞춰 사용자 정의 오류 메시지를 제공합니다.
*   **성능 고려 사항:** `allErrors: true` 옵션은 유효성 검사 시간을 증가시킬 수 있으므로, 성능이 중요한 경우에는 최적화를 고려해야 합니다.
*   **JSON Schema Cheat Sheet의 활용:** JSON Schema cheat sheet는 JSON Schema 학습에 도움을 줍니다.
*   **유효한 데이터의 중요성:** 유효한 데이터 예시는 유효성 검사 규칙이 올바르게 작동하는지 테스트하는 데 도움이 됩니다.
*   **테스트:** 유효성 검사 로직을 테스트하여 소프트웨어의 안정성을 높입니다.

*   **시스템 경계 정의 (데이터 교환 영역) 관련:** 시스템 경계는 데이터가 입력되거나 출력되는 모든 지점을 포함하며, 이는 API 엔드포인트, 파일 입출력, 데이터베이스 연결, 외부 서비스와의 통신 등 다양한 형태로 나타날 수 있습니다. (부모 노드 '시스템 경계의 정의' 참고)
*   **경계에서의 검증 예시 (클라이언트 요청/응답, 외부 소스 데이터) 관련:**
    *   **클라이언트 요청/응답:** API 엔드포인트에 전송되는 JSON 데이터의 유효성을 검증하여, 예상치 못한 데이터로 인한 시스템 오류를 방지하고, API 응답 데이터가 클라이언트에 올바르게 전달되는지 검증합니다.
    *   **외부 소스 데이터:** 외부 API, 데이터베이스, 파일 등에서 수신하는 데이터가 시스템에서 요구하는 스키마를 준수하는지 검증합니다. 데이터 품질을 보장하고, 잠재적인 데이터 손상 문제를 예방합니다. (부모 노드 '경계에서의 검증 예시' 참고)
*   **DOP 데이터 검증 의미 (스키마 준수 여부 확인) 관련:** 스키마를 준수하는 데이터는 시스템이 예상하는 형식과 구조를 갖춘 데이터이며, 시스템의 안정성과 신뢰성을 확보하는 데 중요합니다. (부모 노드 'DOP 데이터 검증 의미' 참고)
*   **검증 실패 정보 (상세한 검증 실패 정보와 사용자 친화적 형식) 관련:** 실패 정보를 사용자 친화적인 형식으로 제공함으로써, 문제의 원인을 쉽게 파악하고 수정할 수 있도록 돕습니다. (부모 노드 '데이터 검증 실패 정보' 참고)
*   **경계 검증의 중요성 (내부 재검증 불필요) 관련:** 경계에서 한 번 검증된 데이터는 시스템 내부에서 추가적인 유효성 검사를 거치지 않아도 됩니다. 이는 성능 향상과 코드 복잡성 감소에 기여합니다. 다만, 보안적인 측면에서 신뢰할 수 없는 데이터에 대한 검증은 필요할 수 있습니다.
