## 7 Basic Data Validation 상세 정리

### 7.1 Data validation in DOP

*   **DOP 원칙 4:** 데이터 스키마와 데이터 표현의 분리 (Separate data schema from data representation).
*   **데이터 검증의 중요성:** DOP에서 데이터 검증은 가능하며 권장됨.
*   **시스템 경계 (Boundaries) 정의:** 시스템이 데이터를 교환하는 영역 (클라이언트, 데이터베이스, 웹 서비스).
*   **두 가지 종류의 데이터 검증:**
*   **경계에서의 검증:** 시스템의 입출력 데이터 검증 (가장 중요).
*   **내부에서의 검증:** 코드베이스가 커짐에 따라 개발 편의성을 위해 사용.
*   **경계 검증의 목적:** 유효하지 않은 데이터의 입출력 방지, 오류 발생 시 상세 정보 제공.
*   **팁:** 경계에서 데이터 검증이 완료되면 내부에서의 재검증은 필수는 아님.

### 7.2 JSON Schema in a nutshell

*   **JSON Schema 개요:** 데이터 스키마를 JSON 형식으로 정의하는 언어.
*   **데이터 스키마와 표현의 분리:** 데이터 표현과 독립적으로 스키마 정의 가능.
*   **JSON Schema 기본 구조:**
*   `type`: 데이터 유형 (예: "object", "string", "array").
*   `properties`: 각 필드의 스키마 정의 (객체인 경우).
*   `items`: 배열 요소의 스키마 (배열인 경우).
*   `enum`: 허용되는 값 목록 (열거형).
*   `required`: 필수 필드 목록.
*   **JSON Schema의 특징:**
*   언어 독립성 (다양한 프로그래밍 언어에서 사용 가능).
*   표현력: 클래스 기반 데이터 표현보다 더 복잡한 검증 조건 표현 가능.

### 7.3 Schema flexibility and strictness

*   **검증 대상:** 클라이언트 요청, 서버 응답, 외부 데이터 소스 등
*   **JSON Schema의 유연성:**
*   필드는 기본적으로 선택 사항.
*   `required` 필드를 통해 필수 필드 지정.
*   스키마는 맵이므로 쉽게 구성하고 조작 가능.
*   **`additionalProperties` 필드:**
*   기본적으로 스키마에 정의되지 않은 필드 허용.
*   `additionalProperties: false`를 설정하여 추가 필드 금지 (엄격한 검증).
*   **모범 사례:**
*   요청에서는 유연하게 (추가 필드 허용).
*   응답에서는 엄격하게 (추가 필드 금지).
*   **데이터 전송 원칙:** "보내는 것은 보수적으로, 받는 것은 관대하게 (Be conservative in what you send, be liberal in what you accept)."

### 7.4 Schema composition

*   **스키마 조합:**  `allOf`, `anyOf`, `oneOf` 등을 사용하여 스키마를 조합.
*   `allOf`: 모든 스키마를 만족해야 함 (AND).
*   `anyOf`: 하나 이상의 스키마를 만족해야 함 (OR).
*   `oneOf`: 정확히 하나의 스키마를 만족해야 함.
*   **스키마 조합의 장점:** 클래스 정의보다 더 유연하고 강력한 데이터 검증 조건 표현 가능.

### 7.5 Details about data validation failures

*   **검증 실패 시 상세 정보:** 유효성 검사 실패의 원인에 대한 구체적인 정보 제공 (예: 누락된 필수 필드, 잘못된 데이터 유형).
*   **구체적인 에러 정보:**  JSON Schema 검증 라이브러리 (예: Ajv)는 검증 실패에 대한 자세한 정보를 제공.
*   `instancePath`: 에러가 발생한 데이터 경로.
*   `schemaPath`: 에러가 발생한 스키마 경로.
*   `keyword`: 발생한 에러 유형 (예: "required", "type").
*   `params`: 에러에 대한 추가 정보.
*   `message`: 사람이 읽을 수 있는 에러 메시지.
*   **Ajv 라이브러리의 특징:**
*   기본적으로 첫 번째 검증 실패만 감지 (성능 향상).
*   `allErrors: true` 옵션을 사용하여 여러 개의 오류를 한 번에 감지 가능.
*   `errorsText()` 유틸리티 함수를 사용하여 에러 정보를 사람이 읽기 쉬운 형식으로 변환.

구성노드1(7.1 Data validation in DOP): ## 7.1 Data validation in DOP: 상세 분석
### 배경: OOP와 DOP의 데이터 검증 비교
*   **OOP의 장점**: 객체 지향 프로그래밍(OOP)에서는 클래스 인스턴스화 시 멤버 필드의 이름과 타입이 보장되어 데이터의 유효성을 쉽게 관리할 수 있습니다.
*   **DOP의 문제점**: 데이터 지향 프로그래밍(DOP)에서는 필드 이름과 타입에 대한 작은 실수로 인해 데이터 일관성 문제가 발생하기 쉽습니다.
### DOP에서의 데이터 검증 가능성
*   **DOP는 데이터 검증을 강제하지 않지만, 금지하지도 않습니다.** DOP에서는 데이터 스키마가 데이터 표현과 분리되어 있습니다.
### 시스템 경계에서의 데이터 검증 중요성
*   **시스템 경계 정의**: 데이터 교환이 일어나는 지점 (예: 웹 서버와 클라이언트, 웹 서버와 데이터베이스, 웹 서비스)
*   **시스템 경계 예시 (웹 서버):**
*   **클라이언트 경계:** 웹 브라우저 등
*   **데이터베이스 경계:** 데이터 저장소
*   **웹 서비스 경계:** 다른 서비스와의 통신
*   **시스템 경계 데이터 검증의 중요성**: 시스템으로 들어오고 나가는 데이터의 유효성을 확보하면, 시스템 내부에서 예상치 못한 데이터가 발생할 가능성이 줄어듭니다.
*   **TIP**: 시스템 경계에서 데이터가 유효하면, 시스템 내부에서 데이터를 다시 검증할 필요가 없습니다.
### 두 가지 종류의 데이터 검증
*   **경계에서의 검증**: 시스템의 출입 데이터의 유효성을 검사 (가디언, 프로덕션 환경)
*   **목적**: 시스템으로 들어오고 나가는 데이터의 유효성 확보, 유효하지 않은 데이터 발생 시 정보 오류 표시
*   **내부에서의 검증**: 코드베이스 증가에 따른 개발 편의성을 위해 사용 (개발 환경)
*   **목적**: 개발 편의성
### 요약
DOP에서 데이터 유효성 검증은 중요하며, 특히 시스템 경계에서 데이터를 검증하는 것이 핵심입니다. 시스템 내부의 데이터 검증은 개발 편의성을 위한 부가적인 기능입니다.
구성노드2(7.2 JSON Schema in a nutshell): ### 7.2 JSON Schema in a nutshell 개요
이 챕터는 JSON Schema를 사용하여 데이터 유효성 검사를 수행하는 방법을 소개합니다. 특히, 도서 검색 요청에 대한 데이터 스키마를 정의하고, 해당 스키마를 기반으로 데이터의 유효성을 검사하는 과정을 단계별로 설명합니다. JSON Schema는 데이터 표현과 별도로 스키마를 정의하여 데이터 유효성 검사를 수행하는 데 사용되는 강력한 도구입니다.
### 데이터 유효성 검사의 중요성
*   데이터 유효성 검사는 데이터가 스키마에 정의된 규칙을 준수하는지 확인하는 과정입니다.
*   유효성 검사를 통해 데이터 무결성을 유지하고, 시스템 오류를 방지할 수 있습니다.
*   JSON Schema는 언어 독립적이며, 다양한 프로그래밍 언어에서 사용 가능한 라이브러리를 제공합니다.
### JSON Schema 소개
*   JSON Schema는 JSON 기반 데이터의 구조와 유효성을 정의하기 위한 스키마 언어입니다.
*   JSON Schema는 데이터 타입, 필수 필드, 허용된 값 등을 정의할 수 있습니다.
*   JSON Schema는 데이터 표현과 분리되어 관리되므로, 데이터 유효성 검사를 유연하게 수행할 수 있습니다.
### 도서 검색 요청 스키마 정의
1.  **요청 유형 정의:** 도서 검색 요청은 JSON 객체(object)로 표현됩니다.
```json
{
"type": "object",
"properties": {...}
}
```
2.  **속성 정의:** `properties` 필드를 사용하여 객체의 각 필드에 대한 스키마를 정의합니다.
*   **title:** 문자열(string) 타입.
```json
"title": {"type": "string"}
```
*   **fields:** 문자열 배열(array) 타입.
```json
"fields": {"type": "array"}
```
*   **fields 배열의 요소 타입 정의:** `items` 필드를 사용하여 배열 요소의 타입을 지정합니다.
```json
"fields": {
"type": "array",
"items": {"type": "string"}
}
```
*   **fields 배열의 허용된 값 정의:** `enum` 키워드를 사용하여 허용된 값의 목록을 지정합니다.
```json
"fields": {
"type": "array",
"items": {
"enum": [
"publishers",
"number_of_pages",
"weight",
"physical_format",
"subjects",
"publish_date",
"physical_dimensions"
]
}
}
```
3.  **필수 필드 정의:** `required` 필드를 사용하여 필수 필드를 지정합니다.
```json
"required": ["title", "fields"]
```
### JSON Schema를 이용한 데이터 유효성 검사
*   JSON Schema를 사용하여 정의된 스키마에 따라 데이터의 유효성을 검사합니다.
*   다양한 프로그래밍 언어에서 JSON Schema 유효성 검사 라이브러리를 사용할 수 있습니다. (예: Ajv, Snow, JSON.net Schema, jschon, JSONSchemer)
*   유효성 검사 라이브러리는 스키마와 데이터를 입력으로 받아 데이터의 유효성 여부를 `true` 또는 `false`로 반환합니다.
*   유효하지 않은 데이터의 경우, 유효성 검사 라이브러리는 실패 이유에 대한 정보를 제공할 수 있습니다.
### JSON Schema의 장점
*   언어 독립성: 다양한 프로그래밍 언어에서 사용 가능합니다.
*   표현력: 클래스 기반의 데이터 표현 방식보다 더 복잡한 유효성 검사 조건을 표현할 수 있습니다. (예: 범위, 정규식)
*   유연성: 데이터 표현과 스키마를 분리하여 관리하므로 유연한 데이터 유효성 검사가 가능합니다.
구성노드3(7.3 Schema flexibility and strictness): ## 7.3 Schema flexibility and strictness 상세 정리
본 내용은 JSON Schema를 사용하여 데이터 유효성 검사를 수행할 때의 유연성과 엄격성에 대해 다룹니다. 특히, JSON Schema에서의 필드 필수 여부, 추가 속성 허용 여부, 그리고 데이터 유효성 검사 시의 모범 사례를 중심으로 설명합니다.
### 필수 필드와 선택 필드
*   **기본 동작:** JSON Schema에서 객체 내 필드는 기본적으로 선택적(Optional)입니다. 즉, 스키마에 정의되지 않은 필드가 존재해도 유효성 검사 오류를 발생시키지 않습니다.
*   **필수 필드 지정:** 필드를 필수 필드로 지정하려면 `required` 배열에 해당 필드 이름을 포함해야 합니다.
*   예시:
```json
{
"type": "object",
"required": ["title", "available"],
"properties": {
"title": {"type": "string"},
"available": {"type": "boolean"},
"subtitle": {"type": "string"}
}
}
```
*   위 예시에서 `title`과 `available` 필드는 필수이며, `subtitle` 필드는 선택적입니다.
### 스키마 재사용 및 구성 가능성
*   **스키마의 유연성:** JSON Schema는 단순한 맵(Map, 객체)으로 구성되어 있어, 변수에 할당하거나 다른 스키마에 포함시키는 방식으로 쉽게 재사용하고 구성할 수 있습니다.
*   **스키마 분리:** 복잡한 스키마를 별도의 스키마로 분리하여 관리함으로써 가독성을 높이고 유지 보수를 용이하게 할 수 있습니다.
*   예시: `bookInfoSchema`와 `searchBooksResponseSchema`
### 추가 속성 허용 여부 (additionalProperties)
*   **기본 동작:** JSON Schema는 기본적으로 스키마에 정의되지 않은 추가 속성을 허용합니다.
*   **추가 속성 금지:** 추가 속성을 금지하려면 `additionalProperties` 속성을 `false`로 설정합니다.
*   예시:
```json
{
"type": "object",
"required": ["title", "isbn", "available"],
"additionalProperties": false,
"properties": {
"title": {"type": "string"},
"isbn": {"type": "string"},
"available": {"type": "boolean"}
}
}
```
*   위 예시에서는 `title`, `isbn`, `available` 필드 외에 다른 필드가 있으면 유효성 검사에서 오류가 발생합니다.
### 데이터 유효성 검사 모범 사례
*   **외부 데이터 유효성 검사:** 외부 데이터 소스(예: 데이터베이스)로부터 받은 데이터는 반드시 유효성 검사를 수행해야 합니다.
*   **송신 데이터의 엄격성:** 서버에서 클라이언트로 전송하는 데이터(응답)는 가능한 엄격하게 검사하여 예상치 못한 데이터가 전송되는 것을 방지합니다. `additionalProperties: false` 설정을 권장합니다.
*   **수신 데이터의 유연성:** 클라이언트로부터 받은 데이터(요청)는 가능한 유연하게 처리하여 예상치 못한 필드가 존재하더라도 처리를 시도합니다.
*   "Be conservative in what you send, be liberal in what you accept." (Jon Postel의 Robustness Principle)
*   **요청/응답 간의 차이:** 요청 스키마는 유연하게, 응답 스키마는 엄격하게 구성하는 것이 일반적인 방법입니다.
구성노드4(7.4 Schema composition): ## 7.4 Schema Composition 상세 분석
### 배경: 외부 API 데이터 검증 필요성
*   **문제 제기:** 외부 웹 서비스(예: Open Library Books API)에서 제공하는 데이터를 검증해야 할 필요성.
*   **예시:** "Watchmen" 책에 대한 API 응답 데이터 검증.
*   **API 응답 구조:** JSON 형식의 데이터 (제목, 출판사, 페이지 수, ISBN 등).
### 초기 스키마 작성과 문제점
*   **초기 스키마:** 기본적인 데이터 타입(string, integer, array 등)과 필수 필드(title)를 정의.
*   **문제점:** `isbn_10`과 `isbn_13` 필드의 필수 여부 처리.
*   두 필드 모두 필수가 아님.
*   하지만 적어도 하나는 존재해야 함.
*   출판 연도에 따라 `isbn_10` 또는 `isbn_13` 또는 둘 다 존재.
### JSON Schema Composition의 도입
*   **개념:** JSON Schema를 결합하여 복잡한 조건을 표현하는 방법. AND, OR, NOT과 유사한 논리적 연산 지원.
*   **구현:**
*   `allOf`: 모든 스키마를 만족해야 함 (AND).
*   `anyOf`: 스키마 중 하나라도 만족하면 됨 (OR).
*   `oneOf`: 스키마 중 정확히 하나만 만족해야 함.
*   **예시: Open Library Books API 응답 스키마 구성**
1.  `basicBookInfoSchema`: 제목(title) 필수, 기타 필드 정의.
2.  `mandatoryIsbn13`: `isbn_13` 필드 필수.
3.  `mandatoryIsbn10`: `isbn_10` 필드 필수.
4.  `bookInfoSchema`: `basicBookInfoSchema` AND (`mandatoryIsbn13` OR `mandatoryIsbn10`).
*   **결과:** JSON Schema를 통해 복잡한 필수 필드 조건을 명확하게 표현 가능.
### JSON Schema Composition 사용의 장점
*   **유연성:** 여러 스키마를 조합하여 복잡한 데이터 구조 및 조건을 표현.
*   **표현력:** 클래스를 사용하여 데이터 구조를 정의하는 것보다 더 강력한 데이터 검증 조건을 표현 가능.
*   **확장성:** JSON Schema는 `allOf`, `anyOf`, `oneOf` 외에도 다양한 조건을 지원하여 데이터 검증 능력을 향상.
### 추가 고려 사항
*   **검증 실패 시 오류 정보:** 데이터 유효성 검사 실패 시, 어떤 이유로 실패했는지 명확한 정보가 제공되지 않는다는 점을 지적. (이 문제는 추후 개선 필요).
*   **고급 데이터 검증:** Chapter 12에서 더 발전된 데이터 검증 기법을 다룸.
구성노드5(7.5 Details about data validation failures): ## 7.5 Details about data validation failures
이 섹션은 JSON Schema 유효성 검사 실패 시 얻을 수 있는 상세 정보와 관련된 내용을 다룹니다.
### 데이터 유효성 검사 실패의 중요성
*   JSON Schema 유효성 검사는 단순한 이진 검사(유효/무효)를 넘어 실패 이유에 대한 상세 정보를 제공합니다.
*   예를 들어, 필수 필드가 누락된 경우 누락된 필드의 이름을, 데이터 유형이 예상과 다른 경우 해당 정보를 얻을 수 있습니다.
### 데이터 유효성 검사 실패 정보 접근 방법
*   각 데이터 검사기 라이브러리(예: Ajv)는 유효성 검사 실패에 대한 정보를 노출하는 자체 방식을 가지고 있습니다.
*   Ajv의 경우, 마지막 데이터 유효성 검사에서 발생한 오류가 validator 인스턴스 내의 배열로 저장됩니다.
### 단일 실패의 경우
*   **예시:** "title" 필드 대신 "myTitle"을 사용하는 검색 도서 요청.
*   **Ajv에서의 오류 정보:** `ajv.errors` 배열에 저장됩니다.
*   **오류 정보의 형식 (Listing 7.21):**
```json
[
{
"instancePath": "",
"schemaPath": "#/required",
"keyword": "required",
"params": {
"missingProperty":"title"
},
"message": "must have required property 'title'"
}
]
```
*   `instancePath`: 오류가 발생한 데이터 내의 경로.
*   `schemaPath`: 오류와 관련된 스키마의 경로.
*   `keyword`: 오류를 발생시킨 JSON Schema 키워드.
*   `params`: 오류와 관련된 추가 정보 (예: 누락된 속성).
*   `message`: 오류에 대한 설명.
*   **Ajv의 `errorsText` 유틸리티 함수:** 오류 배열을 사람이 읽을 수 있는 형식으로 변환합니다.
### 다중 실패의 경우
*   **Ajv의 기본 동작:** 첫 번째 유효성 검사 오류만 감지합니다 (성능상의 이유).
*   **다중 오류 감지 활성화:** `Ajv` 생성자에 `allErrors: true` 옵션을 전달해야 합니다.
*   **예시 (Listing 7.23):**
```javascript
var ajv = new Ajv({allErrors: true});
```
*   `invalidSearchBooksRequest`가 "title" 필드를 누락하고, "fields" 배열에 문자열 대신 숫자를 포함하는 경우, 세 개의 오류가 반환됩니다.
*   `errorsText`를 사용하면 "data must have required property 'title', data/fields/0 must be string, data/fields/1 must be string"과 같은 사람이 읽을 수 있는 형식으로 오류를 확인할 수 있습니다.
### 요약
*   데이터 유효성 검사 실패 시 상세 정보를 활용하면 시스템의 경계를 개선하고 오류를 보다 효과적으로 처리할 수 있습니다.
*   JSON Schema의 사용은 웹 서버를 구축하고, 라이브러리 관리 시스템을 구축하는데 유용합니다.

구성노드1: ## 7.1 Data Validation in DOP: 시스템 경계에서의 데이터 검증 강화

### 핵심 내용 요약 및 DOP 원칙
*   **DOP 원칙 4 재확인:** 데이터 스키마와 데이터 표현의 분리 (7 Basic Data Validation의 기반).
*   **DOP에서의 데이터 검증:** 가능하며, 특히 시스템 경계에서 권장됨 (부모 노드 핵심 내용 반영).

### OOP vs. DOP: 데이터 유효성 관리 차이점
*   **OOP의 장점 (재확인):** 클래스 인스턴스화 시 필드 타입 보장으로 데이터 유효성 관리 용이.
*   **DOP의 문제점 (재확인):** 필드 이름/타입 오류로 인한 데이터 불일치 가능성.

### 시스템 경계와 데이터 검증의 중요성
*   **시스템 경계 정의 (상세):** 데이터 교환 지점 (클라이언트-서버, 서버-DB, 서버-외부 API 등) (부모 노드 상세 내용 반영).
*   **시스템 경계 검증 목적 (명확화):**
    *   유효하지 않은 데이터의 시스템 유입/유출 방지 (부모 노드 상세 내용 반영).
    *   오류 발생 시 구체적인 정보 제공 (상세 오류 정보, 7.5 절과의 연관성 강조).
*   **경계 검증의 효과 (강조):** 경계에서 검증 완료 시, 내부 재검증 불필요 (부모 노드 상세 내용 반영).

### 두 가지 종류의 데이터 검증 (개선)
*   **경계 검증 (가디언):** 시스템 입출력 데이터 유효성 검사 (가장 중요, 부모 노드 강조).
*   **내부 검증 (개발 편의):** 코드베이스 증가에 따른 개발 편의성을 위한 선택적 검증 (부모 노드 상세 내용 반영).

### 요약 및 중요성 강조
*   **핵심:** DOP에서 데이터 유효성 검증은 필수적이며, 특히 시스템 경계에서 중요.
*   **개선:** 유효성 검증 실패 시, 시스템 경계를 넘어 오류의 전파를 막고, 상세한 오류 정보를 제공하여 문제 해결을 돕는다. (7.5절 내용 미리 언급).

구성노드2: ## 7.2 JSON Schema in a nutshell: JSON Schema를 활용한 데이터 유효성 검사

### 핵심 내용 및 JSON Schema 소개
*   **핵심:** JSON Schema를 활용한 데이터 유효성 검사 방법 (부모 노드 핵심 내용 반영).
*   **데이터 유효성 검사 중요성 (재강조):** 데이터 무결성 유지, 시스템 오류 방지, 상세 오류 정보 제공 (7.5절 연계).
*   **JSON Schema 개요 (부모 노드 요약):** 데이터 구조 및 유효성 정의 언어, 데이터 표현과 분리, 언어 독립성 (다양한 언어 지원).

### 도서 검색 요청 스키마 정의 (단계별 상세화, 예시 보강)
1.  **요청 타입 정의:** JSON 객체 ("type": "object") (부모 노드 예시 재확인).
2.  **속성 정의 (상세):** "properties" 사용, 각 필드의 스키마 정의 (부모 노드 예시, 7.3절 연결).
    *   **title:** "string" 타입.
    *   **fields:** "array" 타입.
        *   **items:** 배열 요소 타입 지정 ("string").
        *   **enum:** 허용된 값 목록 지정 (예시: "publishers", "number\_of\_pages"). (부모 노드 예시 재확인).
3.  **필수 필드 정의:** "required" 배열 (예: ["title", "fields"]). (부모 노드 예시 재확인).

### JSON Schema를 이용한 데이터 유효성 검사 (라이브러리 및 에러 처리 강조)
*   **유효성 검사 라이브러리:** Ajv (예시), Snow, JSON.net Schema 등 다양한 언어 지원 (부모 노드 예시 재확인).
*   **검사 결과:** `true`/`false` 반환, 실패 시 상세 오류 정보 (7.5절 연결).
*   **실패 정보 활용:** 시스템 경계에서 유효하지 않은 데이터의 유입을 막고, 오류 메시지를 사용자 친화적으로 제공 (7.1절, 7.5절 연계).

### JSON Schema의 장점 (요약 및 추가)
*   **언어 독립성:** 다양한 언어 지원 (부모 노드 재확인).
*   **표현력:** 클래스 기반보다 복잡한 조건 표현 가능 (범위, 정규식 등).
*   **유연성:** 데이터 표현과 스키마 분리 (부모 노드 재확인).
*   **추가 강조:** 스키마의 재사용과 조합 용이성 (7.4절 연결).

구성노드3: ## 7.3 Schema flexibility and strictness: 유연성과 엄격성 사이의 균형

### 핵심 내용 및 필드의 유연성
*   **핵심:** JSON Schema의 유연성과 엄격성, 데이터 유효성 검사 모범 사례 (부모 노드 핵심 내용 반영).
*   **필드 필수 여부:** 기본적으로 선택적 (Optional) (부모 노드 재확인).

### 필수 필드 지정 및 예시 (상세화)
*   **필수 필드 지정 (재확인):** "required" 배열 사용. (부모 노드 재확인).
*   **예시 (확장):**
```json
{
  "type": "object",
  "required": ["title", "author"],
  "properties": {
    "title": { "type": "string" },
    "author": { "type": "string" },
    "description": { "type": "string" }
  }
}
```
*   "title", "author"는 필수, "description"은 선택적 (예시 추가).

### 스키마의 재사용 및 구성 (7.4절 연결)
*   **스키마 유연성 (재강조):** 맵(Map) 형태, 변수 할당, 다른 스키마 포함 용이 (부모 노드 재확인).
*   **스키마 분리 (재강조):** 가독성, 유지보수 용이 (부모 노드 재확인).
*   **예시:** "bookInfoSchema", "searchBooksResponseSchema" (부모 노드 예시 재확인, 7.4절 연결).

### 추가 속성 허용 여부 (additionalProperties)
*   **기본 동작 (재확인):** 추가 속성 허용 (부모 노드 재확인).
*   **추가 속성 금지 (재확인):** "additionalProperties: false" (부모 노드 재확인).
*   **예시 (확장):**
```json
{
  "type": "object",
  "required": ["title", "isbn"],
  "additionalProperties": false,
  "properties": {
    "title": { "type": "string" },
    "isbn": { "type": "string" }
  }
}
```
*   "title", "isbn" 외 속성 있으면 오류 발생 (부모 노드 예시 재확인).

### 데이터 유효성 검사 모범 사례 (핵심 강조, 7.1, 7.2, 7.5절 연계)
*   **외부 데이터 검증 (재강조):** 외부 소스 데이터 검증 필수 (부모 노드 재확인).
*   **송신 데이터 엄격성 (강조):** 응답(Response)은 "additionalProperties: false" 권장 (부모 노드 재확인).
*   **수신 데이터 유연성 (강조):** 요청(Request)은 유연하게 처리 (부모 노드 재확인).
*   **Jon Postel의 Robustness Principle (재확인):** "Be conservative in what you send, be liberal in what you accept." (부모 노드 재확인).
*   **요청/응답 차이 (중요성 강조):** 요청은 유연, 응답은 엄격 (부모 노드 재확인).
*   **실패 시 상세 오류 정보:** 시스템 경계에서 유효하지 않은 데이터의 유입을 막고, 오류 메시지를 사용자 친화적으로 제공 (7.1, 7.5절 연계).

구성노드4: ## 7.4 Schema Composition: 복잡한 조건, 강력한 유효성 검사

### 핵심 내용 및 배경: 외부 API 데이터 검증의 필요성
*   **핵심:** JSON Schema 조합 (Composition)을 통한 복잡한 데이터 구조 및 조건 표현 (부모 노드 핵심 내용 반영).
*   **배경 (재강조):** 외부 API 데이터 검증 필요성 (7.1절 연계, 시스템 경계 강조).
*   **예시:** Open Library Books API, "Watchmen" 책 정보 검증 (부모 노드 예시 재확인).

### 초기 스키마의 문제점 및 JSON Schema Composition 도입 (7.3절 연결)
*   **문제점 (재확인):** `isbn_10`, `isbn_13` 필수 여부 처리 (부모 노드 예시 재확인).
*   **JSON Schema Composition 소개 (7.2절 연계):** `allOf`, `anyOf`, `oneOf` (부모 노드 예시 재확인).

### JSON Schema Composition 구현 (예시 재강조)
1.  `basicBookInfoSchema` (제목 필수, 기타 필드 정의)
2.  `mandatoryIsbn13` (`isbn_13` 필수)
3.  `mandatoryIsbn10` (`isbn_10` 필수)
4.  `bookInfoSchema`: `basicBookInfoSchema` AND (`mandatoryIsbn13` OR `mandatoryIsbn10`) (부모 노드 예시 재확인).
*   **결과 (재강조):** 복잡한 필수 필드 조건 명확하게 표현 가능.

### JSON Schema Composition 사용의 장점 (7.2, 7.3절 연계)
*   **유연성 (재확인):** 여러 스키마 조합 (부모 노드 재확인).
*   **표현력 (재확인):** 클래스 기반보다 강력 (부모 노드 재확인).
*   **확장성 (재확인):** 다양한 조건 지원 (부모 노드 재확인).

### 추가 고려 사항 및 오류 정보 (7.5절 연결)
*   **검증 실패 시 오류 정보 (강조):** 상세 오류 정보 제공의 중요성 (7.5절 내용 언급).
*   **고급 데이터 검증 (언급):** Chapter 12에서 더 발전된 기법 다룸.

구성노드5: ## 7.5 Details about data validation failures: 오류 정보, 시스템 안정성 강화

### 핵심 내용 및 데이터 유효성 검사 실패의 중요성
*   **핵심:** JSON Schema 유효성 검사 실패 시 얻을 수 있는 상세 정보 활용 (부모 노드 핵심 내용 반영).
*   **데이터 유효성 검사 실패 중요성 (재강조):** 단순 이진 검사 이상, 상세 정보 제공 (부모 노드 재확인, 7.1절 연결).
*   **예시 (재확인):** 필수 필드 누락, 데이터 타입 불일치 시 정보 제공.

### 데이터 유효성 검사 실패 정보 접근 방법 (라이브러리 의존성)
*   **각 라이브러리 방식:** Ajv (예시), 다른 라이브러리도 자체 방식 (부모 노드 재확인).
*   **Ajv의 경우 (재확인):** `ajv.errors` 배열 저장.

### 단일 실패의 경우 (상세화, 예시 보강)
*   **예시 (재강조):** "title" 대신 "myTitle" (부모 노드 예시 재확인).
*   **Ajv 오류 정보 (재강조):** `instancePath`, `schemaPath`, `keyword`, `params`, `message` (부모 노드 예시 재확인).
*   **오류 정보 상세 설명 (재확인):** 각 필드의 의미 (부모 노드 상세 내용 반영).
*   **Ajv의 `errorsText` 유틸리티 함수 (재확인):** 사람 읽기 쉬운 형식으로 변환 (부모 노드 재확인).

### 다중 실패의 경우 (옵션 활용)
*   **Ajv 기본 동작 (재확인):** 첫 번째 오류만 감지 (성능) (부모 노드 재확인).
*   **다중 오류 활성화 (재확인):** `allErrors: true` 옵션 사용 (부모 노드 재확인).
*   **예시 (추가):** "title" 누락, "fields" 타입 오류 시 3개 오류 반환 (부모 노드 예시 재확인).
*   **`errorsText` 활용 (재확인):** 사람이 읽기 쉬운 형식으로 출력.

### 요약 및 중요성 강조 (7.1, 7.2, 7.3, 7.4절 연계)
*   **핵심 (재강조):** 상세 오류 정보 활용, 시스템 경계 개선, 오류 효율적 처리.
*   **JSON Schema 사용 (재확인):** 웹 서버, 라이브러리 관리 시스템 구축에 유용.
*   **강조:** 유효성 검사 실패 시의 상세 정보는, 시스템 경계를 강화하고, 문제 해결 시간을 단축하며, 사용자 경험을 개선하는데 기여한다. (7.1, 7.2, 7.3, 7.4절 내용 통합).
